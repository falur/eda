# 🌊 eda

> Поточная разработка с AI-агентами — на русском языке.
> Пакет готовых скилов и специализированных агентов для **Claude Code**, **Codex CLI** и **OpenCode V2**, которые ведут тебя через весь цикл: от исследования до коммита.

`eda` — это двадцать три скила и пакетные агенты для повторяемых ролей. Скил отвечает за пользовательский workflow и оркестрацию, агент — за изолированную работу с закреплённой моделью и ограничениями. Вместо того чтобы каждый раз объяснять модели, как делать ревью или как исполнять план, ты говоришь одно слово — и она следует чёткой инструкции на русском, со всеми правилами, проверками и артефактами в нужных папках.

## ⚡ Установка

```bash
npm install -g @gian-tiaga/eda
```

Обновляешься с `2.x` или более ранней версии? Перед обновлением прочитай [гайд по миграции на 3.0](MIGRATION.md): рабочие артефакты теперь лежат в `docs/artifacts/`.

В корне твоего проекта:

```bash
eda init
```

Установщик построен на `@clack/prompts`. Сначала он спрашивает платформы: по умолчанию ничего не отмечено, пробел отмечает Claude Code, OpenCode или Codex CLI, Enter продолжает, нужна хотя бы одна. Устанавливаются и скилы, и агенты. Если `docs/settings.yaml` ещё нет, установщик спрашивает только основные настройки в порядке работы: `eda-plan` (размер, решения, тесты), где выполнять `eda-plan-execute`, `eda-review` и `eda-polish`, глубину `eda-manual-test`, режим, этапы и исполнение `eda-orhestra`. Первым в каждом вопросе стоит вариант по умолчанию, «Спрашивать каждый раз» — последним. Редкие настройки и модели `review.agents` получают defaults и меняются вручную в `docs/settings.yaml`. Без интерактивного терминала устанавливаются все три среды и записываются defaults. В конце `eda init` отдельно пишет, какие скилы и агенты реально установлены или изменились.

Чтобы добавить OpenCode или другую платформу в проект с уже установленным EDA, запусти `eda update`. В интерактивном терминале команда при каждом запуске показывает все платформы: установленные уже отмечены, остальные можно добавить. Установленные обновляются в любом случае: снятая с них отметка ничего не удаляет. Enter без изменений обновляет текущий набор. Выбор фиксируется установленными каталогами и manifest каждой платформы, поэтому при следующем запуске она уже отмечена; отдельный список в `docs/settings.yaml` не нужен. Без TTY новые платформы не добавляются. Если ни одной среды ещё нет, сначала нужен `eda init`. У `update-all` выбор платформ не меняется: он обновляет только уже найденные среды.

После выбора платформ `eda update` переносит старые рабочие каталоги из `docs/<тип>/` в `docs/artifacts/<тип>/`, затем обновляет настройки, скилы и агентов. Содержимое файлов при переносе не меняется. Если один относительный путь уже существует в новой структуре, новый файл сохраняется, а старый удаляется.

Полный валидный v3-конфиг сохраняется, пока совпадает с актуальным шаблоном; если в пакете появились новые значения или подсказки, файл молча перерисовывается с сохранением ваших значений. Старый, неизвестный или неполный файл разбирается как YAML: известные значения переносятся, в TTY спрашиваются только отсутствующие основные настройки, редкие получают defaults, затем профиль целиком атомарно записывается как v3. Без TTY используются перенесённые значения и defaults.

Если пакет уже стоит во многих проектах, можно обновить его одной командой:

```bash
eda update-all ~/Code
```

`eda update-all` ищет проекты в указанной директории, её прямых подпапках и подпапках второго уровня. Проект считается найденным, если в нём уже есть установленный скил, агент или manifest `eda` для Claude/Codex/OpenCode. Служебные каталоги, включая `.opencode`, и symlink-директории не обходятся. В каждом проекте команда переносит рабочие артефакты, затем предлагает настроить один общий профиль для всех проектов или выбрать `skip`. В режиме `skip` актуальный полный v3 сохраняется, устаревший по шаблону перерисовывается, старые и неполные конфиги индивидуально переносятся, отсутствующие создаются с defaults. Без TTY автоматически используется `skip`. Ошибка одного проекта не останавливает остальные.

## 🛠️ Скилы

| Скил | Что делает | Куда складывает |
|---|---|---|
| `eda-orhestra` | Выполняет настраиваемую цепочку `eda-*`-скилов. В `subagents` каждый этап получает чистый контекст, в `main` этапы выполняет текущий агент, а `main_propagated` дополнительно передаёт `main` в совместимые execute/review-этапы. По умолчанию: план без проверок → полировка плана → выполнение → автономное ревью и исправления → ручные тесты. Если QA нашёл баг, оркестра запускает fix и повторяет только ручной тест. В `orhestra.steps` шаги можно переставлять, отключать и снабжать `args`. Не коммитит | Артефакты включённых скилов |
| `eda-aim` | Сначала через отдельного агента-планировщика согласует с человеком одну или несколько простых проверяемых целей, затем передаёт их агентам-исполнителям и повторяет работу до независимого подтверждения агентом-проверяющим. При необходимости использует установленные скилы в отдельных изолированных субагентах. В `automatic` отвечает на безопасные рабочие вопросы самостоятельно, в `manual` передаёт их человеку; режим задаётся через `aim.mode` или текущий вызов. Точный список новых целей человек подтверждает всегда | `docs/artifacts/aims/` и артефакты задействованных скилов |
| `eda-new-project` | Помогает стартовать новый проект: собирает и согласует требования, функциональность и границы, ограничения и архитектурные драйверы, сравнивает варианты основного стека и фиксирует выбранные компоненты с актуальными стабильными версиями. Если у стека есть официальный generator/scaffold CLI, передаёт его как обязательный способ разворачивания вместо ручного создания основы. Не проектирует архитектуру, правила, проверки, AI-скилы или MCP; сохраняет подтверждённый стартовый бриф и всегда без дополнительного вопроса запускает полный технический bootstrap через `eda-prepare-ai` | `docs/artifacts/project-starts/`, затем артефакты `eda-prepare-ai` |
| `eda-business` | Совместно с человеком описывает целевое поведение проекта по тематическим карточкам: сложные темы фиксирует подробно, но без шума, соседних модулей и привязки к текущему коду. Может закрепить значимый механизм вроде JWT или серверного хранения токенов, но не язык, библиотеку или конкретную СУБД. `about` содержит лишь короткое описание проекта и основные возможности. Карточка не больше 20 КБ: большую тему делит на подтемы, изменения вносит на месте без датированных дополнений | `docs/business.md`, `docs/business/` |
| `eda-roadmap` | Создаёт roadmap-файл: список будущих задач с короткими, понятными и недвусмысленными описаниями без деталей реализации, файлов, библиотек, API и пошагового плана | `docs/artifacts/roadmaps/` |
| `eda-explore` | Исследует тему до конкретного результата: описание проблемы, релевантная архитектура, закрытые развилки, риски внутри решений и короткий выбранный вариант решения без плана. После определения темы читает только применимые business- и reference-карточки. В дефолтном режиме ведёт исследование как диалог; для пакетов и ПО проверяет актуальные стабильные версии | `docs/artifacts/researches/` |
| `eda-plan` | Пишет план реализации: закрывает решения с пользователем, фиксирует контракты БД и API, устройство и дизайн интерфейса, консольные команды и фазы, каждую из которых один агент выполняет и проверяет за один проход. В разделе `Рамка` по строке на пункт выписывает всё, что задача обязана соблюдать из правил, архитектуры, эталонов, бизнес-карточек и `AGENTS.md`. `Целевой алгоритм` пишет сценариями из нумерованных шагов в порядке выполнения, а каждую таблицу БД — своей таблицей колонок. Каждый ответ пользователя попадает в `Принятые решения`, механизмов вне запроса и рамки план не добавляет. На подтверждение показывает полный план: в Claude Code — через Plan Mode, в Codex — в чате; сохраняет тот же текст. Для затронутой инфраструктуры, публичных страниц и частого пути ввода-вывода записывает решения, которые иначе принял бы исполнитель: переменные окружения и деплой, адреса и индексацию, допустимое число запросов и внешних вызовов. Если целевое поведение ещё не описано в business-карточках, до реализации добавляет `Дополнить бизнесовые правила`; если решение противоречит правилам или архитектуре, сначала меняет сам документ. Полировку плана не запускает — для неё есть `eda-plan-polish` и этап `eda-orhestra`; `plan.strict` включает кросс-CLI ревью | `docs/artifacts/plans/`, опционально plan-review артефакты |
| `eda-plan-review` | Одним read-only проходом проверяет план по фиксированному чек-листу из 22 пунктов: покрытие запроса фазами, отсутствие развилок, качества без меры и механизмов вне запроса, полноту `Рамки`, дубли и одинаковые имена, порядок разделов, формат алгоритма и таблиц БД, ошибки и восстановление в сценариях, тесты на каждую ветку алгоритма, удаляемое поведение, фазы с проверяемым результатом, объём и записанные решения по затронутой инфраструктуре, публичным страницам и числу запросов на частом пути. Замечания вне списка не принимает. Оценка — доля закрытых пунктов, поэтому растёт монотонно. План не меняет | `docs/artifacts/plan-reviews/` |
| `eda-plan-review-fix` | Закрывает проваленные пункты чек-листа минимальным изменением плана с совпадающим SHA-256. План не растёт: сначала удаление и замена, прирост объёма за один заход не больше 3%. Пункт, который не закрыть без роста, оставляет открытым со статусом `partial`; если план не изменился — `no-change`. Оба статуса не блокируют полировку. Новое ревью не делает и код не меняет | `docs/artifacts/plan-review-fixes/` |
| `eda-plan-polish` | Оркестрирует изолированный цикл plan-review → plan-review-fix до подтверждённых 100/100 без открытых пунктов или лимита попыток. Отсутствие прогресса не останавливает цикл. Хранит снапшот лучшей версии для восстановления при завершении без успеха. По умолчанию одна итерация: проверка и исправление. Исправление проверяет ревью следующей итерации, поэтому при `limit 1` последняя правка остаётся неперепроверенной. Кросс-CLI strict не используется | `docs/artifacts/plan-reviews/`, `docs/artifacts/plan-review-fixes/` |
| `eda-plan-execute` | Управляет выполнением плана по фазам в режиме `subagents`, `main` или `auto`. В `subagents` каждую фазу целиком выполняет отдельный изолированный субагент: он полностью читает план, его `Рамку` и все файлы из `sources`. Перед сдачей фазы исполнитель сверяет изменения с каждым пунктом `Рамки` и `Принятых решений`, а проверяющий повторяет эту сверку независимо. Поле `Согласование` останавливает работу до ответа пользователя, механизмов вне плана исполнитель не добавляет. Фазы проходят строго последовательно и принимаются независимыми проверяющими. В `main` весь план по тем же правилам выполняет и проверяет основной агент в одном контексте, а `auto` выбирает режим по плану. Отметки подтверждённых задач и журнал ведёт основной агент | `docs/artifacts/executions/` |
| `eda-just-do-it` | Сразу выполняет задачу из текста рядом с вызовом: определяет scope, загружает только необходимые проектные инструкции, business/reference-карточки, код и тесты, вносит нужные изменения и проверяет результат. Не подменяет выполнение планом и не делает git- или внешние действия без прямого указания | `docs/artifacts/just-do-it/` |
| `eda-fix` | Делает обычные фиксы по короткому контексту, баг-репорту или плану. Перед правками читает правила, архитектуру и только применимые карточки, добавляет нужные тесты, прогоняет проверки и сохраняет историю правок | `docs/artifacts/fixes/` |
| `eda-review` | Сначала отдельный агент `eda-review-triage` по содержимому ревью выбирает нужные проверки и применимые карточки, затем параллельно запускаются только они. Оркестрирует отдельные read-only проверки корректности, архитектуры, правил, references, business-правил, плана, качества, тестов, безопасности, производительности, frontend/UI/UX, API, БД, инфраструктуры, SEO, документации и предыдущих ревью. Производительность сравнивает base и head: рост числа запросов к БД и внешних вызовов на ту же операцию считается дефектом, а не оптимизацией. Инфраструктура и SEO проверяют только затронутое изменением и берут проектные решения вроде канонического хоста из `docs/rules.md`. Для PR/MR переиспользует результаты CI текущего head и не запускает локально уже завершённые там тесты, линтеры, typecheck, сборку и аналогичные проверки; смысловое ревью diff при этом выполняется полностью. Сохраняет только доказанные дефекты, которые обязательно исправить; косметические и спекулятивные предложения отбрасывает. Любая находка даёт `changes-required`, а чистое ревью — `clean` и 100/100. Без аргументов ревьюит `git diff HEAD` | `docs/artifacts/reviews/` |
| `eda-fix-by-review` | Применяет все находки из ревью с учётом правил, архитектуры и применимых карточек. Спрашивает только при неоднозначности, конфликте, расширении scope или рискованном действии. В конце ссылается на отчёт прямо в файле ревью | `docs/artifacts/review-fixes/` |
| `eda-manual-test` | Делает ручную проверку после изменений. По умолчанию проверка полная: разбирает план или другой артефакт по разделам, дополняет его фактическим `git diff HEAD` и закрывает матрицу областей — API, база данных, консольные команды, интерфейс, алгоритмы, фон и интеграции, права и роли, конфигурация, логи, регрессии рядом. Область нельзя закрыть чтением кода или зелёными автотестами; незакрытая область даёт `blocked`. Быстрый smoke включается настройкой `manual-test.depth` или словом в запросе. Применимая business-карточка может добавить только относящийся к задаче инвариант или сценарий. Не правит код, не пишет автотесты и не коммитит | `docs/artifacts/manual-tests/` |
| `eda-prod-check` | Read-only диагностика работающего прода или стейджа: «почему каждая страница открывается 5 секунд». Сначала замеряет симптом в цифрах, затем проходит слои снаружи внутрь — сеть и TLS, отдача статики, сервер (CPU, steal, память, диск), веб-сервер, runtime (opcache, PHP-FPM), приложение (debug, кеши фреймворка, драйверы), база, фронтенд — и сохраняет отчёт с причинами, их вкладом, доказательствами и исправлениями с ожидаемым эффектом. На сервере ничего не меняет и секреты не выводит | `docs/artifacts/prod-checks/` |
| `eda-polish` | Оркестрирует доводку изменений: запускает полное `eda-review`, затем `eda-fix-by-review` и повторяет цикл до подтверждённых 100/100, `clean` и отсутствия находок либо до лимита 5 итераций. Отсутствие прогресса не останавливает цикл. Режим цикла задаёт `polish.execution`: в `main` оба контракта выполняет основной агент без субагентов, в `subagents` каждый шаг получает отдельный изолированный контекст. Все находки исправляются. Не коммитит | `docs/artifacts/reviews/`, `docs/artifacts/review-fixes/` |
| `eda-send-review` | На `sonnet` / `gpt-5.6-terra` отправляет ревью на открытый GitHub PR через `gh` всегда в едином формате: общий комментарий-сводка плюс комментарии к строкам кода. Закрытый или смерженный PR не переиспользует и предлагает создать новый либо указать другой открытый PR. Без явно указанного типа использует `comment`; `approve` и `request-changes` берёт только из контекста текущего вызова. По настройке может скрыть предыдущие сводки eda-send-review и зарезолвить их inline-треды. По умолчанию шлёт все пункты. Claude-модель закрепляется при установке; Codex-модель хранится как рекомендуемый будущий override | (комментарий в PR) |
| `eda-commit` | Работает как лёгкий оркестратор одного `sonnet` / `gpt-5.6-terra` агента: тот сам собирает git-контекст, пишет сообщения и тексты PR по исходному запросу и фактическим изменениям, точечно коммитит и выполняет явно заданные push/PR/merge-действия. Агент экономит время: собирает контекст одним вызовом, не читает кодовую базу и документацию целиком, вместо полного diff берёт сводку `--stat` и дочитывает только неясные файлы, а смысл работы берёт из свежих артефактов `docs/artifacts/**`, если они есть в составе изменений. Весь состав идёт одним коммитом; на несколько логически цельных коммитов он делится только по явной просьбе (`split`, «раздели», «отдельными коммитами») или при явно раздельном scope. Для PR использует шаблон репозитория, отражает все группы изменений и указывает только реально выполненные проверки; существующим считает только открытый PR, а после закрытого или смерженного создаёт новый. С явным контекстом охватывает указанный состав; без контекста коммитит всё — все tracked-изменения и все untracked-файлы независимо от авторства и связи с текущей задачей, кроме очевидных кэшей и локальных служебных артефактов вроде `.DS_Store`. В Claude Code сам оркестратор закреплён за `sonnet`; в Codex остаётся на активной модели сессии из-за отсутствия per-skill override. При вероятном секрете агент блокируется до индексации затронутой группы. После любого push всегда возвращает ссылку — на существующий PR или на его создание — и спрашивает, создавать ли PR, если его нет. ### Структура `docs/`

Постоянная документация проекта остаётся непосредственно в `docs/`: `settings.yaml`, `rules.md`, `arch.md`, `business.md`, каталог `business/`, `references.md` и каталог `references/`. Все временные и рабочие результаты скилов лежат в `docs/artifacts/<тип>/`.

Версия 3.0 не поддерживает старые пути во время работы скилов. `eda update` и `eda update-all` физически переносят известные старые каталоги, но сохраняют байты файлов как есть: ссылки вида `docs/plans/...`, уже записанные внутри исторических документов, не переписываются. `eda init` миграцию артефактов не запускает.

### Business-контекст

`eda-business` хранит в `docs/business.md` только простое оглавление из двух колонок — описание темы и ссылка на готовую согласованную карточку. Степень подробности определяется темой: сложная аутентификация может подробно фиксировать вид токенов, их выпуск, обновление и отзыв, тогда как `about` остаётся коротким описанием проекта и основных возможностей. Карточки не привязываются к путям, классам и внутренним модулям текущего кода; значимый механизм вроде JWT указать можно, а язык, библиотеку, конкретную СУБД и схему реализации — нет. Последний раздел содержит только прямые расхождения поведения по собственной теме.

Потребляющий скил сначала определяет текущую задачу и фактически затронутое поведение, а затем выбирает по описаниям только применимые business-карточки. Отсутствие подходящей карточки не является ошибкой и не требует загружать остальные. Если задача противоречит карточке, агент показывает конфликт и спрашивает человека, изменить задачу или пересогласовать правило через `eda-business`.

`eda-review-check` выведен из эксплуатации: его специализированные проверки теперь входят прямо в `eda-review`. `eda-execute` переименован в `eda-plan-execute`, `eda-automate` — в `eda-discover-automations`, `eda-docs` — в `eda-prepare-ai`, а `eda-start` — в `eda-new-project`. Контекстный агент `eda-commit-context` также выведен из эксплуатации: сбор контекста теперь выполняет единый `eda-commit-executor`. При обновлении старые имена удаляются из целевых сред. Установщик удаляет только управляемые EDA-копии retired-компонентов и не трогает чужие компоненты.

### Экстремальный профиль проверок

`eda-prepare-ai` и `eda-discover-automations` проходят не короткий список, а полный стек-зависимый каталог. В него входят unit/integration/component/contract/API/e2e/smoke/regression-тесты; property-based, mutation и fuzz; visual regression, accessibility и cross-browser; форматирование, lint, сложность, дубли и dead code; typecheck, taint и sanitizers; границы модулей, циклы и направления зависимостей; валидация env, CI, Docker, Kubernetes, Terraform, прокси и других конфигов, включая редиректы на HTTPS и канонический хост; API/схемы и migrations; security, supply chain и SBOM; performance/load/soak/chaos и тесты на число запросов к БД и внешних вызовов; SEO и индексация публичных страниц; reproducible build, compatibility и release checks; документация, observability, backup/restore, доменные инварианты и AI evals.

Для каждой применимой проверки скил указывает инструмент, точную команду или сценарий, риск и место запуска: `pre-commit`, `pre-push`, `PR CI`, `nightly`, `release`, `post-deploy` или `MCP/manual`. Browser/Playwright MCP и MCP выбранного стека рассматриваются отдельно и не подменяют детерминированные CLI/CI-проверки. Фиксированного лимита предложений нет; неприменимые группы должны иметь явное обоснование.

`eda-prepare-ai` разбирает значимые настройки каждого выбранного инструмента и предлагает самый строгий стабильный применимый профиль, а не конфигурацию по умолчанию. Для динамических и слаботипизированных языков это включает строгий typecheck, nullability, типизированные публичные контракты и runtime-валидацию внешних данных; для линтеров, статанализа, тестов, security и CI — максимальные полезные наборы проверок, нулевой бюджет предупреждений и явное обоснование каждого ослабления.

Агенты устанавливаются отдельно от скилов. Модели review-агентов в таблице — сбалансированные defaults; `docs/settings.yaml` или прямое указание пользователя может заменить модель конкретной проверки на текущий запуск в режиме `subagents`. `eda-aim` последовательно разделяет согласование, выполнение и независимую проверку, а при необходимости использует установленные скилы только в отдельных изолированных субагентах; основной агент передаёт вопросы и структурированные результаты. `eda-commit` сохраняет исходный запрос и целиком передаёт сбор контекста, выбор файлов, коммит и разрешённое продолжение одному простому агенту. `eda-worktree` и `eda-merge-worktree` передают одному специализированному агенту git-операцию, обрабатывают его вопрос или результат и сами команды не выполняют. `eda-review` поддерживает два режима: `subagents` параллельно запускает применимых review-агентов, а `main` выполняет те же проверки основным агентом без субагентов. Чек-лист каждой проверки хранится в одном файле `skills/eda-review/references/checks/<проверка>.md`: его читает `main`, а установщик встраивает в агента, поэтому оба режима проверяют одно и то же. Чек-лист перечисляет конкретные классы дефектов: тихие сбои и гонки, доступ к чужим объектам, SSRF и prompt injection, совместимость API для старых клиентов, миграции без простоя, вес CSS и JS, сжатие и кеш статики, production-настройки. В Codex специализированные review-агенты запускаются с `fork_turns: "none"`, без наследования истории. В `subagents` все выбранные проверки отправляются одним нативным параллельным пакетом без ручных партий и shell-опроса.

Для Claude Code установленный `eda-commit` получает `model: sonnet`, а `eda-worktree` и `eda-merge-worktree` — `model: haiku`. В Codex у скилов пока нет отдельного per-skill model override: основной поток остаётся на выбранной пользователем модели, но он выполняет только лёгкую оркестрацию; содержательная работа `eda-commit` закреплена за `gpt-5.6-terra`, а worktree-операции — за `gpt-5.6-luna`.

Codex-копии скилов начинаются с платформенного адаптера, а Codex-агенты заканчиваются тем же правилом чтения. Codex обрезает середину длинного вывода команды, поэтому вывод с пометкой `tokens truncated` не считается прочитанным файлом: агент дочитывает пропущенные строки, большие файлы читает частями, а документы рамки и план — только целиком. Интерактивный `request_user_input` адаптер запрещает и в скилах, и в агентах: Codex сам сворачивает его окно, и непонятно, что агент ждёт ответа. Вопросы в Codex задаются только текстом в чат по разделу «Вопросы текстом», после чего агент завершает ход до ответа. `Agent` адаптер сопоставляет со `spawn_agent`, а Plan Mode — с показом полного плана в чате; `update_plan` документ плана не заменяет.

### OpenCode V2

Вызывай скилы через `@eda-plan`, `@eda-review` и другие точные ID. OpenCode-копии содержат платформенный адаптер: вложенные скилы загружаются через `skill`, агенты запускаются через `subagent`, вопросы задаются через `question`. Изолированные шаги оркестраторов выполняет `eda-skill-runner`, а не встроенный general, у которого запрещены вложенные субагенты. Режимы `main` / `subagents` сохраняют обычные границы.

Все OpenCode-агенты по умолчанию наследуют модель сессии: колонки Claude/Codex в таблице выше к OpenCode не применяются. Модели ролей ревью из `review.agents` в формате `provider/model#variant` OpenCode применяет как есть. В каноническом `agent.json` можно задать необязательное `models.opencode` в формате `provider/model#variant`; variant необязателен. Модель можно настроить средствами OpenCode. Per-skill модель не назначается. При явном runtime override, который хост не поддерживает, скил возвращает `blocked`, а не молча заменяет модель.

Read-only роли используют V2 `permissions`: разрешены чтение, поиск и web-инструменты, запрещены shell, редакторы, MCP и субагенты. Оркестратор передаёт им diff и git/CI-контекст; такие агенты сами не запускают тесты. Git-write роли не получают редакторов, но shell наследует разрешения пользователя; workspace-write также не переопределяет пользовательские разрешения. Это правила инструментов, не отдельный OS sandbox.

Установщик не меняет `opencode.json(c)` и не требует перезапуска OpenCode. Скилы `.opencode/skills` имеют приоритет над совместимыми копиями `.claude/skills` и `.agents/skills` с тем же ID. Если нет обязательного инструмента, разрешения или нативного Plan Mode, workflow сообщает конкретный блокер. В strict из OpenCode нужно явно выбрать внешний Claude Code или Codex CLI либо ответить на вопрос скила.

## 🚩 Флаги скилов

У некоторых скилов есть флаг `strict` — он включает дополнительные тяжёлые проверки. Передаётся как часть запроса агенту, например: `eda-explore strict <тема>`. Также strict можно включить отдельно в `docs/settings.yaml`, например через `explore.strict: true`. У `eda-review` режим исполнения задаётся через `subagents` / `main`, а состав проверок — через собственные `mode` и `model`.

У `eda-plan-execute` есть режимы `main` / `auto` / `subagents`. Режим можно разово указать в вызове, например `eda-plan-execute subagents docs/artifacts/plans/....md`; без него используется `plan-execute.mode` из настроек, а без настроек — `main`.

Выбранный режим исполнения обязателен для `eda-plan-execute`, `eda-review`, `eda-polish` и `eda-orhestra`. При `main` из вызова или настроек агент не может перейти к субагентам из-за большого плана, diff или нехватки контекста. Прогресс и режим сохраняются для продолжения после сжатия контекста; при технической невозможности продолжить агент сообщает блокер. Выбор по размеру плана разрешён только в `eda-plan-execute auto` до начала выполнения. Зафиксированный режим меняется только по новому прямому указанию пользователя; `automatic` оркестратора такого права не даёт. У оркестратора `main` по-прежнему управляет только верхней цепочкой, а `main_propagated` также передаёт `main` совместимым execute/review-этапам; остальные вложенные контракты сохраняются.

У `eda-aim` есть режимы `automatic` / `manual`. В автоматическом основной агент сам отвечает на безопасные рабочие вопросы по рекомендации субагента и фактам проекта, в ручном передаёт их человеку. Режим можно разово указать в вызове; без него используется `aim.mode` из настроек. Точный список новых целей перед записью в `docs/artifacts/aims/` всё равно один раз подтверждает человек.

Скилы, которых нет в таблице ниже, не поддерживают эти флаги. Набор проверок `eda-review` выбирает `eda-review-triage` по содержимому ревью; модели и effort ролей задаются в `review.agents`.

| Скил | Флаг | Что включает | Когда стоит использовать |
|---|---|---|---|
| `eda-orhestra` | `automatic` / `manual`, `subagents` / `main` / `main_propagated`, `без полировки плана`, `без полировки кода`, `полировка кода N итераций`, `без ручных тестов` | Разово меняет вопросы, исполнение, состав цепочки и параметры шагов поверх `docs/settings.yaml` | `main` экономит верхний слой, `main_propagated` также включает main у совместимых execute/review-этапов |
| `eda-aim` | `automatic` / `manual` | Разово меняет способ ответа на рабочие вопросы поверх `aim.mode`; подтверждение точного списка новых целей остаётся обязательным | Автономная работа или совместное прохождение развилок с человеком |
| `eda-explore` | `strict` | После сохранения отчёта отдаёт его соседнему CLI (Claude → Codex или наоборот) на критическое ревью конкретности, фактов, развилок, рисков и версий; затем доправляет отчёт по замечаниям | Серьёзные исследования, которые лягут в основу больших решений; когда хочется второго мнения от другой модели/среды |
| `eda-plan` | `strict`, `без проверок` | `strict` включает кросс-CLI проверку плана; `без проверок` её отключает. Полировку плана `eda-plan` не запускает: для неё есть `eda-plan-polish` и этап `eda-orhestra` | Когда нужна независимая проверка плана другим CLI |
| `eda-plan-review` | `threshold N` | Разово меняет долю закрытых пунктов, при которой план считается готовым | Для самостоятельного аудита готового плана |
| `eda-plan-execute` | `subagents` / `main` / `auto` | Разово меняет, где выполняются фазы, поверх `plan-execute.mode` | `main` для обязательного выполнения основным агентом, `subagents` для изолированных фаз, `auto` для выбора по размеру плана |
| `eda-plan-polish` | `limit N` | Меняет максимальное число итераций «проверка + исправление»; gate всегда 100, `threshold N` игнорируется | Для доводки ответственных планов перед `eda-plan-execute` |
| `eda-manual-test` | `full` / `полная проверка`, `smoke` / `быстро` | Разово меняет глубину ручной проверки поверх `manual-test.depth` | `smoke` для короткой правки, `full` — когда нужно закрыть все области после плана |
| `eda-polish` | `subagents` / `main`, `limit N` | Разово меняет способ выполнения review и исправлений поверх `polish.execution` и число итераций | `subagents` держит каждый шаг в чистом контексте, `main` экономит контекст на мелкой доводке |
| `eda-review` | `subagents` / `main` | Разово меняет способ выполнения выбранных проверок поверх `review.execution` | `main` экономит контекст на частых локальных ревью; `subagents` сохраняет независимость ролей для ответственных изменений |

## ⚙️ Настройки проекта

Скилы читают `docs/settings.yaml`, если файл есть. Прямое указание в текущем запросе важнее настроек: например, `strict` включает строгий режим для одного запуска, а `normal` / `без strict` выключает его. Для `eda-plan` явный `short` включает короткий план, а `normal` / `обычный план` — обычный.

Файл по умолчанию:

```yaml
version: 3

explore:
  # Включает кросс-CLI ревью в eda-explore.
  # false | true
  strict: false
  # Как eda-explore ведёт исследовательские развилки.
  # recommend_and_ask | autonomous | ask_each_time
  decision_mode: recommend_and_ask

plan:
  # Размер плана.
  # normal | short | ask_each_time
  size: normal
  # Как eda-plan принимает существенные решения.
  # recommend_and_ask | autonomous | ask_each_time
  decision_mode: recommend_and_ask
  # Когда писать тесты и запускать автоматические проверки.
  # phase_tests_final_checks | tdd_each_phase | after_each_phase | end_of_plan | ask_each_time
  test_strategy: phase_tests_final_checks
  # Стратегия логирования.
  # standard | debug_precise | ask_each_time
  logging_strategy: standard
  # Включает кросс-CLI ревью в eda-plan.
  # false | true
  strict: false

plan-review:
  # Доля закрытых пунктов чек-листа, при которой план считается готовым.
  # 1..100
  threshold: 100

plan-polish:
  # Максимальное число итераций «проверка + исправление».
  # Положительное целое число.
  limit: 5

plan-execute:
  # Где eda-plan-execute выполняет фазы плана.
  # main — весь план одним контекстом, auto — решает по плану, subagents — каждая фаза в отдельном субагенте.
  mode: main

review:
  # Где eda-review выполняет выбранные проверки.
  # main — все проверки основным агентом без субагентов, subagents — разведчик и отдельный агент на проверку.
  execution: main
  # Какие проверки нужны, решает eda-review-triage по содержимому ревью.
  # Модель роли в subagents: default — модель установленного агента, иначе provider/model#variant,
  # например anthropic/claude-opus-5-5#high или deepseek/deepseek-flash-4.1; variant задаёт effort.
  # Если среда не может запустить модель, роль идёт на модели агента с предупреждением в ревью.
  # В main все проверки выполняет текущая модель.
  agents:
    triage: default
    correctness: default
    architecture: default
    rules: default
    references: default
    business: default
    plan_alignment: default
    code_quality: default
    tests: default
    security: default
    performance: default
    frontend: default
    api: default
    database: default
    infra: default
    seo: default
    documentation: default
    previous_reviews: default

polish:
  # Где eda-polish выполняет review и исправления цикла полировки.
  # subagents — каждое review и каждое исправление в отдельном изолированном субагенте, main — оба контракта основным агентом.
  execution: subagents

manual-test:
  # Глубина ручной проверки в eda-manual-test.
  # full — закрыть все применимые области: API, база, консольные команды, интерфейс, алгоритмы, фон, права, конфигурацию, логи и регрессии рядом.
  # smoke — только запуск и основной сценарий изменённой области.
  # full | smoke | ask_each_time
  depth: full

send-review:
  # После успешной отправки скрывает предыдущие сводки eda-send-review и резолвит их inline-треды.
  # true | false
  close_previous_reviews: true

discover-automations:
  # Добавляет docs/artifacts/plans/ в обычный запуск eda-discover-automations.
  # false | true
  include_plans: false

orhestra:
  # Режим полного цикла eda-orhestra.
  # automatic | manual
  mode: automatic
  # Где выполняются этапы и передаётся ли main совместимым вложенным скилам.
  # subagents | main | main_propagated
  execution: subagents
  # Упорядоченная цепочка. Шаги можно отключать, удалять и переставлять.
  steps:
    - id: plan
      skill: eda-plan
      enabled: true
      # Строка аргументов передаётся скиллу как часть текущего вызова.
      args: "без проверок"
    - id: plan-polish
      skill: eda-plan-polish
      enabled: true
      # Строка аргументов передаётся скиллу как часть текущего вызова.
      args: ""
    - id: execute
      skill: eda-plan-execute
      enabled: true
      # Строка аргументов передаётся скиллу как часть текущего вызова.
      args: ""
    - id: polish
      skill: eda-polish
      enabled: true
      # Строка аргументов передаётся скиллу как часть текущего вызова.
      args: "limit 5"
    - id: manual-test
      skill: eda-manual-test
      enabled: true
      # Строка аргументов передаётся скиллу как часть текущего вызова.
      args: ""
      # Обработка failed-результата этого шага.
      on_failure:
        skill: eda-fix
        args: ""
        # После исправления повторно запускаются включённые шаги с этими id.
        then:
          - manual-test
        max_cycles: 5

aim:
  # Режим ответов на рабочие вопросы eda-aim.
  # automatic | manual
  mode: automatic
```

Что означают настройки:
- `orhestra.mode` — `automatic` безопасно закрывает рабочие вопросы без промежуточных подтверждений; `manual` пишет план вместе с человеком и передаёт ему вопросы.
- `orhestra.execution` — `subagents` запускает каждый этап отдельно, `main` выполняет верхнюю цепочку текущим агентом, `main_propagated` дополнительно передаёт `main` шагам `eda-plan-execute`, `eda-polish` и прямому `eda-review`; default `subagents`. Другие вложенные скилы сохраняют собственный контракт.
- `orhestra.steps` — выполняемый сверху вниз workflow. `enabled: false` отключает шаг, а `args` передаёт ему дополнительные параметры. Например, для `eda-polish`: `args: "limit 2"`. Шаги можно переставлять или добавлять, но git/publish-скиллы оркестратор не запускает.
- Старое значение `steps[].skill: eda-execute` во время запуска автоматически понимается как `eda-plan-execute`; существующий `docs/settings.yaml` установщик не переписывает.
- `steps[].on_failure` — настраивает исправление failed manual-test прямо рядом с этим шагом: `skill` и `args` задают фикс, `then` — повторяемые id шагов, `max_cycles` — лимит. Если обработчика нет, оркестратор сохраняет failed-отчёт и останавливается.
- `aim.mode` — `automatic` самостоятельно выбирает безопасные ответы на рабочие вопросы; `manual` передаёт вопросы человеку. Явный режим в текущем вызове имеет приоритет.
- `explore.strict` и `explore.decision_mode` — кросс-CLI ревью и способ выбора по исследовательским развилкам в `eda-explore`.
- `plan.strict` — кросс-CLI ревью плана в `eda-plan`. Полировки плана внутри `eda-plan` нет: её делает `eda-plan-polish` отдельно или этапом `eda-orhestra`.
- `plan.size`, `plan.decision_mode`, `plan.test_strategy`, `plan.logging_strategy` — режим и структура работы `eda-plan`. Имя `test_strategy` сохранено для совместимости, но настройка управляет и тестами, и автоматическими проверками: `after_each_phase` запускает их после каждой фазы, `tdd_each_phase` сначала пишет тесты и после реализации запускает все проверки фазы, `phase_tests_final_checks` в фазе запускает только добавленные или изменённые ею тесты, а остальные проверки оставляет финалу, `end_of_plan` переносит тесты и автоматические проверки в конец плана. Defaults: `size: normal`, `decision_mode: recommend_and_ask`, `test_strategy: phase_tests_final_checks`, `logging_strategy: standard`.
- `plan-review.threshold` — доля закрытых пунктов чек-листа для статуса `ready`, default `100`. Отдельных агентов у `plan-review` больше нет: проверку целиком делает один субагент.
- `plan-polish.limit` — максимальное число итераций «проверка + исправление»; default `5`. Отдельного подтверждающего прохода нет: исправление проверяет ревью следующей итерации. Отсутствие роста score, повторные пункты и исправление без изменений цикл не останавливают: он идёт до 100/100 или лимита.
- `plan-execute.mode` — где `eda-plan-execute` выполняет фазы: `subagents` — каждая фаза в отдельном изолированном субагенте с независимой проверкой, `main` — весь план одним контекстом без субагентов, `auto` — выбор по плану; default `main`. Явный режим в вызове имеет приоритет.
- `polish.execution` — где `eda-polish` выполняет review и исправления своего цикла: `subagents` — каждый шаг в отдельном изолированном субагенте, `main` — оба контракта основным агентом; default `subagents`. Настройка независима от `review.execution`, которая задаёт только раскладку проверок внутри `eda-review`. Явный режим в вызове и `main` от `eda-orhestra` в `main_propagated` имеют приоритет.
- `manual-test.depth` — глубина ручной проверки в `eda-manual-test`: `full` — закрыть все применимые области матрицы покрытия, `smoke` — только запуск и основной сценарий изменённой области, `ask_each_time` — спрашивать каждый раз; default `full`. Явная глубина в вызове имеет приоритет.
- `review.execution` — где выполняются проверки `eda-review`: `subagents` запускает отдельные специализированные роли, `main` выполняет те же выбранные проверки основным агентом без субагентов и с однократной загрузкой общего контекста; default `main`. Явный режим в вызове имеет приоритет.
- `review.agents.<role>` — одна строка на роль: `default` или модель `provider/model#variant`, где provider и variant необязательны, а variant задаёт effort. Например: `security: anthropic/claude-opus-5-5#high`, `triage: deepseek/deepseek-flash-4.1`, `tests: default#high`. `default` — модель и effort установленного агента: в Claude Code и Codex — из `agent.json`, в OpenCode — модель агента или сессии. Установщик пишет `default` и о моделях не спрашивает; значения меняются вручную. Применяются только в `subagents`, в `main` работает текущая модель агента.
- Одна строка действует во всех средах проекта. Claude Code запускает только модели Claude, Codex — только OpenAI, OpenCode — любые. Если текущая среда не может запустить указанную модель, роль выполняется на модели установленного агента, а в покрытии ревью появляется warning.
- Режимов `always` / `auto` / `off` у проверок нет: какие проверки нужны, решает `eda-review-triage` по содержимому ревью, а в `main` — основной агент по той же таблице. При переходе на 4.0 `eda update` ставит `default` всем ролям и переписывает конфиг; после этого заданные вручную модели сохраняются, а значение не в формате `default` или `provider/model#variant` заменяется на `default` с сообщением.
- `eda-review` не делит находки по обязательности: каждый принятый пункт требует исправления, а предложения без доказанного практического дефекта отбрасываются. Score остаётся экспертной оценкой серьёзности; любая находка блокирует `clean` независимо от score.
- `send-review.close_previous_reviews` — после успешной новой отправки скрывает предыдущие сводки, созданные `eda-send-review` текущим GitHub-пользователем, и резолвит связанные inline-треды; default `true`, прямое указание в текущем запросе переопределяет настройку.
- `discover-automations.include_plans` — добавляет `docs/artifacts/plans/` в обычный запуск `eda-discover-automations`.

Каждый скилл читает только свой раздел. Для `eda-review` прямое указание в текущем запросе может разово включить или отключить проверку и заменить её модель или effort, например: «без performance, включи business, architecture на anthropic/claude-opus-5-5#high, security на default#xhigh». Такие указания важнее выбора triage.

Поддерживается только `version: 3`. Полный валидный v3 установщик сохраняет как есть, пока его текст совпадает с шаблоном пакета; когда шаблон меняется — например, у настройки появляется новое допустимое значение, — файл перерисовывается без вопросов: ваши значения переносятся, посторонние ключи и ручные комментарии не сохраняются. Старые, неизвестные и неполные файлы разбираются через YAML: валидные известные значения переносятся, в TTY спрашиваются только отсутствующие, затем профиль целиком атомарно нормализуется. Без TTY недостающие поля получают defaults. `plan.review`, `plan.meta_review` и `plan-polish.strict` удаляются.

`eda update-all configure` записывает один общий v3-профиль. `skip` сохраняет актуальный полный v3 и перерисовывает устаревший по шаблону, индивидуально переносит остальные конфиги и создаёт defaults при отсутствии файла. Подробности перехода приведены в [MIGRATION.md](MIGRATION.md)

## 🔄 Воркфлоу

`eda-orhestra` по умолчанию запускает основной цикл одной командой:

В default `subagents` каждая стрелка передаёт явный вход и пути к артефактам в новый изолированный субагент. В `main` и `main_propagated` верхние этапы идут последовательно в текущем контексте.

```text
plan без проверок → plan-polish → plan-execute → polish → manual-test ──passed──> готово
                                                                  ^          │
                                                                  └── fix <───┘ failed
```

`eda-aim` может обернуть любую цепочку ниже в автономный цикл:

```text
согласование цели → выполнение с нужными скилами в изолированных субагентах → независимая проверка
                              ^                         │
                              └──── устранение пробелов ─┘
```

```text
new-project ───────> prepare-ai ─────────┬───────────────┐
                    │                     │               │
                    v                     v               v
                 roadmap ────────> explore ─────> plan ───> plan-polish ───> plan-execute ───┬──> manual-test ───> review ───> fix-by-review ───┬──> send-review
                                              │                         │                                  │
                                              └────────────> plan       v                                  └──> commit
                                                                     fix ─────────────> manual-test
```

Если проект уже существует, можно начинать без `eda-new-project`:

```text
prepare-ai ─────────┬───────────────┐
                    │               │
                    v               v
roadmap ────────> explore ─────> plan ───> plan-polish ───> plan-execute ───┬──> manual-test ───> review ───> fix-by-review ───┬──> send-review
                    │                                  │                                  │
                    └──────────────> plan              v                                  └──> commit
                                                      fix ─────────────> manual-test

polish = полное review ─> fix-by-review всех находок ─> подтверждающий review до clean и нужной оценки
plan-polish = итерации «plan-review ─> plan-review-fix всех находок» до gate или limit

discover-automations может запускаться от review, fix-by-review или fix.
```

`eda-manual-test` обычно ставится после `eda-plan-execute`, `eda-fix` или `eda-fix-by-review`, чтобы руками проверить API, базу, консольные команды, интерфейс и алгоритмы перед ревью или коммитом.

Использовать всю цепочку не обязательно — каждый скил самодостаточен. Для полного прохода одной задачи можно вызвать `eda-orhestra automatic <задача>` или `eda-orhestra manual <задача>`. Разовые варианты: `eda-orhestra main <задача>`, `eda-orhestra main_propagated <задача>`, `eda-orhestra automatic без полировки плана <задача>`, `eda-orhestra полировка кода 2 итерации <задача>`, `eda-orhestra без ручных тестов <задача>`. Постоянный режим исполнения задаётся в `orhestra.execution`, порядок и аргументы — в `orhestra.steps`. Для прямой задачи без отдельного процесса вызови `eda-just-do-it <задача>`: скил сам выберет необходимый контекст, выполнит работу и сохранит отчёт. Новый проект можно начать с `eda-new-project`; существующий — с `eda-prepare-ai`, `eda-roadmap`, `eda-explore`, или сразу с `eda-plan-execute` на готовом плане, или просто `eda-commit`, когда правки уже сделаны. Для параллельной работы есть `eda-worktree`, а для возврата ветки из worktree в текущую ветку — `eda-merge-worktree`.

Вызов `eda-commit` без контекста охватывает все незакоммиченные tracked-изменения и все untracked-файлы, в том числе чужие и не относящиеся к текущей задаче; очевидные кэши, временные и локальные служебные артефакты вроде `.DS_Store` остаются вне коммитов. Executor коммитит полный состав одним коммитом; чтобы получить несколько логически цельных коммитов, добавь в запрос `split`, «раздели» или «отдельными коммитами». Например, запрос `eda-commit сразу отправь ветку, создай PR и дай ссылку` использует тот же полный состав и выполняет всю указанную цепочку без отдельного вопроса после серии коммитов.

## 🎯 Главные принципы

- **Простой язык.** Скилы общаются с тобой так, чтобы понял человек без глубоких знаний предмета. Термины — только когда без них нельзя.
- **Вопросы — раундами с рекомендацией.** Скилы, которые согласуют решения (`eda-plan`, `eda-explore`, `eda-business`, `eda-new-project`, `eda-prepare-ai`), сначала сами выясняют факты, а затем задают раундом все вопросы, которые уже можно задать; вопрос, зависящий от ещё не данного ответа, ждёт следующего раунда. У каждого вопроса — зачем он, 2–4 варианта и рекомендованный вариант первым с причиной.
- **Вопросы — инструментом среды или текстом.** Скилы задают вопрос через `AskUserQuestion`, а платформенный адаптер подставляет способ среды: в Claude Code это сам `AskUserQuestion`, в OpenCode — `question`, в Codex — только текст в чат: `request_user_input` запрещён, потому что Codex сам сворачивает его окно. В неинтерактивных запусках (`codex exec`, `claude -p`) скил не имитирует диалог: если без ответа нельзя безопасно продолжать, он завершает работу со статусом `blocked: нужен ответ пользователя`.
- **Без инструмента вопросов — нумерованный список.** Если интерактивного инструмента нет или он запрещён, как в Codex, скил задаёт до 8 вопросов одним сообщением; вопросы и варианты пронумерованы, рекомендованный вариант первый, остальные вопросы приходят после ответа. Отвечать можно парами «вопрос - вариант»: `1-1 2-3`, а вместо номера варианта — написать свой; «ок» или «согласен» принимает все рекомендации. Тем же списком скил перечисляет вопросы в `blocked`.
- **Способ review настраивается.** В `subagents` `eda-review` запускает установленных read-only агентов нативным механизмом Claude/Codex и блокируется при их недоступности без CLI-fallback. В `main` основной агент выполняет те же выбранные проверки по тем же чек-листам без субагентов и повторной загрузки общего контекста.
- **Технические остановки обрабатываются по причине.** Оркестраторы ждут свободный слот при лимите параллельности, запрашивают недостающее разрешение, один раз продолжают агента после временной API-ошибки и без бессмысленных retry останавливаются при лимите глубины, исчерпанной квоте или неизвестном сбое.
- **Повторяемые роли — в пакетных агентах.** Скилы управляют процессом, а стабильные изолированные роли получают собственный prompt, модель и доступ. Полные review-prompts не дублируются в оркестраторе.
- **Артефакты только из текущего проекта.** План, ревью, research или файл цели из другого проекта скил не читает: проверяет путь до чтения и останавливается со статусом `blocked: артефакт из другого проекта`. Своими считаются корень git-репозитория и его worktree. Если чужой артефакт нужен намеренно, перенеси его в `docs/artifacts/` текущего проекта.
- **Артефакты по папкам.** Исследования отдельно, планы отдельно, ревью отдельно. Между файлами — ссылки. Через месяц легко найти, кто что когда решал.
- **Границы между скилами жёсткие.** `plan-execute` только управляет субагентами и не коммитит — это работа `commit`. `review` не правит код — это `fix-by-review`. Никаких размытых ответственностей.
- **Доверие модели.** Скилы короткие. Они говорят «что» и «почему», а «как именно» — модель разбирается сама.

## 💻 Команды

```bash
eda init      # выбрать Claude Code / Codex / OpenCode и установить пакет
eda update    # предложить добавить платформы, обновить настройки, скилы и агентов
eda update-all [dir] # сохранить конфиги или настроить общий и обновить проекты на глубине 2
eda --version # показать версию установленного пакета
eda --help    # справка
```

Когда выходит новая версия пакета:

```bash
npm update -g @gian-tiaga/eda    # подтянуть новый код
eda update           # синхронизировать пакет в текущем проекте
```

Для папки с несколькими проектами:

```bash
npm update -g @gian-tiaga/eda
eda update-all ~/Code
```

## 📁 Структура и установка компонентов

Исходники скилов лежат в `skills/<skill>/SKILL.md`. Дополнительные ресурсы скила можно хранить рядом; `skill.json` содержит только платформенные настройки и в проект пользователя не копируется. Поля `claude.context: fork` и `claude.agent` renderer добавляет только во front matter Claude-копии скила. `models.codex` можно хранить как зарезервированную настройку для будущего per-skill override, но текущий Codex renderer её не добавляет в `SKILL.md`.

Исходники агентов лежат в `agents/<agent>/agent.json` и `prompt.md`. Установщик рендерит единый агентный контракт в нативный формат выбранной среды.

| Компонент | Claude Code | Codex CLI | OpenCode V2 |
|---|---|---|---|
| Скил | `.claude/skills/<skill>/SKILL.md` | `.agents/skills/<skill>/SKILL.md` | `.opencode/skills/<skill>/SKILL.md` |
| Агент | `.claude/agents/<agent>.md` | `.codex/agents/<agent>.toml` | `.opencode/agents/<agent>.md` |
| Manifest владения | `.claude/eda-manifest.json` | `.codex/eda-manifest.json` | `.opencode/eda-manifest.json` |

`eda update` переносит известные старые каталоги артефактов, сохраняет актуальный полный v3-конфиг как есть, устаревший по шаблону перерисовывает с сохранением значений, а старый или неполный умно переносит и целиком нормализует; затем идемпотентно синхронизирует обе группы компонентов и отдельно показывает реально изменившиеся скилы и агенты. Manifest хранит только идентификаторы компонентов, которыми владеет `eda`: retired-компоненты удаляются, а чужие скилы и агенты остаются нетронутыми. `eda update-all [dir]` выполняет тот же перенос артефактов в каждом проекте, затем либо записывает общий профиль, либо в `skip` сохраняет актуальный полный v3, перерисовывает устаревший по шаблону и переносит остальные настройки. При миграции Codex установщик переносит актуальные скилы в `.agents/skills/` и удаляет принадлежащие `eda` старые копии `.codex/skills/<skill>/` и `.codex/skills/<skill>.md`, не затрагивая чужие компоненты.

Установленные копии не являются источником правды. Локальные изменения внутри `.claude/skills/eda-*`, `.agents/skills/eda-*`, `.opencode/skills/eda-*`, `.claude/agents/eda-*`, `.codex/agents/eda-*` или `.opencode/agents/eda-*` будут заменены следующим обновлением.

`AGENTS.md` (как и любые другие файлы в корне проекта) установщик **не трогает**. Codex автоматически обнаруживает проектные скилы в `.agents/skills/`.

## 🤝 Для кого это

- Для тех, кто **постоянно** пишет код с AI-агентом и устал каждый раз заново объяснять, как делать ревью.
- Для команд, где хочется единый стандарт работы с агентами — чтобы ревью у всех было пронумеровано и оценено, планы лежали в одной папке, а коммиты были по одному стилю.
- Для разработчиков, которые любят **строгость**: максимально жёсткие правила, обязательные тесты и отдельные контекстные проверки ревью на подходящих моделях.

# AGENTS.md

> Карта проекта для AI-агентов. Держать в актуальном состоянии при изменении структуры, команд, правил установки или набора скилов.

## Обзор проекта

`eda` — npm-пакет `@gian-tiaga/eda` с CLI для установки и обновления русскоязычных AI-скилов и специализированных агентов `eda-*` в проектах пользователя.

Пакет поддерживает три среды:

- Claude Code: установка в `.claude/skills/<skill>/SKILL.md`
- Codex CLI: установка в `.agents/skills/<skill>/SKILL.md`
- OpenCode V2: установка в `.opencode/skills/<skill>/SKILL.md`

Агенты устанавливаются в `.claude/agents/<agent>.md`, `.codex/agents/<agent>.toml` и `.opencode/agents/<agent>.md`. Главная идея проекта: хранить канонические скилы в `skills/<skill>/`, канонические определения агентов в `agents/<agent>/`, а CLI рендерит и синхронизирует платформенные форматы. Корневой `AGENTS.md` в проектах пользователей установщик не трогает.

## Стек

- Runtime: Node.js `>=18`
- Module system: ESM (`"type": "module"`)
- CLI entry: `bin/cli.js`
- Installer logic: `lib/install.js`
- Tests: Node.js built-in test runner (`node --test`)
- Interactive prompts: `@clack/prompts` через адаптер `lib/prompts.js`
- Package manager: npm

## Команды

```bash
npm test
node bin/cli.js --help
node bin/cli.js --version
node bin/cli.js init
node bin/cli.js update
node bin/cli.js update-all [dir]
```

`init`, `update` и `update-all` интерактивны при TTY. `update` и `update-all` переносят известные рабочие каталоги из `docs/<тип>/` в `docs/artifacts/<тип>/`, не меняя содержимое файлов; при конфликте новый путь имеет приоритет. Полный `docs/settings.yaml` версии 3 сохраняется, пока его текст совпадает с актуальным шаблоном; если шаблон изменился, файл без вопросов перерисовывается с сохранением значений. Старый, неизвестный или неполный конфиг разбирается через YAML, известные валидные значения переносятся, отсутствующие спрашиваются и файл целиком атомарно переписывается как v3; без TTY используются перенесённые значения и defaults. `update-all configure` записывает общий профиль, а `skip` сохраняет актуальный v3 и индивидуально переносит остальные конфиги. Команда ищет проекты с уже установленным eda-скилом, агентом или manifest на глубине 2.

## Правила для агентов

- Работай на русском языке: проект, README и скилы написаны для русскоязычного пользователя.
- Перед изменением поведения CLI читай `lib/install.js`, `bin/cli.js`, `README.md` и релевантные тесты.
- Перед изменением скила читай соседние `skills/eda-*/SKILL.md`: у них должен оставаться единый стиль, структура и терминология.
- Перед изменением агента читай его `agent.json`, `prompt.md`, вызывающие скилы и все platform renderer.
- Не редактируй установленные копии в `.agents/`, `.claude/`, `.codex/` или `.opencode/` как источник правды. Источник правды — только `skills/` и `agents/` пакета.
- Не добавляй новые runtime-зависимости без необходимости. Для простого поведения предпочитай стандартные модули Node.js.
- Не используй команды с интерактивным вводом в автоматических тестах.
- Не обходи pre-commit/pre-push hooks через `--no-verify`.
- Не коммить секреты, токены, `.env` и локальные артефакты.

## Правила изменения CLI

- `eda init` должен спрашивать целевые среды при интерактивном TTY без заранее отмеченных (Claude Code, OpenCode, Codex CLI; нужна хотя бы одна) и выбирать все три среды без TTY. Промпты построены на `@clack/prompts` через адаптер `lib/prompts.js`. В TTY `askSettings` спрашивает только основные настройки по ходу работы: `eda-plan` (размер, решения, тесты), исполнение `eda-plan-execute`, `eda-review`, `eda-polish`, глубину `eda-manual-test`, режим, необязательные этапы и исполнение `eda-orhestra`. Первым в вопросе идёт вариант по умолчанию, «Спрашивать каждый раз» — последним. Редкие настройки не спрашиваются даже при отсутствии и получают defaults.
- OpenCode V2 использует `.opencode/skills/`, `.opencode/agents/*.md` и `.opencode/eda-manifest.json`; `update-all` не заходит в `.opencode`. Конфиги OpenCode установщик не редактирует. OpenCode renderer добавляет к скилам платформенный адаптер, роли рендерит с `mode: subagent` и V2 `permissions`. Read-only роли не имеют shell/MCP/редакторов/субагентов, diff и CI им передаёт оркестратор; git-write запрещает редакторы, workspace-write наследует permissions пользователя. Модель по умолчанию наследуется от сессии; необязательное `models.opencode` задаёт `provider/model#variant`. Claude/Codex настройки моделей не переносятся автоматически. Для изолированных шагов используется `eda-skill-runner` с возможностью вложенных запусков, не встроенный general. Недоступные обязательные возможности дают `blocked` без смены режима.
- `eda update` в TTY при каждом запуске показывает checkbox всех платформ: найденные уже отмечены и обновляются в любом случае, даже если отметку снять, остальные можно добавить. После подтверждения синхронизирует найденные и добавленные платформы; выбор сохраняется их каталогами и target manifests, отдельного списка в settings нет. Без TTY обновляет только найденные среды. Среда считается найденной по каталогу `skills`, каталогу `agents` или target manifest; если ни одной среды нет, команда просит сначала запустить `eda init`. `update-all` не добавляет платформы. Полный валидный `docs/settings.yaml` версии 3 сохраняется без вопросов и перезаписи, пока его текст совпадает с актуальным шаблоном; при изменившемся шаблоне файл молча перерисовывается, значения пользователя переносятся, посторонние ключи и ручные комментарии не сохраняются. Старый, неизвестный или неполный файл переносится целиком: известные валидные значения сохраняются, в TTY спрашиваются только отсутствующие, без TTY используются defaults.
- `eda update` и `eda update-all` перед настройками переносят каталоги `aims`, `automations`, `executions`, `fixes`, `manual-tests`, `plan-review-fixes`, `plan-reviews`, `plans`, `project-starts`, `researches`, `review-fixes`, `reviews`, `roadmaps` из `docs/` в `docs/artifacts/`. Содержимое файлов не переписывается, новые пути имеют приоритет при конфликте, старые пути после миграции не поддерживаются. `eda init` этот перенос не выполняет.
- `eda update-all [dir]` должен обходить указанную директорию, её прямых детей и внуков. Проект считается найденным при наличии установленного `eda`-скила, агента или target manifest.
- `eda update-all` должен обновлять только найденные среды и перед настройками предложить `configure` или `skip`. `configure` один раз спрашивает полный профиль и атомарно записывает одинаковый `docs/settings.yaml` во все проекты. `skip` не задаёт вопросы, сохраняет полный v3 с актуальным текстом как есть и перерисовывает его при изменившемся шаблоне, индивидуально переносит старые, неизвестные и неполные файлы с defaults для отсутствующих значений и создаёт полный профиль defaults только при отсутствии файла. Без TTY используется `skip`. Команда не должна заходить в `.git`, `.agents`, `.claude`, `.codex`, `.opencode`, `node_modules` и следовать symlink-директориям.
- Ошибка обновления одного проекта в `eda update-all` не должна останавливать остальные проекты; в конце нужна сводка по успехам, пропускам и ошибкам.
- При `eda init` полный v3 с актуальным текстом сохраняется, а устаревший по шаблону, старый, неизвестный или неполный файл умно переносится и целиком атомарно переписывается. `eda update-all configure` атомарно записывает общий профиль; `skip` сохраняет актуальный полный v3, индивидуально переносит остальные версии и создаёт defaults при отсутствии файла.
- Актуальный формат `docs/settings.yaml` — только `version: 3`: разделы по ходу работы — `explore`, `plan`, `plan-review`, `plan-polish`, `plan-execute`, `review`, `polish`, `manual-test`, `send-review`, `discover-automations`, `orhestra`, `aim`. `orhestra.execution` принимает `subagents`, `main` или `main_propagated` с default `subagents`; `plan.test_strategy` управляет тестами и автоматическими проверками и принимает `phase_tests_final_checks` (default), `tdd_each_phase`, `after_each_phase`, `end_of_plan` или `ask_each_time`, `plan.logging_strategy` — default `standard`; новые допустимые значения и подсказки доезжают в уже созданные конфиги через перерисовку при `eda update`; `plan-review.threshold` задаёт gate; `plan-polish.limit` ограничивает итерации «проверка + исправление» с default `5`; `plan-execute.mode` принимает `main`, `auto` или `subagents` с default `main`; `polish.execution` принимает `subagents` или `main` с default `subagents` и задаёт режим цикла `eda-polish` независимо от `review.execution`; `manual-test.depth` принимает `full`, `smoke` или `ask_each_time` с default `full`; `review.execution` принимает `main` или `subagents` с default `main`; `send-review.close_previous_reviews` — default `true`; `review.agents.<role>` — одна строка на роль для всех сред: `default` (модель и reasoning установленного агента) или `provider/model#variant`, где variant задаёт effort; режимов запуска у проверок нет, установщик пишет `default` и не спрашивает модели, конфиг формата до 4.0 при обновлении получает `default` во всех ролях и переписывается, а в конфиге 4.0 сохраняет значения и заменяет на `default` только значения не в формате `default` или `provider/model#variant`. Среда, которая не может запустить указанную модель, выполняет роль на модели агента с warning в покрытии ревью. `plan.review`, `plan.meta_review` и `plan-polish.strict` удаляются как устаревшие: полировку плана `eda-plan` больше не запускает.
- Для Codex формат установки — директория с `SKILL.md`: `.agents/skills/<skill>/SKILL.md`.
- `models.codex` в `skill.json` разрешено хранить как зарезервированную настройку будущего per-skill override; пока Codex её не поддерживает, renderer не добавляет модель в `SKILL.md`.
- Для агентов форматы установки — `.claude/agents/<agent>.md`, `.codex/agents/<agent>.toml` и `.opencode/agents/<agent>.md`.
- `.claude/eda-manifest.json`, `.codex/eda-manifest.json` и `.opencode/eda-manifest.json` хранят только компоненты, которыми владеет `eda`; удалять чужие skills/agents нельзя.
- Старые Codex-копии `.codex/skills/<skill>/` и `.codex/skills/<skill>.md` удаляются при обновлении соответствующего скила; чужие компоненты в `.codex/skills/` сохраняются.
- Retired-скилы и агенты удаляются из всех установленных целевых сред.
- `AGENTS.md` в проектах пользователей установщик не создаёт и не перезаписывает.

## Правила изменения скилов

- Каждый скил должен быть самостоятельной инструкцией и иметь front matter:

```markdown
---
name: eda-...
description: '...'
---
```

- `description` в front matter каждого скила должен быть одним коротким предложением не длиннее 200 символов: только назначение и контекст вызова, без моделей, внутренних шагов, путей сохранения и подробных ограничений.
- Все рабочие артефакты packaged-скилов сохраняются в тематических каталогах внутри `docs/artifacts/`. В корне `docs/` остаются `settings.yaml`, `rules.md`, `arch.md`, `business.md`, `business/`, `references.md` и `references/`.
- В каждом packaged `eda-*` скиле должна быть ровно одна секция `## Вход из сообщения пользователя`.
- Если скил зависит от настроек, явно документируй чтение `docs/settings.yaml` и значения по умолчанию.
- Режим исполнения из вызова, применимого override оркестратора или настроек обязателен: размер задачи и нехватка контекста не разрешают его менять. Эвристики выбора исполнителя применяются только в `auto` до начала выполнения; после выбора режим сохраняется до нового прямого указания пользователя, в том числе после сжатия контекста. `orhestra.mode: automatic` не разрешает переопределять режим исполнения вложенного скила; границы `main` и `main_propagated` сохраняются.
- Интерактивные вопросы пиши через `AskUserQuestion` без веток по платформам: адаптер OpenCode сопоставляет его с `question`, а адаптер Codex запрещает `request_user_input` в скилах и агентах (Codex сам сворачивает его окно) и задаёт вопросы только текстом с завершением хода до ответа. Неинтерактивный запуск описывай отдельно: не читать stdin и вернуть `blocked` с вопросом. Каждый скил, который задаёт вопросы, подключает `skills/_shared/text-questions.md`: без инструмента вопросов — до 8 нумерованных вопросов в сообщении с нумерованными вариантами и ответом вида `1-1 2-3`, «ок» или «согласен» принимает все рекомендации; тем же форматом вопросы перечисляются в `blocked`. Адаптеры Codex и OpenCode отсылают к этому разделу.
- В `review.execution: subagents` специализированные проверки `eda-review` идут через установленных нативных субагентов и при их недоступности блокируются без CLI-fallback. В `review.execution: main` те же выбранные проверки выполняет основной агент по тем же чек-листам `references/checks/` без субагентов.
- Сохраняй жёсткие границы ответственности:
  - `eda-business` совместно с человеком фиксирует целевое описание проекта, требования и бизнес-логику в `docs/business.md` и карточках `docs/business/`; сложную тему описывает подробно и конкретно, но без шума, сведений соседних тем и привязки к структуре текущего кода; может закреплять значимые алгоритмы и механизмы вроде JWT или серверного хранения токенов, но не язык, библиотеку, конкретную СУБД или схему реализации; `about` содержит только краткое описание проекта и основные возможности; при пустом вызове предлагает непересекающиеся темы по реальному проекту и прорабатывает их по одной, но не пишет код, архитектуру или план реализации и не сохраняет неподтверждённые темы; карточка не больше 20 КБ — большую тему делит на подтемы, изменения вносит на месте без датированных дополнений.
  - `eda-roadmap` создаёт список будущих задач, но не пишет детали реализации.
  - `eda-new-project` собирает требования, функциональность, границы, ограничения и архитектурные драйверы нового проекта, вместе с пользователем выбирает основной стек и фиксирует его актуальные версии; если у стека есть официальный generator/scaffold CLI, передаёт его как обязательный способ последующего разворачивания вместо ручного создания основы; не навязывает формат минимальной или первой версии, не проектирует архитектуру, правила, проверки, AI-скилы или MCP, не пишет код и не ставит зависимости, сам сохраняет только `docs/artifacts/project-starts/`, после чего всегда без дополнительного вопроса запускает полный технический bootstrap через `eda-prepare-ai`.
  - `eda-explore` исследует, но не пишет план реализации; до сохранения закрывает все открытые вопросы — фактом со ссылкой, решением по `decision_mode` или подтверждённой границей, а без возможности спросить пользователя возвращает `blocked`; раздела «Открытые вопросы» в отчёте нет.
  - `eda-plan` планирует, но не меняет код; до подтверждения показывает пользователю полный текст по шаблону скила — в Claude Code через Plan Mode, в Codex в чате, — затем сохраняет подтверждённый текст; в разделе `Рамка` выписывает по строке каждое применимое требование правил, архитектуры, эталонов, бизнес-карточек и `AGENTS.md`; `Целевой алгоритм` пишет сценариями из нумерованных шагов в порядке выполнения, таблица допустима только для матрицы статусов и формул; каждую таблицу БД описывает своей таблицей колонок; каждый ответ пользователя записывает в `Принятые решения` и не добавляет механизмов вне запроса, рамки и решений; пишет конкретный план без повторов и пояснений, которые не меняют действие, контракт, зависимость, проверку или решение; в контрактах отдельно фиксирует данные и БД, API, устройство и дизайн интерфейса и консольные команды, а неприменимые подразделы явно помечает; разрешает формулы и компактный псевдокод, когда они задают бизнес-правило, контракт, инвариант или критерий приёмки, но не внутренние вычисления без контрактного смысла; для отсутствующего, неполного или расширяемого business-правила обязательно добавляет до зависимой реализации отдельную задачу `Дополнить бизнесовые правила`; для затронутой инфраструктуры, публичных индексируемых страниц и частого пути ввода-вывода записывает решения, которые иначе примет исполнитель: переменные окружения и деплой — в эксплуатацию, адреса, редиректы и индексацию — во внешние контракты, допустимое число запросов и внешних вызовов со способом проверки — в тесты и проверки; формирует связные фазы для одного исполнителя с целью, описанием работы, результатом и проверкой, без ID задач и графа зависимостей; полировку плана не запускает — для неё есть `eda-plan-polish` и этап `eda-orhestra`, а `plan.strict` включает кросс-CLI ревью.
  - `eda-plan-review` одним read-only проходом без субагентов проверяет исполнимость плана по фиксированному чек-листу из 22 пунктов, включая полноту `Рамки`, формат алгоритма и таблиц БД, ошибки и восстановление в сценариях, тесты на каждую ветку алгоритма, одинаковые имена и удаляемое поведение; пункты 17 и 22 условные, пункт 17 и требует записанных решений по затронутой инфраструктуре, публичным страницам и числу запросов на частом пути. Качество решений не оценивает, замечания вне списка не принимает, score считает долей закрытых пунктов без `n/a`, сохраняет SHA-256 цепочку и не меняет план. Специализированных plan-review агентов нет: проверки по ролям относятся к `eda-review` кода.
  - `eda-plan-review-fix` применяет все открытые находки минимальным изменением только к плану с совпадающим SHA-256, сохраняет fix-отчёт, но не делает повторное ревью и не меняет код. Пункт, который не закрыть без роста больше 3%, оставляет открытым со `status: partial`, неизменённый план даёт `status: no-change`; это результаты, а не блокеры.
  - `eda-plan-polish` оркестрирует изолированный цикл plan-review / plan-review-fix до подтверждённых 100/100 без открытых находок или лимита; всегда передаёт threshold 100 независимо от настроек и аргумента threshold. `limit` считает итерации «проверка + исправление» с default 5, исправление проверяет review следующей итерации; отсутствие прогресса, снижение score, повторные пункты и fix со статусом `partial` или `no-change` цикл не останавливают, технические блокеры сохраняются; strict и кросс-CLI не поддерживаются.
  - `eda-orhestra` выполняет настраиваемую упорядоченную цепочку установленных `eda-*`-скилов из `orhestra.steps`: шаги можно отключать, переставлять и снабжать общей строкой `args`, включая `threshold` и `limit` для скилов полировки; `manual-test.on_failure` рядом с шагом задаёт fix, повторные шаги и лимит циклов. Дефолтная цепочка: plan без проверок → plan-polish → plan-execute → polish → manual-test; после failed manual-test запускается fix и повторяется только manual-test. `orhestra.execution` задаёт выполнение этапов: `subagents` изолирует каждый вызов, `main` ведёт верхнюю цепочку текущим агентом, `main_propagated` дополнительно передаёт `main` только в `eda-plan-execute`, `eda-polish` и прямой `eda-review`; остальные вложенные контракты не меняются. В `automatic` безопасно отвечает на рабочие вопросы сам, в `manual` передаёт вопросы человеку; git/publish-скиллы не запускает и не коммитит.
  - `eda-aim` оркестрирует отдельных пакетных агентов для согласования, выполнения и независимой проверки одной или нескольких целей; `aim.mode` задаёт `automatic` или `manual` по умолчанию, а режим из текущего вызова имеет приоритет; новый файл `docs/artifacts/aims/` создаётся только после подтверждения списка человеком; при необходимости установленные скилы запускаются только в отдельных изолированных субагентах, основной агент не применяет их и не выполняет содержательную работу; цикл продолжается до подтверждения всех критериев или внешнего блокера.
  - `eda-plan-execute` управляет выполнением готового плана и проходит фазы строго последовательно; режим берётся из вызова, затем из `plan-execute.mode`, иначе `auto`. В `subagents` каждая фаза целиком идёт отдельному изолированному субагенту, вопросы и исправления фазы продолжает тот же исполнитель, отдельные субагенты независимо проверяют каждую фазу и весь план, а основной агент меняет только отметки плана и журнал `docs/artifacts/executions/`. В `main` те же фазы, проверки и запреты выполняет сам основной агент; размер плана и нехватка контекста не разрешают смену режима. Он сохраняет прогресс и режим для продолжения после сжатия контекста, а при технической невозможности продолжить фиксирует блокер. `auto` до первой фазы выбирает `main` только для небольшого плана, помещающегося в один контекст, иначе `subagents`. Тот, кто выполняет фазу, полностью читает план, его `Рамку` и все файлы из `sources`, а при затрагивании компонента с карточкой в `docs/references.md` читает её перед соответствующим изменением; перед сдачей фазы сверяет изменения с каждым пунктом `Рамки` и `Принятых решений`, проверяющий повторяет сверку независимо; поле фазы `Согласование` останавливает работу до ответа пользователя; механизмов вне плана не добавляет, документы рамки правит в разделе-владельце без датированных дополнений; новый проект разворачивает официальным scaffold CLI выбранного стека, если он существует, а не ручным созданием генерируемой основы; скил не коммитит и не делает ревью.
  - `eda-just-do-it` напрямую выполняет задачу из текущего вызова без обязательного планирования или передачи другому скилу, после определения scope загружает только применимые инструкции, business/reference-карточки, код и тесты, проверяет результат и всегда сохраняет отчёт в `docs/artifacts/just-do-it/`; при создании нового проекта использует официальный generator/scaffold CLI выбранного стека, если он существует, вместо ручного воспроизведения основы; git-, внешние и разрушительные действия выполняет только при прямом однозначном указании пользователя.
  - `eda-fix`, `eda-fix-by-review` меняют код и проверяют результат. `eda-fix-by-review` применяет все находки и отклоняет только фактически неверные, всегда с причиной в отчёте.
  - `eda-manual-test` вручную проверяет изменения и сохраняет отчёт; глубина берётся из `manual-test.depth` с дефолтом `full` и переопределяется словом в запросе; в `full` артефакт разбирается по разделам, дополняется фактическим diff, а покрытие закрывается по матрице областей (API, база данных, консольные команды, интерфейс, алгоритмы, фон и интеграции, права и роли, конфигурация, логи, регрессии рядом); область не закрывается чтением кода или автотестами, незакрытая область даёт `blocked`; business-карточки использует только как дополнительный контекст для непосредственно затронутого поведения; не правит код, не пишет автотесты и не коммитит.
  - `eda-prod-check` read-only диагностирует работающее окружение: замер симптома командой до гипотез, 3–5 проверяемых гипотез, проход по чек-листу слоёв снаружи внутрь со статусом каждого слоя (`проблема`, `в порядке`, `не проверено`), отчёт в `docs/artifacts/prod-checks/` с вкладом каждой причины, доказательством и исправлением с ожидаемым эффектом. Ничего не меняет на сервере, нагрузку и тяжёлые профилировщики запускает только после подтверждения, секреты маскирует, исправления передаёт в `eda-fix` или `eda-plan`.
  - `eda-review` поддерживает `subagents` и `main` с default `main`. Фиксированного набора проверок нет: в `subagents` первым запускается `eda-review-triage`, который по содержимому ревью выбирает проверки и применимые карточки references/business, а основной агент сам target для выбора не читает; в `main` выбор делает основной агент по `references/triage.md`. Поверх выбора применяются детерминированные правила и разовые указания пользователя. В первом режиме основной агент оркестрирует отдельные read-only packaged-агенты для correctness, architecture, rules, references, business, plan alignment, code quality, tests, security, performance, frontend, API, database, infra, SEO, documentation и previous reviews; в Codex запускает их с `fork_turns: "none"` и отправляет все выбранные проверки одним нативным параллельным пакетом без ручных партий и shell-опроса. В `main` основной агент один раз читает общий контекст и последовательно выполняет те же выбранные проверки по установленным чек-листам `references/checks/` без субагентов; модели отдельных ролей не применяются. Для PR/MR он получает CI текущего head и не повторяет локально уже завершённые там автоматические команды, но не пропускает смысловые review-проходы. В обоих режимах он принимает только доказанные дефекты, которые уже существуют в текущем коде и названы вместе со способом воспроизведения, отклоняет косметические и спекулятивные предложения и находки про будущее, записывает отклонённые в раздел «Отклонено», объединяет подтверждённые проблемы, выставляет score и пишет `clean` только при отсутствии находок, но не правит код. Business-проверка запускается только для применимых карточек и различает нарушение правила и намеренное изменение правила с устаревшей документацией.
  - `eda-polish` оркестрирует цикл полного `review` / `fix-by-review` до подтверждённых 100/100, `clean` и отсутствия находок или лимита (default 5). Режим берётся из вызова, override оркестратора или `polish.execution`, иначе default `subagents`; `review.execution` его не меняет. В `main` основной агент последовательно выполняет оба контракта сам без субагентов и передаёт `main` вложенному `eda-review`; в `subagents` каждый review и fix идёт отдельному изолированному субагенту с `fork_turns: "none"` в Codex, а раскладку проверок внутри ревью определяет `review.execution`. Настраиваемого порога у цикла нет; отсутствие прогресса, повторные находки, снижение score и fix, который отклонил все находки или ничего не изменил, цикл не останавливают; останавливают только технические блокеры субагентов, сбой обязательной проверки ревью, невалидный review, недоступный ответ пользователя и блокер fix вне его области; скил не коммитит.
  - `eda-send-review` на `sonnet` / `gpt-5.6-terra` отправляет готовое ревью только в открытый PR, но не делает новое; закрытый или смерженный PR не переиспользует и предлагает создать новый либо указать другой открытый PR; по умолчанию использует статус `comment`, а при `send-review.close_previous_reviews: true` скрывает предыдущие созданные им сводки и резолвит связанные inline-треды. Claude override применяется renderer, Codex-модель пока хранится как зарезервированная рекомендация.
  - `eda-commit` на `sonnet` / `gpt-5.6-terra` оркестрирует одного пакетного агента, который сам собирает git-контекст, при явном scope охватывает соответствующий состав, а без контекста включает все tracked-изменения и все untracked-файлы независимо от авторства и связи с задачей, кроме очевидных кэшей и локальных служебных артефактов вроде `.DS_Store`; агент работает дёшево: собирает контекст одним вызовом, вместо полного diff берёт `--stat` и точечно дочитывает неясные файлы, смысл работы берёт из свежих артефактов `docs/artifacts/**` в составе изменений, а форму сообщений ищет точечным поиском в `AGENTS.md`, `CLAUDE.md` и `docs/rules.md` и при отсутствии правил повторяет форму последних коммитов; весь состав он коммитит одним коммитом и делит на несколько логически цельных коммитов только по явной просьбе (`split`) или при явно раздельном scope, пишет сообщения и тексты PR по исходному запросу и фактическим изменениям, точечно коммитит группы по порядку и выполняет явно заданные push/PR/merge-действия; открытый PR не дублирует, а закрытый или смерженный PR не переиспользует и при запросе создаёт новый; после выполненного push всегда возвращает ссылку на существующий PR или на его создание и спрашивает про создание PR, если его нет; при вероятном секрете блокируется до индексации затронутой группы; основной агент не дописывает логику и сам не выполняет git/GitHub-команды.
  - `eda-worktree` на `haiku` / `gpt-5.6-luna` оркестрирует пакетного агента, который создаёт отдельный git worktree и ветку, но не правит код; основной агент сам не выполняет git-команды.
  - `eda-merge-worktree` на `haiku` / `gpt-5.6-luna` оркестрирует пакетного агента, который мержит ветку из worktree в текущую, но не удаляет worktree и ветку; основной агент сам не выполняет git-команды.
  - `eda-discover-automations` проводит полный baseline gap-аудит даже без истории ревью/фиксов, проходит весь каталог тестов, статических, архитектурных, конфигурационных, security, performance, SEO, release, browser MCP и стек-зависимых MCP-проверок, предлагает автоматизации, но не внедряет их.
  - `eda-prepare-ai` проектирует или актуализирует архитектуру, строгие правила и профиль инструментов, полный стек-зависимый каталог проверок и AI/MCP-процесс, затем создаёт и обновляет `docs/rules.md`, `docs/arch.md`, индекс `docs/references.md`, карточки областей в `docs/rules/` и `docs/arch/`, самодостаточные карточки в `docs/references/`, компактный `AGENTS.md` и минимальный `CLAUDE.md`; правила и архитектура — короткие индексы с таблицами карточек, любой файл рамки не больше 20 КБ, без датированных разделов и журналов изменений, а в `docs/rules.md` записано правило ведения рамки; применимые business-карточки принимает как read-only требования и не редактирует их; подтверждённые требования, стек и архитектурные драйверы стартового документа `eda-new-project` принимает как обязательный вход, для нового проекта фиксирует в `docs/rules.md` точную команду официального scaffold CLI выбранного стека, в остальных случаях пишет только действующие подтверждённые команды, не выдаёт неустановленные инструменты за доступные и не выдумывает references до появления устойчивого кода.
- `docs/references.md` в пользовательском проекте содержит только индекс карточек. Карточки в `docs/references/*.md` содержат нормализованные законченные примеры кода и не ссылаются на исходники проекта или внешние материалы.
- `docs/business.md` в пользовательском проекте содержит только таблицу `Описание | Карточка`; в индекс попадают лишь существующие согласованные карточки из `docs/business/*.md`. Карточки подробно фиксируют значимые решения только собственной темы, не обязаны иметь универсальный набор разделов и не ссылаются на структуру текущего кода; последним разделом описывают на уровне поведения только прямые расхождения этой темы с реализацией.
- Потребляющие скилы читают `docs/rules.md` и `docs/arch.md` целиком и по их таблицам выбирают карточки областей задачи; затем определяют затронутое поведение и через `docs/business.md` и `docs/references.md` читают только применимые карточки. Business-карточки не расширяют scope задачи; при конфликте с задачей агент останавливается и спрашивает человека, изменить задачу или пересогласовать правило через `eda-business`.

## Правила изменения агентов

- Каждый агент хранится в `agents/<name>/agent.json` и `prompt.md`; имя директории и `agent.json.name` должны совпадать.
- `agent.json` schema version 1 должен задавать модели Claude/Codex и access `read-only`, `workspace-write` или `git-write`.
- Общую семантику роли храни только в `prompt.md`; не дублируй полный prompt в вызывающем скиле или renderer.
- Текст, который нужен нескольким скилам или агентам, храни в одном файле пакета и подключай в `SKILL.md` или `prompt.md` отдельной строкой `<!-- include: <путь от корня пакета> -->`: `expandIncludes` из `lib/catalog.js` подставляет файл при установке во все платформы. Общие фрагменты скилов лежат в `skills/_shared/` — это не скил, установщик его не копирует. Правило вопросов `skills/_shared/questions.md` подключают `eda-plan`, `eda-explore`, `eda-business`, `eda-new-project` и `eda-prepare-ai`: вопросы задаются раундами — сразу все решения, предпосылки которых закрыты, — у каждого вопроса рекомендованный вариант первым и причина. Правило `skills/_shared/text-questions.md` подключают все скилы, которые упоминают `AskUserQuestion` или имеют раздел `## Вопросы`. Правило `skills/_shared/project-artifacts.md` подключают скилы, которые принимают план, ревью, research или файл цели: `eda-aim`, `eda-fix-by-review`, `eda-manual-test`, `eda-orhestra`, `eda-plan`, `eda-plan-execute`, `eda-plan-polish`, `eda-plan-review`, `eda-plan-review-fix`, `eda-polish`, `eda-review`, `eda-send-review`; путь вне корня git-репозитория и его worktree даёт `blocked: артефакт из другого проекта` до чтения файла. Так устроены review-проверки: чек-лист — `skills/eda-review/references/checks/<проверка>.md`, требования к находке — `defects.md`, выбор проверок — `triage.md`; main-режим `eda-review` читает те же файлы.
- Read-only агент должен рендериться в Claude с `permissionMode: plan` и в Codex с `sandbox_mode = "read-only"`.
- Workspace-write агент получает редакторы файлов и наследует обычные разрешения рабочей директории; в Codex рендерится с `sandbox_mode = "workspace-write"`.
- Git-write агент не получает редакторы файлов, но наследует sandbox/approval пользователя, необходимые для git hooks и записи в `.git`.
- Скил управляет последовательностью, вопросами и передачей результатов; агент выполняет только одну изолированную роль.
- Контракты результатов агентов должны быть структурированными и проверяться тестами вместе с моделями и ограничениями.
- `eda-review-triage` — read-only разведчик на `sonnet` / `gpt-5.6-terra` с reasoning `low`: возвращает `selected`, `skipped`, `reference_files` и `business_files` без находок. Таблица моделей `default` в `skills/eda-review/SKILL.md` должна совпадать с `models` и `reasoning` в `agent.json` ролей.
- Review-агенты именуются `eda-review-<role>`, работают только read-only и возвращают YAML со `status`, `check`, `model`, `находки`, доказательствами и `repro`. Они возвращают только ошибки и существенные неточности, которые обязательно исправить; поля recommendation и деления на required/optional в их контрактах нет. Роль, вход и формат ответа хранятся в `agents/eda-review-*/prompt.md`, а чек-лист проверки — только в `skills/eda-review/references/checks/<проверка>.md`. Чек-лист состоит из разделов `Что проверять` (пункт: что смотреть → что считается дефектом) и `Не находка`. `eda-review-business` получает только применимые `BUSINESS_FILES`, работает на `sonnet` / `gpt-5.6-terra` и не подменяет correctness или documentation review. `eda-review-performance` сравнивает base и head по числу запросов к БД и внешних вызовов на операцию и по весу отдаваемых CSS, JS и шрифтов и считает внесённый рост дефектом, а не оптимизацией; время подтверждает только измерением. `eda-review-code-quality` принимает доказуемые случаи: повтор существующей реализации, расходящийся копипаст, мёртвый и отладочный код, расхождение с прямым образцом модуля. `eda-review-infra` проверяет также сжатие и кеширование статики и production-настройки runtime и фреймворка. `eda-review-infra` и `eda-review-seo` проверяют только затронутое изменением, проектные решения вроде канонического хоста берут из `docs/rules.md`, а `seo` неприменим к неиндексируемым страницам.

## Релизы

- Версия в `package.json` и тег в git должны совпадать: версии `X.Y.Z` соответствует тег `vX.Y.Z`. Поднял версию — в том же изменении поставь тег.
- Версия без тега и тег без версии — расхождение, которое нужно исправить, а не оставлять на потом.

## Проверки перед финалом

Минимальная проверка после изменений:

```bash
npm test
```

Если менялось поведение CLI, дополнительно проверь:

```bash
node bin/cli.js --help
node bin/cli.js --version
```

Если менялись тексты скилов, убедись, что README не расходится с реальным списком скилов, флагов, настроек и директорий установки.

## Документация

При изменении пользовательского поведения обновляй `README.md` в том же изменении:

- команды и их вывод;
- формат установки;
- список скилов;
- настройки `docs/settings.yaml`;
- retired-скилы или миграции старого формата.

Для внутренних инструкций агентам обновляй этот файл.

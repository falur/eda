# AGENTS.md

> Карта проекта для AI-агентов. Держать в актуальном состоянии при изменении структуры, команд, правил установки или набора скилов.

## Обзор проекта

`eda` — npm-пакет `@gian-tiaga/eda` с CLI для установки и обновления русскоязычных AI-скилов и специализированных агентов `eda-*` в проектах пользователя.

Пакет поддерживает две среды:

- Claude Code: установка в `.claude/skills/<skill>/SKILL.md`
- Codex CLI: установка в `.codex/skills/<skill>/SKILL.md`

Агенты устанавливаются в `.claude/agents/<agent>.md` и `.codex/agents/<agent>.toml`. Главная идея проекта: хранить канонические скилы в `skills/<skill>/`, канонические определения агентов в `agents/<agent>/`, а CLI рендерит и синхронизирует платформенные форматы. Корневой `AGENTS.md` в проектах пользователей установщик не трогает.

## Стек

- Runtime: Node.js `>=18`
- Module system: ESM (`"type": "module"`)
- CLI entry: `bin/cli.js`
- Installer logic: `lib/install.js`
- Tests: Node.js built-in test runner (`node --test`)
- Interactive prompts: `@inquirer/checkbox`, `@inquirer/select`
- Package manager: npm

## Команды

```bash
npm test
node bin/cli.js --help
node bin/cli.js --version
node bin/cli.js init
node bin/cli.js update
node bin/cli.js update-all [dir]
```

`init`, `update` и `update-all` интерактивны при TTY. `update` сохраняет полный `docs/settings.yaml` версии 2 без вопросов, а в неполный v2 атомарно дописывает только отсутствующие разделы и спрашивает только их; для отсутствующего файла или другой версии заново собирает полный профиль. `update-all` предлагает общий профиль с перезаписью или `skip`; `skip` сохраняет существующие конфиги и создаёт defaults только при отсутствии файла. Без TTY `update-all` использует `skip`. Команда ищет проекты с уже установленным eda-скилом, агентом или manifest на глубине 2.

## Правила для агентов

- Работай на русском языке: проект, README и скилы написаны для русскоязычного пользователя.
- Перед изменением поведения CLI читай `lib/install.js`, `bin/cli.js`, `README.md` и релевантные тесты.
- Перед изменением скила читай соседние `skills/eda-*/SKILL.md`: у них должен оставаться единый стиль, структура и терминология.
- Перед изменением агента читай его `agent.json`, `prompt.md`, вызывающие скилы и оба platform renderer.
- Не редактируй установленные копии в `.claude/` или `.codex/` как источник правды. Источник правды — только `skills/` и `agents/` пакета.
- Не добавляй новые runtime-зависимости без необходимости. Для простого поведения предпочитай стандартные модули Node.js.
- Не используй команды с интерактивным вводом в автоматических тестах.
- Не обходи pre-commit/pre-push hooks через `--no-verify`.
- Не коммить секреты, токены, `.env` и локальные артефакты.

## Правила изменения CLI

- `eda init` должен спрашивать целевые среды при интерактивном TTY и выбирать обе среды без TTY.
- `eda update` должен обновлять только уже найденные среды. Среда считается найденной по каталогу `skills`, каталогу `agents` или target manifest; если ни одной среды нет, команда просит сначала запустить `eda init`. Полный `docs/settings.yaml` версии 2 команда сохраняет без вопросов и перезаписи. Если в v2 отсутствуют обязательные верхнеуровневые разделы, команда спрашивает только настройки этих разделов и атомарно дописывает только их, сохраняя существующий текст; без TTY для недостающих разделов использует defaults. Для отсутствующего файла или версии, отличной от 2, команда заново собирает полный v2-профиль.
- `eda update-all [dir]` должен обходить указанную директорию, её прямых детей и внуков. Проект считается найденным при наличии установленного `eda`-скила, агента или target manifest.
- `eda update-all` должен обновлять только найденные среды и перед настройками предложить `configure` или `skip`. `configure` один раз спрашивает полный профиль и атомарно записывает одинаковый `docs/settings.yaml` во все проекты. `skip` не задаёт вопросы, сохраняет любой существующий файл байт-в-байт и создаёт полный профиль defaults только там, где `docs/settings.yaml` отсутствует. Без TTY используется `skip`. Команда не должна заходить в `.git`, `.claude`, `.codex`, `node_modules` и следовать symlink-директориям.
- Ошибка обновления одного проекта в `eda update-all` не должна останавливать остальные проекты; в конце нужна сводка по успехам, пропускам и ошибкам.
- При `eda init` `docs/settings.yaml` создаётся только если его ещё нет: существующий v2 или файл неизвестной версии не перезаписывается, существующий v1 атомарно мигрируется в v2. `eda update` атомарно дополняет неполный v2 или заново записывает полный профиль только для отсутствующего файла и другой версии. `eda update-all` атомарно записывает общий профиль в `configure`, а в `skip` пишет defaults только при отсутствии файла.
- Актуальный формат `docs/settings.yaml` — только `version: 2`: настройки сгруппированы по коротким именам скилов `orhestra`, `aim`, `explore`, `plan`, `plan-polish`, `review`, `send-review`, `discover-automations`; `orhestra.steps` задаёт порядок, включение и параметры этапов, `aim.mode` — режим ответов на рабочие вопросы, а `review.agents` — режим и модели каждой специализированной проверки. Старый раздел `automate` поддерживается `eda-discover-automations` только как fallback для существующих v2-файлов.
- Для Codex формат установки — директория с `SKILL.md`: `.codex/skills/<skill>/SKILL.md`.
- `models.codex` в `skill.json` разрешено хранить как зарезервированную настройку будущего per-skill override; пока Codex её не поддерживает, renderer не добавляет модель в `SKILL.md`.
- Для агентов форматы установки — `.claude/agents/<agent>.md` и `.codex/agents/<agent>.toml`.
- `.claude/eda-manifest.json` и `.codex/eda-manifest.json` хранят только компоненты, которыми владеет `eda`; удалять чужие skills/agents нельзя.
- Старый Codex-формат `.codex/skills/<skill>.md` удаляется при обновлении соответствующего скила.
- Retired-скилы и агенты удаляются из всех установленных целевых сред.
- `AGENTS.md` в проектах пользователей установщик не создаёт и не перезаписывает.

## Правила изменения скилов

- Каждый скил должен быть самостоятельной инструкцией и иметь front matter:

```markdown
---
name: eda-...
description: '...'
---
```

- `description` в front matter каждого скила должен быть одним коротким предложением не длиннее 200 символов: только назначение и контекст вызова, без моделей, внутренних шагов, путей сохранения и подробных ограничений.
- В каждом packaged `eda-*` скиле должна быть ровно одна секция `## Вход из сообщения пользователя`.
- Если скил зависит от настроек, явно документируй чтение `docs/settings.yaml` и значения по умолчанию.
- Интерактивные вопросы формулируй через общий паттерн `AskUserQuestion`: Claude Code, Codex interactive и неинтерактивный Codex должны быть описаны отдельно.
- Обычные мета-проверки `eda-plan` в интерактивном Codex должны идти через субагентов (`spawn_agent` или аналог). Специализированные проверки `eda-review` всегда идут через установленных нативных субагентов; если они недоступны, ревью блокируется без CLI-fallback и без выполнения ролей основным агентом.
- Сохраняй жёсткие границы ответственности:
  - `eda-roadmap` создаёт список будущих задач, но не пишет детали реализации.
  - `eda-new-project` собирает требования, функциональность, границы, ограничения и архитектурные драйверы нового проекта, вместе с пользователем выбирает основной стек и фиксирует его актуальные версии; не навязывает формат минимальной или первой версии, не проектирует архитектуру, правила, проверки, AI-скилы или MCP, не пишет код и не ставит зависимости, сам сохраняет только `docs/project-starts/`, после чего всегда без дополнительного вопроса запускает полный технический bootstrap через `eda-prepare-ai`.
  - `eda-explore` исследует, но не пишет план реализации.
  - `eda-plan` планирует, но не меняет код; каждой задаче присваивает ID, указывает прямые зависимости и формирует связные фазы, каждая из которых выполнима одним агентом за один проход.
  - `eda-plan-polish` сразу запускает три изолированных полных ревью готового плана на быстрой, кодовой и флагманской моделях с одним общим промптом; в `strict` дополнительно запускает кросс-CLI ревью плана Claude ↔ Codex; после ответов выставляет оценку 0–100, при оценке ниже порога содержательно правит только файл плана и запускает новую итерацию; код не меняет и проверки проекта не запускает.
  - `eda-orhestra` выполняет настраиваемую упорядоченную цепочку установленных `eda-*`-скилов из `orhestra.steps`: шаги можно отключать, переставлять и снабжать общей строкой `args`, включая `threshold` и `limit` для `eda-polish`; `manual-test.on_failure` рядом с шагом задаёт fix, повторные шаги и лимит циклов. Каждый вызов этапа, включая составные скилы, повторы и fix после manual-test, идёт в отдельном субагенте с чистым контекстом без истории диалога. В `automatic` безопасно отвечает на рабочие вопросы сам, в `manual` пишет план вместе с человеком; содержательную работу вложенных скилов основной агент не выполняет, git/publish-скиллы не запускает и не коммитит.
  - `eda-aim` оркестрирует отдельных пакетных агентов для согласования, выполнения и независимой проверки одной или нескольких целей; `aim.mode` задаёт `automatic` или `manual` по умолчанию, а режим из текущего вызова имеет приоритет; новый файл `docs/aims/` создаётся только после подтверждения списка человеком; при необходимости установленные скилы запускаются только в отдельных изолированных субагентах, основной агент не применяет их и не выполняет содержательную работу; цикл продолжается до подтверждения всех критериев или внешнего блокера.
  - `eda-plan-execute` управляет выполнением готового плана: проходит фазы строго последовательно и каждую фазу целиком передаёт отдельному изолированному субагенту; исполнитель читает весь план, правила и архитектуру, а при затрагивании компонента с карточкой в `docs/references.md` читает её перед соответствующим изменением. Вопросы и исправления фазы продолжает тот же исполнитель, отдельные субагенты независимо проверяют каждую фазу и весь план; основной агент меняет только отметки плана и журнал `docs/executions/`, не коммитит и не делает ревью.
  - `eda-fix`, `eda-fix-by-review` меняют код и проверяют результат.
  - `eda-manual-test` вручную проверяет API/UI после изменений и сохраняет отчёт, но не правит код, не пишет автотесты и не коммитит.
  - `eda-review` оркестрирует отдельные read-only packaged-агенты для correctness, architecture, rules, references, plan alignment, code quality, tests, security, performance, frontend, API, database, documentation и previous reviews; сам объединяет подтверждённые проблемы и пишет итоговое ревью, но не правит код.
  - `eda-polish` оркестрирует цикл полного `review` / `fix-by-review apply-optional`, но не делает эти шаги основным агентом и не коммитит.
  - `eda-send-review` на `sonnet` / `gpt-5.6-terra` отправляет готовое ревью, но не делает новое; по умолчанию использует статус `comment`, а при `send-review.close_previous_reviews: true` скрывает предыдущие созданные им сводки и резолвит связанные inline-треды. Claude override применяется renderer, Codex-модель пока хранится как зарезервированная рекомендация.
  - `eda-commit` на `haiku` / `gpt-5.6-luna` оркестрирует одного пакетного агента, который сам собирает git-контекст, выбирает один логический набор файлов, точечно коммитит и выполняет явно заданные push/PR/merge-действия; при неоднозначном составе или вероятном секрете блокируется до индексации; основной агент не дописывает логику и сам не выполняет git/GitHub-команды.
  - `eda-worktree` на `haiku` / `gpt-5.6-luna` оркестрирует пакетного агента, который создаёт отдельный git worktree и ветку, но не правит код; основной агент сам не выполняет git-команды.
  - `eda-merge-worktree` на `haiku` / `gpt-5.6-luna` оркестрирует пакетного агента, который мержит ветку из worktree в текущую, но не удаляет worktree и ветку; основной агент сам не выполняет git-команды.
  - `eda-discover-automations` проводит полный baseline gap-аудит даже без истории ревью/фиксов, проходит весь каталог тестов, статических, архитектурных, конфигурационных, security, performance, release, browser MCP и стек-зависимых MCP-проверок, предлагает автоматизации, но не внедряет их.
  - `eda-prepare-ai` проектирует или актуализирует архитектуру, строгие правила и профиль инструментов, полный стек-зависимый каталог проверок и AI/MCP-процесс, затем создаёт и обновляет `docs/rules.md`, `docs/arch.md`, индекс `docs/references.md`, самодостаточные карточки в `docs/references/`, компактный `AGENTS.md` и минимальный `CLAUDE.md`; подтверждённые требования, стек и архитектурные драйверы стартового документа `eda-new-project` принимает как обязательный вход, в `docs/rules.md` пишет только действующие подтверждённые команды, не выдаёт неустановленные инструменты за доступные и не выдумывает references до появления устойчивого кода.
- `docs/references.md` в пользовательском проекте содержит только индекс карточек. Карточки в `docs/references/*.md` содержат нормализованные законченные примеры кода и не ссылаются на исходники проекта или внешние материалы.
- `eda-explore`, `eda-plan`, `eda-plan-polish`, `eda-plan-execute`, `eda-fix`, `eda-fix-by-review` и `eda-review` читают через индекс только применимые карточки. Приоритет: подтверждённое решение пользователя, затем `docs/rules.md`, `docs/arch.md` и references.

## Правила изменения агентов

- Каждый агент хранится в `agents/<name>/agent.json` и `prompt.md`; имя директории и `agent.json.name` должны совпадать.
- `agent.json` schema version 1 должен задавать модели Claude/Codex и access `read-only`, `workspace-write` или `git-write`.
- Общую семантику роли храни только в `prompt.md`; не дублируй полный prompt в вызывающем скиле или renderer.
- Read-only агент должен рендериться в Claude с `permissionMode: plan` и в Codex с `sandbox_mode = "read-only"`.
- Workspace-write агент получает редакторы файлов и наследует обычные разрешения рабочей директории; в Codex рендерится с `sandbox_mode = "workspace-write"`.
- Git-write агент не получает редакторы файлов, но наследует sandbox/approval пользователя, необходимые для git hooks и записи в `.git`.
- Скил управляет последовательностью, вопросами и передачей результатов; агент выполняет только одну изолированную роль.
- Контракты результатов агентов должны быть структурированными и проверяться тестами вместе с моделями и ограничениями.
- Review-агенты именуются `eda-review-<role>`, работают только read-only и возвращают YAML со `status`, `check`, `model`, `findings` и доказательствами. Полные role-prompts хранятся только в `agents/`, а `eda-review` содержит лишь правила выбора, запуска и агрегации.

## Проверки перед финалом

Минимальная проверка после изменений:

```bash
npm test
```

Если менялось поведение CLI, дополнительно проверь:

```bash
node bin/cli.js --help
node bin/cli.js --version
```

Если менялись тексты скилов, убедись, что README не расходится с реальным списком скилов, флагов, настроек и директорий установки.

## Документация

При изменении пользовательского поведения обновляй `README.md` в том же изменении:

- команды и их вывод;
- формат установки;
- список скилов;
- настройки `docs/settings.yaml`;
- retired-скилы или миграции старого формата.

Для внутренних инструкций агентам обновляй этот файл.

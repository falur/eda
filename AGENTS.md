# AGENTS.md

> Карта проекта для AI-агентов. Держать в актуальном состоянии при изменении структуры, команд, правил установки или набора скилов.

## Обзор проекта

`eda` — npm-пакет `@gian-tiaga/eda` с CLI для установки и обновления русскоязычных AI-скилов и специализированных агентов `eda-*` в проектах пользователя.

Пакет поддерживает две среды:

- Claude Code: установка в `.claude/skills/<skill>/SKILL.md`
- Codex CLI: установка в `.agents/skills/<skill>/SKILL.md`

Агенты устанавливаются в `.claude/agents/<agent>.md` и `.codex/agents/<agent>.toml`. Главная идея проекта: хранить канонические скилы в `skills/<skill>/`, канонические определения агентов в `agents/<agent>/`, а CLI рендерит и синхронизирует платформенные форматы. Корневой `AGENTS.md` в проектах пользователей установщик не трогает.

## Стек

- Runtime: Node.js `>=18`
- Module system: ESM (`"type": "module"`)
- CLI entry: `bin/cli.js`
- Installer logic: `lib/install.js`
- Tests: Node.js built-in test runner (`node --test`)
- Interactive prompts: `@inquirer/checkbox`, `@inquirer/select`
- Package manager: npm

## Команды

```bash
npm test
node bin/cli.js --help
node bin/cli.js --version
node bin/cli.js init
node bin/cli.js update
node bin/cli.js update-all [dir]
```

`init`, `update` и `update-all` интерактивны при TTY. `update` и `update-all` переносят известные рабочие каталоги из `docs/<тип>/` в `docs/artifacts/<тип>/`, не меняя содержимое файлов; при конфликте новый путь имеет приоритет. Полный `docs/settings.yaml` версии 3 сохраняется байт-в-байт. Старый, неизвестный или неполный конфиг разбирается через YAML, известные валидные значения переносятся, отсутствующие спрашиваются и файл целиком атомарно переписывается как v3; без TTY используются перенесённые значения и defaults. `update-all configure` записывает общий профиль, а `skip` сохраняет только полный v3 и индивидуально переносит остальные конфиги. Команда ищет проекты с уже установленным eda-скилом, агентом или manifest на глубине 2.

## Правила для агентов

- Работай на русском языке: проект, README и скилы написаны для русскоязычного пользователя.
- Перед изменением поведения CLI читай `lib/install.js`, `bin/cli.js`, `README.md` и релевантные тесты.
- Перед изменением скила читай соседние `skills/eda-*/SKILL.md`: у них должен оставаться единый стиль, структура и терминология.
- Перед изменением агента читай его `agent.json`, `prompt.md`, вызывающие скилы и оба platform renderer.
- Не редактируй установленные копии в `.agents/`, `.claude/` или `.codex/` как источник правды. Источник правды — только `skills/` и `agents/` пакета.
- Не добавляй новые runtime-зависимости без необходимости. Для простого поведения предпочитай стандартные модули Node.js.
- Не используй команды с интерактивным вводом в автоматических тестах.
- Не обходи pre-commit/pre-push hooks через `--no-verify`.
- Не коммить секреты, токены, `.env` и локальные артефакты.

## Правила изменения CLI

- `eda init` должен спрашивать целевые среды при интерактивном TTY и выбирать обе среды без TTY.
- `eda update` должен обновлять только уже найденные среды. Среда считается найденной по каталогу `skills`, каталогу `agents` или target manifest; если ни одной среды нет, команда просит сначала запустить `eda init`. Полный валидный `docs/settings.yaml` версии 3 сохраняется без вопросов и перезаписи. Старый, неизвестный или неполный файл переносится целиком: известные валидные значения сохраняются, в TTY спрашиваются только отсутствующие, без TTY используются defaults.
- `eda update` и `eda update-all` перед настройками переносят каталоги `aims`, `automations`, `executions`, `fixes`, `manual-tests`, `plan-review-fixes`, `plan-reviews`, `plans`, `project-starts`, `researches`, `review-fixes`, `reviews`, `roadmaps` из `docs/` в `docs/artifacts/`. Содержимое файлов не переписывается, новые пути имеют приоритет при конфликте, старые пути после миграции не поддерживаются. `eda init` этот перенос не выполняет.
- `eda update-all [dir]` должен обходить указанную директорию, её прямых детей и внуков. Проект считается найденным при наличии установленного `eda`-скила, агента или target manifest.
- `eda update-all` должен обновлять только найденные среды и перед настройками предложить `configure` или `skip`. `configure` один раз спрашивает полный профиль и атомарно записывает одинаковый `docs/settings.yaml` во все проекты. `skip` не задаёт вопросы, сохраняет полный v3 байт-в-байт, индивидуально переносит старые, неизвестные и неполные файлы с defaults для отсутствующих значений и создаёт полный профиль defaults только при отсутствии файла. Без TTY используется `skip`. Команда не должна заходить в `.git`, `.agents`, `.claude`, `.codex`, `node_modules` и следовать symlink-директориям.
- Ошибка обновления одного проекта в `eda update-all` не должна останавливать остальные проекты; в конце нужна сводка по успехам, пропускам и ошибкам.
- При `eda init` полный v3 сохраняется, а старый, неизвестный или неполный файл умно переносится и целиком атомарно переписывается. `eda update-all configure` атомарно записывает общий профиль; `skip` сохраняет полный v3, индивидуально переносит остальные версии и создаёт defaults при отсутствии файла.
- Актуальный формат `docs/settings.yaml` — только `version: 3`: разделы `orhestra`, `aim`, `explore`, `plan`, `plan-review`, `plan-polish`, `review`, `send-review`, `discover-automations`. `plan.review` включает изолированный цикл `eda-plan-polish`; `plan-review.threshold` и `plan-review.agents` задают gate, режимы и модели; `plan-polish.limit` ограничивает подтверждающие review-итерации. Старые `plan.meta_review` и `plan-polish.strict` переносятся соответственно в `plan.review` и удалённое поле без runtime-fallback.
- Для Codex формат установки — директория с `SKILL.md`: `.agents/skills/<skill>/SKILL.md`.
- `models.codex` в `skill.json` разрешено хранить как зарезервированную настройку будущего per-skill override; пока Codex её не поддерживает, renderer не добавляет модель в `SKILL.md`.
- Для агентов форматы установки — `.claude/agents/<agent>.md` и `.codex/agents/<agent>.toml`.
- `.claude/eda-manifest.json` и `.codex/eda-manifest.json` хранят только компоненты, которыми владеет `eda`; удалять чужие skills/agents нельзя.
- Старые Codex-копии `.codex/skills/<skill>/` и `.codex/skills/<skill>.md` удаляются при обновлении соответствующего скила; чужие компоненты в `.codex/skills/` сохраняются.
- Retired-скилы и агенты удаляются из всех установленных целевых сред.
- `AGENTS.md` в проектах пользователей установщик не создаёт и не перезаписывает.

## Правила изменения скилов

- Каждый скил должен быть самостоятельной инструкцией и иметь front matter:

```markdown
---
name: eda-...
description: '...'
---
```

- `description` в front matter каждого скила должен быть одним коротким предложением не длиннее 200 символов: только назначение и контекст вызова, без моделей, внутренних шагов, путей сохранения и подробных ограничений.
- Все рабочие артефакты packaged-скилов сохраняются в тематических каталогах внутри `docs/artifacts/`. В корне `docs/` остаются `settings.yaml`, `rules.md`, `arch.md`, `business.md`, `business/`, `references.md` и `references/`.
- В каждом packaged `eda-*` скиле должна быть ровно одна секция `## Вход из сообщения пользователя`.
- Если скил зависит от настроек, явно документируй чтение `docs/settings.yaml` и значения по умолчанию.
- Интерактивные вопросы формулируй через общий паттерн `AskUserQuestion`: Claude Code, Codex interactive и неинтерактивный Codex должны быть описаны отдельно.
- Обычные мета-проверки `eda-plan` в интерактивном Codex должны идти через субагентов (`spawn_agent` или аналог). Специализированные проверки `eda-review` всегда идут через установленных нативных субагентов; если они недоступны, ревью блокируется без CLI-fallback и без выполнения ролей основным агентом.
- Сохраняй жёсткие границы ответственности:
  - `eda-business` совместно с человеком фиксирует целевое описание проекта, требования и бизнес-логику в `docs/business.md` и карточках `docs/business/`; сложную тему описывает подробно и конкретно, но без шума, сведений соседних тем и привязки к структуре текущего кода; может закреплять значимые алгоритмы и механизмы вроде JWT или серверного хранения токенов, но не язык, библиотеку, конкретную СУБД или схему реализации; `about` содержит только краткое описание проекта и основные возможности; при пустом вызове предлагает непересекающиеся темы по реальному проекту и прорабатывает их по одной, но не пишет код, архитектуру или план реализации и не сохраняет неподтверждённые темы.
  - `eda-roadmap` создаёт список будущих задач, но не пишет детали реализации.
  - `eda-new-project` собирает требования, функциональность, границы, ограничения и архитектурные драйверы нового проекта, вместе с пользователем выбирает основной стек и фиксирует его актуальные версии; не навязывает формат минимальной или первой версии, не проектирует архитектуру, правила, проверки, AI-скилы или MCP, не пишет код и не ставит зависимости, сам сохраняет только `docs/artifacts/project-starts/`, после чего всегда без дополнительного вопроса запускает полный технический bootstrap через `eda-prepare-ai`.
  - `eda-explore` исследует, но не пишет план реализации.
  - `eda-plan` планирует, но не меняет код; пишет конкретный план без повторов и пояснений, которые не меняют действие, контракт, зависимость, проверку или решение; для отсутствующего, неполного или расширяемого business-правила обязательно добавляет до зависимой реализации отдельную задачу `Дополнить бизнесовые правила`; каждой задаче присваивает ID, указывает прямые зависимости и формирует связные фазы для одного исполнителя; `plan.review` запускает один изолированный `eda-plan-polish`, а `plan.strict` независимо управляет кросс-CLI ревью.
  - `eda-plan-review` оркестрирует установленных read-only агентов requirements, rules, architecture, feasibility, execution, verification и применимые API/database/security/frontend/performance/previous; принимает только доказанные ошибки и существенные неточности, которые обязательно исправить, отклоняет косметические расширения текста, валидирует YAML, дедуплицирует находки, сохраняет стабильные ID и SHA-256 цепочку, экспертно выставляет score и не меняет план.
  - `eda-plan-review-fix` применяет все открытые находки минимальным изменением только к плану с совпадающим SHA-256, сохраняет fix-отчёт, но не делает повторное ревью и не меняет код.
  - `eda-plan-polish` оркестрирует изолированный цикл plan-review / plan-review-fix до отсутствия открытых находок и score не ниже threshold; default limit 3, один круг без изменения находок останавливает цикл, strict и кросс-CLI не поддерживаются.
  - `eda-orhestra` выполняет настраиваемую упорядоченную цепочку установленных `eda-*`-скилов из `orhestra.steps`: шаги можно отключать, переставлять и снабжать общей строкой `args`, включая `threshold` и `limit` для скилов полировки; `manual-test.on_failure` рядом с шагом задаёт fix, повторные шаги и лимит циклов. Дефолтная цепочка: plan без проверок → plan-polish → plan-execute → polish → manual-test; после failed manual-test запускается fix и повторяется только manual-test. Каждый вызов этапа, включая составные скилы, повторы и fix после manual-test, идёт в отдельном субагенте с чистым контекстом без истории диалога. В `automatic` безопасно отвечает на рабочие вопросы сам, в `manual` пишет план вместе с человеком; содержательную работу вложенных скилов основной агент не выполняет, git/publish-скиллы не запускает и не коммитит.
  - `eda-aim` оркестрирует отдельных пакетных агентов для согласования, выполнения и независимой проверки одной или нескольких целей; `aim.mode` задаёт `automatic` или `manual` по умолчанию, а режим из текущего вызова имеет приоритет; новый файл `docs/artifacts/aims/` создаётся только после подтверждения списка человеком; при необходимости установленные скилы запускаются только в отдельных изолированных субагентах, основной агент не применяет их и не выполняет содержательную работу; цикл продолжается до подтверждения всех критериев или внешнего блокера.
  - `eda-plan-execute` управляет выполнением готового плана: проходит фазы строго последовательно и каждую фазу целиком передаёт отдельному изолированному субагенту; исполнитель читает весь план, правила и архитектуру, а при затрагивании компонента с карточкой в `docs/references.md` читает её перед соответствующим изменением. Вопросы и исправления фазы продолжает тот же исполнитель, отдельные субагенты независимо проверяют каждую фазу и весь план; основной агент меняет только отметки плана и журнал `docs/artifacts/executions/`, не коммитит и не делает ревью.
  - `eda-fix`, `eda-fix-by-review` меняют код и проверяют результат. `eda-fix-by-review` применяет все находки и отклоняет только фактически неверные, всегда с причиной в отчёте.
  - `eda-manual-test` вручную проверяет API/UI после изменений и сохраняет отчёт; основной чеклист строит по выполненной задаче и фактическим изменениям, а business-карточки использует только как дополнительный контекст для непосредственно затронутого поведения; не правит код, не пишет автотесты и не коммитит.
  - `eda-review` оркестрирует отдельные read-only packaged-агенты для correctness, architecture, rules, references, business, plan alignment, code quality, tests, security, performance, frontend, API, database, documentation и previous reviews; в Claude рендерится с `context: fork`, в Codex запускает leaf-агентов с `fork_turns: "none"`, запускает все выбранные проверки одним нативным параллельным пакетом без ручных партий и shell-опроса; принимает только доказанные дефекты, которые уже существуют в текущем коде и названы вместе со способом воспроизведения, отклоняет косметические и спекулятивные предложения и находки про будущее, записывает отклонённые в раздел «Отклонено», сам объединяет подтверждённые проблемы, выставляет score и пишет `clean` только при отсутствии находок, но не правит код. Business-проверка запускается только для применимых карточек и различает нарушение правила и намеренное изменение правила с устаревшей документацией.
  - `eda-polish` оркестрирует цикл полного `review` / `fix-by-review` до `clean` и отсутствия находок, но не делает эти шаги основным агентом и не коммитит. В Claude вызывает `eda-review` именно через `Skill` с отрендеренным `context: fork`, не поглощает review-оркестрацию и не запускает leaf review-агентов напрямую; в Codex запускает каждый review и fix с `fork_turns: "none"`. Порога у цикла нет; цикл останавливается, если число открытых находок не сократилось за круг.
  - `eda-send-review` на `sonnet` / `gpt-5.6-terra` отправляет готовое ревью, но не делает новое; по умолчанию использует статус `comment`, а при `send-review.close_previous_reviews: true` скрывает предыдущие созданные им сводки и резолвит связанные inline-треды. Claude override применяется renderer, Codex-модель пока хранится как зарезервированная рекомендация.
  - `eda-commit` на `haiku` / `gpt-5.6-luna` оркестрирует одного пакетного агента, который сам собирает git-контекст, при явном scope охватывает соответствующий состав, а без контекста включает все tracked-изменения и содержательные untracked-файлы кроме очевидных кэшей и локальных служебных артефактов; сам делит выбранный состав на необходимое число логически цельных коммитов, точечно коммитит их по порядку и выполняет явно заданные push/PR/merge-действия; после выполненного push всегда возвращает ссылку на существующий PR или на его создание и спрашивает про создание PR, если его нет; при вероятном секрете блокируется до индексации затронутой группы; основной агент не дописывает логику и сам не выполняет git/GitHub-команды.
  - `eda-worktree` на `haiku` / `gpt-5.6-luna` оркестрирует пакетного агента, который создаёт отдельный git worktree и ветку, но не правит код; основной агент сам не выполняет git-команды.
  - `eda-merge-worktree` на `haiku` / `gpt-5.6-luna` оркестрирует пакетного агента, который мержит ветку из worktree в текущую, но не удаляет worktree и ветку; основной агент сам не выполняет git-команды.
  - `eda-discover-automations` проводит полный baseline gap-аудит даже без истории ревью/фиксов, проходит весь каталог тестов, статических, архитектурных, конфигурационных, security, performance, release, browser MCP и стек-зависимых MCP-проверок, предлагает автоматизации, но не внедряет их.
  - `eda-prepare-ai` проектирует или актуализирует архитектуру, строгие правила и профиль инструментов, полный стек-зависимый каталог проверок и AI/MCP-процесс, затем создаёт и обновляет `docs/rules.md`, `docs/arch.md`, индекс `docs/references.md`, самодостаточные карточки в `docs/references/`, компактный `AGENTS.md` и минимальный `CLAUDE.md`; применимые business-карточки принимает как read-only требования и не редактирует их; подтверждённые требования, стек и архитектурные драйверы стартового документа `eda-new-project` принимает как обязательный вход, в `docs/rules.md` пишет только действующие подтверждённые команды, не выдаёт неустановленные инструменты за доступные и не выдумывает references до появления устойчивого кода.
- `docs/references.md` в пользовательском проекте содержит только индекс карточек. Карточки в `docs/references/*.md` содержат нормализованные законченные примеры кода и не ссылаются на исходники проекта или внешние материалы.
- `docs/business.md` в пользовательском проекте содержит только таблицу `Описание | Карточка`; в индекс попадают лишь существующие согласованные карточки из `docs/business/*.md`. Карточки подробно фиксируют значимые решения только собственной темы, не обязаны иметь универсальный набор разделов и не ссылаются на структуру текущего кода; последним разделом описывают на уровне поведения только прямые расхождения этой темы с реализацией.
- Потребляющие скилы сначала определяют текущую задачу и затронутое поведение, затем через `docs/business.md` и `docs/references.md` читают только применимые карточки. Business-карточки не расширяют scope задачи; при конфликте с задачей агент останавливается и спрашивает человека, изменить задачу или пересогласовать правило через `eda-business`.

## Правила изменения агентов

- Каждый агент хранится в `agents/<name>/agent.json` и `prompt.md`; имя директории и `agent.json.name` должны совпадать.
- `agent.json` schema version 1 должен задавать модели Claude/Codex и access `read-only`, `workspace-write` или `git-write`.
- Общую семантику роли храни только в `prompt.md`; не дублируй полный prompt в вызывающем скиле или renderer.
- Read-only агент должен рендериться в Claude с `permissionMode: plan` и в Codex с `sandbox_mode = "read-only"`.
- Workspace-write агент получает редакторы файлов и наследует обычные разрешения рабочей директории; в Codex рендерится с `sandbox_mode = "workspace-write"`.
- Git-write агент не получает редакторы файлов, но наследует sandbox/approval пользователя, необходимые для git hooks и записи в `.git`.
- Скил управляет последовательностью, вопросами и передачей результатов; агент выполняет только одну изолированную роль.
- Контракты результатов агентов должны быть структурированными и проверяться тестами вместе с моделями и ограничениями.
- Review-агенты именуются `eda-review-<role>`, работают только read-only и возвращают YAML со `status`, `check`, `model`, `находки`, доказательствами и `repro`. Обычные и plan-review агенты возвращают только ошибки и существенные неточности, которые обязательно исправить; поля recommendation и деления на required/optional в их контрактах нет. Полные role-prompts хранятся только в `agents/`, а вызывающий скил содержит лишь правила выбора, запуска и агрегации. `eda-review-business` получает только применимые `BUSINESS_FILES`, работает на `sonnet` / `gpt-5.6-terra` и не подменяет correctness или documentation review.

## Релизы

- Версия в `package.json` и тег в git должны совпадать: версии `X.Y.Z` соответствует тег `vX.Y.Z`. Поднял версию — в том же изменении поставь тег.
- Версия без тега и тег без версии — расхождение, которое нужно исправить, а не оставлять на потом.

## Проверки перед финалом

Минимальная проверка после изменений:

```bash
npm test
```

Если менялось поведение CLI, дополнительно проверь:

```bash
node bin/cli.js --help
node bin/cli.js --version
```

Если менялись тексты скилов, убедись, что README не расходится с реальным списком скилов, флагов, настроек и директорий установки.

## Документация

При изменении пользовательского поведения обновляй `README.md` в том же изменении:

- команды и их вывод;
- формат установки;
- список скилов;
- настройки `docs/settings.yaml`;
- retired-скилы или миграции старого формата.

Для внутренних инструкций агентам обновляй этот файл.

# Скил: Достижение цели (eda-aim)

Оркестрируй полный цикл: согласовать цель → выполнить работу → независимо проверить результат → при необходимости продолжить. Не выполняй содержательную работу основным агентом.

## Настройки

Прочитай только раздел `aim` из `docs/settings.yaml`, если файл есть. Применяй только `version: 3`.

```yaml
aim:
  mode: automatic
```

`aim.mode` принимает только `automatic` или `manual`; при отсутствующем или невалидном значении используй `automatic`. Прямое указание режима в текущем сообщении всегда важнее настройки. Файл настроек не изменяй.

## Вход из сообщения пользователя

Сохрани весь текст текущего сообщения в `$USER_REQUEST`. Извлеки описание результата, ограничения, указанный файл цели и режим:

- `automatic`, `auto`, `автоматически`, `автоматический`, `автономно`, `без вопросов` → `$MODE=automatic`;
- `manual`, `вручную`, `ручной`, `спрашивай` → `$MODE=manual`;
- без явного режима → `$MODE=aim.mode` из валидных настроек, иначе `$MODE=automatic`.

В автоматическом режиме основной агент сам выбирает ответ на рабочие вопросы по рекомендации субагента и фактам проекта. Это не отменяет одно обязательное подтверждение человеком точного списка целей до создания нового файла.

Если пользователь передал существующий файл из `docs/artifacts/aims/`, продолжай его с текущего статуса. Не создавай второй файл для той же цели.

## Пакетные агенты

| Этап | Агент | Claude Code | Codex | Доступ |
|---|---|---|---|---|
| Согласование | `eda-aim-planner` | `opus` | `gpt-5.6-sol` | workspace-write |
| Выполнение | `eda-aim-executor` | `opus` | `gpt-5.6-sol` | workspace-write |
| Проверка | `eda-aim-verifier` | `opus` | `gpt-5.6-sol` | workspace-write |

- В Claude Code запускай установленного пакетного агента через инструмент `Agent` по имени.
- В Codex запускай установленного пакетного агента через `spawn_agent` или аналог по имени.
- Не копируй системный промпт агента в сообщение с заданием.
- Если нужный агент или нативные субагенты недоступны, остановись: `blocked: нужен установленный агент <имя>`. Не выполняй его роль основным агентом и не заменяй отдельным CLI-процессом.

## Технические остановки субагентов

Техническую ошибку инструмента субагентов не смешивай со статусами `failed` и `blocked` содержательного контракта. Сохрани полный исходный текст ошибки и обработай её по причине:

- лимит параллельности или отсутствие свободного слота — дождись уже запущенного этим workflow агента, при необходимости закрой завершённые потоки и повтори тот же запуск; если управляемых активных агентов нет, заверши `blocked: заняты слоты субагентов`;
- лимит глубины вложения — не повторяй запуск и не выполняй этап сам; заверши `blocked: достигнут лимит глубины субагентов`, указав наблюдаемую и требуемую глубину;
- исчерпана usage-квота — не делай автоматических повторов; заверши `blocked: исчерпана квота`, сохрани время reset или условие продолжения, если хост его сообщил;
- не хватает разрешения — запроси одно конкретное разрешение по правилам текущей среды и после ответа продолжи того же агента; в неинтерактивной среде заверши `blocked: нужно разрешение пользователя`;
- временная API-, server-, overload- или network-ошибка — один раз продолжи того же агента; если resume недоступен, один раз запусти ту же роль с исходным входом, полным частичным результатом и требованием сначала сверить текущее состояние; повторный такой сбой заверши как `blocked` с исходной ошибкой;
- неизвестная техническая ошибка — не угадывай причину и не зацикливай retry; заверши `blocked: техническая ошибка субагента` с полным исходным текстом.

Ожидание слота и один технический retry не расходуют лимиты содержательных итераций или циклов достижения цели.

## Вопросы и автоматический режим

Агент может вернуть один конкретный `question`, 1–3 взаимоисключающих `options` и `recommended_answer`.

В ручном режиме передай вопрос пользователю:

- Claude Code: используй `AskUserQuestion`;
- Интерактивный Codex: используй `request_user_input`, если доступен; иначе задай короткий вопрос с вариантами и остановись до ответа;
- Неинтерактивный Codex: не читай stdin; заверши `blocked: нужен ответ пользователя` и перечисли вопрос с вариантами.

В автоматическом режиме не спрашивай пользователя: выбери `recommended_answer`, если он не противоречит исходному запросу, правилам или безопасности; иначе выбери лучший безопасный вариант по фактам проекта. Запиши автоматический ответ в данные продолжения и передай тому же агенту. Не принимай автоматически необратимые внешние действия, расширение цели, публикацию, расходы, удаление данных или ослабление проверок — для них нужен человек.

Подтверждение точного списка новых целей — отдельный обязательный вопрос человеку в обоих режимах. До ответа файл цели не существует.

## Файл цели

После подтверждения `eda-aim-planner` создаёт `docs/artifacts/aims/{YYYY-MM-DD}_{HH-MM}_{slug}.md`. Файл должен оставаться коротким и содержать только цель и фактический журнал:

```markdown
# <Короткое название>

Режим: <ручной | автоматический>
Статус: <согласована | выполняется | проверяется | достигнута | заблокирована>

## Цели

- [ ] A1 — <ясный наблюдаемый результат>; проверка: <критерий>.
- [ ] A2 — <результат>; проверка: <критерий>.

## Журнал

- `<YYYY-MM-DD HH:MM>` — цели согласованы пользователем.
```

Правила файла:

- один пункт допустим и предпочтителен, если задача едина;
- не превращай цели в план реализации, бэклог, исследование или длинную спецификацию;
- каждый пункт описывает результат, а не действие агента;
- новые разделы не добавляй;
- журнал только дополняй, старые записи не переписывай;
- используй относительные Markdown-ссылки на изменённые файлы и созданные артефакты;
- отметку `[x]` ставит только `eda-aim-verifier`, когда критерий подтверждён фактами.

Если применён другой `eda-*`-скил, журнал обязательно содержит его имя, итог и ссылку на каждый созданный им артефакт. Если отдельный артефакт этим скилом не создаётся, явно напиши `артефакт не создаётся`. Без отдельного скила запиши, что выполнено, и дай ссылки на затронутые файлы или иной проверяемый результат.

## Использование установленных скилов

В случае необходимости `eda-aim` может использовать установленные скилы в изолированных субагентах. Субагенты `eda-aim` не запускают их сами: исполнитель или проверяющий возвращает `needs_skill` со структурированным `skill_request`, а основной агент:

1. Приостанавливает запросившего агента и сохраняет его полный YAML.
2. Запускает новый изолированный субагент с чистым контекстом и поручает ему применить указанный установленный скил к `skill_request`.
3. Дожидается результата скила и собирает `skill`, `status`, полный результат, пути к артефактам и проверки.
4. Передаёт эти данные как `SKILL_RESULTS` тому же исполнителю или проверяющему; именно он дополняет общий журнал и продолжает свою роль.

Каждый такой вызов использует отдельного субагента. Основной агент не применяет запрошенный скил сам, не копирует его процедуру и не выполняет его содержательную работу. Субагент следует установленной инструкции скила целиком, включая её правила вопросов и делегации. Если изолированный запуск или обязательные для скила нативные субагенты недоступны, остановись с конкретным `blocked`, не заменяя их работой основного агента или CLI-fallback.

## Процесс

### 1. Согласовать цели

Запусти `eda-aim-planner` и передай:

```text
Рабочая директория: <cwd>
USER_REQUEST:
<полный дословный запрос>

MODE: <manual | automatic>
GOAL_FILE: <путь | none>
ANSWERS: <предыдущие вопросы и ответы | none>
APPROVAL: <approved | rejected | pending>

Верни результат строго по YAML-контракту агента.
```

Для нового запуска обрабатывай ответы так:

- `needs_input` — получи или самостоятельно выбери ответ по режиму, затем продолжи того же planner;
- `needs_approval` — покажи человеку точный список целей и задай один вопрос: подтверждает ли он этот список; автоматический режим это подтверждение не пропускает;
- после подтверждения передай `APPROVAL: approved` тому же planner;
- `ready` — сохрани `$GOAL_FILE` и переходи к выполнению;
- `blocked` — назови конкретный блокер.

Если человек отклонил список, передай причину planner и повтори согласование. Основной агент сам цели не формулирует и файл не пишет.

Для существующего файла возьми `pending_goals` из результата планировщика: если список непуст, передай его исполнителю; если все пункты уже отмечены, сразу запусти нового независимого проверяющего и не повторяй выполненную работу.

### 2. Выполнить цели

Раздели независимые пункты между одним или несколькими последовательными вызовами `eda-aim-executor`. Не запускай одновременную запись нескольких агентов в общий файл цели. Связанные пункты передавай одному агенту вместе.

Каждому executor передай:

```text
Рабочая директория: <cwd>
GOAL_FILE: <путь>
ASSIGNED_GOALS: <идентификаторы>
USER_REQUEST: <полный дословный запрос>
ANSWER_HISTORY: <вопросы и ответы этого запуска | none>
PREVIOUS_RESULT: <полный результат предыдущей попытки | none>
SKILL_RESULTS: <результаты запрошенных скилов и артефакты | none>

Запрашивай установленные eda-* скилы через `needs_skill`, когда они нужны для достижения назначенных целей.
Дополни журнал после каждого завершённого результата и верни YAML-контракт.
```

Исполнитель сам выбирает необходимые скилы. Например, он может запросить `eda-explore`, `eda-plan`, `eda-plan-polish`, `eda-plan-execute`, `eda-fix`, `eda-fix-by-review`, `eda-manual-test` или `eda-review`, соблюдая их границы и вопросы. Скил, который только планирует или проверяет, не считается выполнением цели без последующей реализации.

Обработай результат:

- `completed` — передай следующую группу целей или переходи к проверке;
- `needs_input` — ответь по общим правилам режима и продолжи того же executor;
- `needs_skill` — запусти `skill_request` по правилам выше и продолжи того же executor с полным `SKILL_RESULTS`;
- `failed` — не завершай цель: передай полный результат следующему вызову executor для тех же пунктов, чтобы он учёл диагностику и выбрал другую безопасную попытку;
- `blocked` — остановись только при явно названном внешнем неустранимом препятствии; если блокер требует ответа или изменения среды, продолжи после него.

Не считай отчёт исполнителя доказательством достижения и не ставь отметку `[x]`.

### 3. Независимо проверить

После каждого полного круга выполнения запусти отдельного `eda-aim-verifier`:

```text
Рабочая директория: <cwd>
GOAL_FILE: <путь>
USER_REQUEST: <полный дословный запрос>
ANSWER_HISTORY: <вопросы и ответы проверки | none>
SKILL_RESULTS: <результаты запрошенных проверочных скилов | none>

Независимо проверь каждый критерий по текущим файлам и фактическому поведению.
При необходимости запроси проверочные eda-* скилы через `needs_skill`.
Обнови только статусы, отметки `[x]` и журнал файла цели. Верни YAML-контракт.
```

Проверяющий не чинит реализацию. Он перепроверяет результат, запускает применимые тесты и при необходимости использует `eda-manual-test` или `eda-review`; созданные отчёты связывает в журнале. Если журнал ссылается на план, проверяющий также подтверждает, что в нём не осталось обязательных невыполненных пунктов.

- `reached` — все пункты подтверждены, статус файла `достигнута`, цикл завершён;
- `needs_work` — передай исполнителю только неподтверждённые пункты вместе с найденными пробелами и снова запусти проверяющего после исправлений;
- `needs_input` — ответь по режиму и продолжи того же verifier;
- `needs_skill` — запусти проверочный `skill_request` и продолжи того же verifier с полным `SKILL_RESULTS`;
- `blocked` — сохрани статус `заблокирована` и сообщи, что именно мешает проверке.

Продолжай цикл исполнитель → проверяющий без произвольного лимита, пока все цели не подтверждены либо не возник внешний неустранимый блокер. После повторного сбоя executor обязан использовать накопленную диагностику и изменить способ выполнения либо вернуть доказанный внешний блокер; повтор одного и того же сбоя не является достижением цели.

### 4. Финал

Сообщи:

- достигнута ли цель;
- путь к файлу цели;
- какие пункты подтверждены;
- главные изменённые файлы;
- использованные скилы и ссылки на их артефакты;
- выполненные проверки;
- конкретный блокер и оставшиеся пункты, если работа не завершена.

## Чего НЕ делать

- Формулировать цели, применять запрошенные скилы, менять код, выполнять реализацию или ставить финальную отметку основным агентом.
- Создавать файл до подтверждения точного списка целей человеком.
- Раздувать файл деталями реализации или повторять в нём содержимое других артефактов.
- Считать план, diff или самоотчёт исполнителя доказательством результата.
- Отмечать цель выполненной без отдельного проверяющего.
- Давать нескольким агентам параллельно редактировать общий журнал.
- Терять вопросы, ответы, ссылки на артефакты или причины блокировки при продолжении.
- Коммитить, пушить, создавать PR или выполнять другие внешние действия без явного запроса пользователя.

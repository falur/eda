# Скил: Отправитель ревью (eda-send-review)

Берёшь готовое ревью из `docs/reviews/`, отправляешь его на GitHub PR через `gh`. Отправляешь **всегда в одном формате**: общий комментарий-сводка плюс комментарии к строкам кода. В конец файла ревью дописываешь, куда отправил.

## Режим запуска

Прочитай `docs/settings.yaml`, если файл есть. Прямое указание пользователя в текущем сообщении важнее настройки.

Поддерживается только `version: 3`. При другой версии, отсутствующем разделе или неизвестном значении используй дефолт; настройки старого формата не применяй. Дефолт: `send-review.close_previous_reviews: false`.

| Настройка | Значения | Аргументы в сообщении |
|---|---|---|
| `send-review.close_previous_reviews` | `true`, `false` | `close_previous_reviews=true/false`, `send-review.close_previous_reviews=true/false`; включение: «закрой предыдущие ревью», «скрой старые комментарии»; выключение: «не закрывай предыдущие ревью», `keep previous reviews` |

Вычисли `$CLOSE_PREVIOUS_REVIEWS` один раз до отправки. Настройку в файле не меняй.

## Вход из сообщения пользователя

Текст рядом с вызовом скилла в текущем сообщении пользователя — главный вход. Сначала разбери именно его: тему, задачу, путь к файлу, статус отправки, ограничение по пунктам, режим закрытия предыдущих ревью и прямые указания.

Если этого входа достаточно, продолжай без вопроса. `AskUserQuestion` задавай только если входа нет, он противоречивый, найдено несколько равных вариантов или есть риск выполнить не ту задачу. Старое обсуждение в истории не считай входом, если пользователь не связал его с текущим вызовом явно.

## Главные правила

1. **Единый формат всегда.** Отправляешь как GitHub review: тело — общий комментарий-сводка, а каждое замечание с привязкой к строке — отдельным комментарием к строке кода (inline). Тип отправки меняет только статус review (`event`), но не структуру вывода.
2. **По умолчанию — все пункты.** Если пользователь не указал, что отправлять, отправляешь все замечания ревью. Если указал подмножество — только его.
3. **Интерактивные вопросы** — по разделу ниже.
4. **Прочитай `docs/rules.md` и `docs/arch.md`**, если есть, и строго следуй им при выборе способа отправки и финальной отметке.
5. **Не правишь код, не делаешь само ревью.** Только переупаковка и отправка.
6. **По умолчанию — `COMMENT`.** Статус review определяется только по явному указанию в контексте текущего вызова. Если статуса нет, отправляй `COMMENT` без вопроса. Оценка ревью не меняет event.
7. **Закрывай только свои предыдущие отправки.** При включённой настройке скрывай только более ранние сводки `eda-send-review`, созданные текущим GitHub-пользователем в целевом PR, и резолви только связанные с ними inline-треды. Чужие комментарии и обсуждения не трогай.
8. **Простой язык.** В сообщениях пользователю и комментариях PR без лишних терминов.

## Интерактивные вопросы

Когда инструкция говорит `AskUserQuestion`, это означает блокирующий интерактивный вопрос.
- Claude Code: используй `AskUserQuestion`.
- Codex interactive: если доступен `request_user_input`, используй его. Если tool недоступен, задай один короткий вопрос в чат, дай варианты 1–3, напиши «Ответь номером или своим вариантом. Я продолжу только после ответа.» и остановись.
- Codex exec / неинтерактивный запуск: не задавай вопросы и не пытайся читать stdin. Если без ответа нельзя безопасно продолжать, заверши работу со статусом `blocked: нужен ответ пользователя`, перечисли вопросы и варианты, не выполняй рискованные действия.
- Не запускай команды, которые ждут интерактивного ввода в терминале; перед такими командами спроси в хост-интерфейсе или остановись с `blocked`.
- Для отправки ревью это правило важнее продолжения: не создавай PR и не угадывай статус при противоречивых прямых указаниях вместо ответа пользователя. Одно явно указанное действие `approve` или `request-changes` уже является достаточным разрешением и повторного подтверждения не требует.

## Этапы

### 1. Проверить инструменты
`gh --version` + `gh auth status`. Если `gh` отсутствует или не авторизован — остановись, сообщи и выйди (это пользователю нужно решить).

### 2. Выбрать ревью и что отправлять
Сначала разбери текст рядом с вызовом: путь к ревью, название или часть названия, «последнее ревью», PR (`PR 12`, `#12`), статус отправки (`comment`, `review-comment`, `approve`, `request-changes`) и указание закрыть или сохранить предыдущие ревью.

Если найдено ровно одно ревью — продолжай без вопроса. Если найдено несколько одинаково подходящих ревью — `AskUserQuestion` со списком вариантов. Если входа нет — `AskUserQuestion` со списком последних файлов из `docs/reviews/`. Если `docs/reviews/` отсутствует или пуста — остановись с понятным вопросом или статусом `blocked: нужно ревью`. Прочитай файл целиком: result, оценку и замечания. Отсутствие статуса отправки само по себе не считается недостатком входа и не требует вопроса.

**Что отправлять.** По умолчанию — все замечания. Если в тексте указано подмножество, отправь только его. Синтаксис свободный, распознавай по смыслу: по номерам («пункты 1, 3, 5») или по типу («только security» → замечания с этим `Тип`). У находок нет разных степеней обязательности: каждый отправляемый пункт требует исправления. Выбор влияет и на сводку, и на комментарии к строкам. Для старого формата отправляй только раздел `Править обязательно`; предложения из остальных групп отбрасывай.

### 3. Найти целевой PR
Если номер PR указан в тексте пользователя — используй его. Иначе попробуй `gh pr view --json number,url,headRefName` — если у текущей ветки уже есть PR, возьми его номер.

Если PR нет — `AskUserQuestion`: «PR ещё нет: создать PR из текущей ветки / указать номер существующего PR / прервать». При создании используй `gh pr create` (заголовок и тело — по последним коммитам ветки).

### 4. Выбрать статус review

Review отправляется всегда; здесь выбирается только его статус (`event`).

| Контекст текущего вызова | event | Вопрос |
|---|---|---|
| явно указано `approve` | `APPROVE` | не задавать |
| явно указано `request-changes` / «запросить изменения» | `REQUEST_CHANGES` | не задавать |
| явно указано `comment` / `review-comment` | `COMMENT` | не задавать |
| статус не указан | `COMMENT` | не задавать |

`comment` и `review-comment` означают review без решения о принятии изменений (`event=COMMENT`) — обычный комментарий-ревью, который тоже несёт сводку и комментарии к строкам. Явно приложенный или названный пользователем контекст текущего вызова учитывай наравне с текстом рядом со скиллом. Не выводи статус из result, score, старого обсуждения или предыдущих запусков. Если в текущем контексте одновременно указаны несовместимые статусы и приоритет неясен — `AskUserQuestion` с тремя вариантами.

### 5. Собрать сводку и комментарии к строкам
Из выбранных пунктов собери две части.

**Сводка** — тело review:

```markdown
## Ревью: <заголовок>

**Оценка:** N/100. <одно-два предложения почему>
**Результат:** <clean | changes-required>

<короткое резюме: что отправлено и общий вывод>

### Замечания
1. **[тип]** <краткая суть и требуемое исправление>

### Замечания вне diff
1. **[тип]** `path/file.py:42` — <что не так>. → <что предлагаешь>

_Сгенерировано из `<путь к docs/reviews/...>`_
<!-- eda-send-review -->
```

Раздел «Замечания вне diff» добавляй только если такие пункты есть (см. ниже); иначе опусти его.

**Комментарии к строкам** — по одному на каждое отправляемое замечание, чьё `Где: path:line` входит в diff PR. Для каждого: `{ "path": "<path>", "line": <line>, "side": "RIGHT", "body": "<суть простым языком + рекомендация + как исправить>\n\n<!-- eda-send-review -->" }`. Для замечания об удалённой строке используй `"side": "LEFT"`.

Какие строки входят в diff — определи по `gh pr diff <num>`. Замечания, чьи строки в diff не попали (или без `path:line`), в комментарии к строкам **не** клади — перенеси их в раздел «Замечания вне diff» сводки, чтобы ничего не потерялось.

### 6. Зафиксировать предыдущие отправки и отправить

Если `$CLOSE_PREVIOUS_REVIEWS=false`, не запрашивай старые комментарии и переходи сразу к отправке.

Если `$CLOSE_PREVIOUS_REVIEWS=true`, **до новой отправки** получи через `gh api graphql` все страницы `reviews`, `comments` и `reviewThreads` целевого PR. Сохрани два списка:

- `$PREVIOUS_SUMMARY_IDS` — Node ID неминимизированных `PullRequestReview` и fallback-`IssueComment`, у которых `viewerDidAuthor=true`, `viewerCanMinimize=true`, а тело содержит `<!-- eda-send-review -->` или старую метку `_Сгенерировано из \`docs/reviews/...\`_`;
- `$PREVIOUS_THREAD_IDS` — Node ID незарезолвленных тредов с `viewerCanResolve=true`, у которых корневой комментарий относится через `pullRequestReview.id` к одному из найденных предыдущих review.

Не выбирай предыдущие отправки только по автору: метка `eda-send-review` обязательна. Не включай комментарии других пользователей, немаркированные ручные review и треды, не связанные с найденными review. Обработай пагинацию до `hasNextPage=false`. Поскольку снимок сделан до POST, новая отправка в эти списки не попадёт.

Тело сводки и комментарии собери в один JSON через `mktemp`:

```json
{ "body": "<сводка>", "event": "COMMENT|APPROVE|REQUEST_CHANGES", "comments": [ { "path": "...", "line": 42, "side": "RIGHT", "body": "..." } ] }
```

Отправь одним вызовом Reviews API:

```bash
OWNER_REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)
gh api "repos/$OWNER_REPO/pulls/<num>/reviews" --method POST --input <payload.json>
```

Fallback'ы:
- API упал с `422` из-за конкретных строк — перенеси эти пункты в раздел «Замечания вне diff» сводки и переотправь без них.
- У цели нет diff/строк PR вовсе (нечего привязывать) — отправь только сводку обычным комментарием: `gh pr comment <num> --body-file <tmpfile>`.
- Другая ошибка — покажи вывод пользователю и спроси через `AskUserQuestion` (повторить / прервать). Не меняй event без нового прямого указания пользователя.

### 7. Закрыть предыдущие отправки

Выполняй этот этап только после успешной новой отправки и только при `$CLOSE_PREVIOUS_REVIEWS=true`.

Каждую старую сводку из `$PREVIOUS_SUMMARY_IDS` скрой как устаревшую — это действие **Hide** в интерфейсе GitHub:

```bash
gh api graphql -f query='mutation($id: ID!) { minimizeComment(input: {subjectId: $id, classifier: OUTDATED}) { minimizedComment { isMinimized } } }' -F id="$SUMMARY_ID"
```

Каждый связанный старый тред из `$PREVIOUS_THREAD_IDS` зарезолви:

```bash
gh api graphql -f query='mutation($id: ID!) { resolveReviewThread(input: {threadId: $id}) { thread { isResolved } } }' -F id="$THREAD_ID"
```

Обрабатывай все элементы, даже если отдельная мутация упала. Ошибка очистки не отменяет уже отправленное новое ревью и не должна приводить к повторной отправке. Сохрани количества успешных и неуспешных Hide/Resolve для финала.

### 8. Дописать ссылку в файл ревью
В конец `$REVIEW_FILE` добавь:

```markdown
## Отправлено
- PR: <URL из ответа gh>
- Статус: <comment | approve | request-changes>
- Отправлено пунктов: <сколько / inline + сколько в сводке>
- Предыдущие ревью: <не закрывались | скрыто N сводок, зарезолвлено M тредов | частично: скрыто N, зарезолвлено M, ошибок K>
- Дата: <YYYY-MM-DD HH:MM>
```

### 9. Финал
Короткое сообщение: PR-номер и URL, статус отправки, сколько пунктов ушло комментариями к строкам и сколько в сводку, результат закрытия предыдущих ревью и путь к файлу ревью.

## Чего НЕ делать
- Делать само ревью или править замечания — это `eda-review` / `eda-fix-by-review`.
- Отправлять всё одним обычным комментарием PR, когда строки можно привязать к diff — обычный комментарий только fallback при отсутствии diff.
- Терять замечания вне diff — они идут в сводку отдельным разделом.
- Выводить `approve` или `request-changes` из result, score или не связанного с вызовом старого контекста — без явного статуса в контексте текущего вызова всегда `COMMENT`.
- Скрывать или резолвить чужие, ручные или не связанные с предыдущими отправками `eda-send-review` комментарии.
- Закрывать предыдущие отправки до успешной публикации нового ревью.
- Передавать тело через `-b "..."` со спецсимволами — только `--input` (Reviews API) или `--body-file` (fallback).
- Создавать PR молча, если его нет — только через `AskUserQuestion`.
- Сохранять копии отправленного в отдельные файлы — связь через ссылку в файле ревью.

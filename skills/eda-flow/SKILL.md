# Скил: Цикл разработки (eda-flow)

Ведёшь одну задачу через три сессии и останавливаешься перед коммитом.

| Сессия | Где выполняется | Шаги |
|---|---|---|
| 1. План | текущий контекст | `eda-plan` → параллельные проверки плана → мета-ревью плана → `eda-plan-review-fix` при находках |
| 2. Реализация | изолированный субагент | `eda-plan-execute` → `eda-manual-test` при визуальных изменениях → `eda-fix` при найденных багах |
| 3. Ревью | изолированные субагенты | `eda-review` на мета-модели → `eda-fix-by-review` |

Полировочных циклов здесь нет: `eda-plan-polish` и `eda-polish` не запускаются ни при каких аргументах. Каждый вид ревью выполняется один раз за круг, а число кругов ограничено настройками.

Коммит в цикл не входит. После третьей сессии верни управление пользователю с предложением `eda-commit`.

## Вход из сообщения пользователя

Текст рядом с вызовом скила в текущем сообщении — главный вход. Сохрани его целиком в `$USER_REQUEST` для журнала и раздели на две части:

- `$FLOW_ARGS` — служебные аргументы запуска цикла из списка overrides ниже;
- `$TASK_TEXT` — сама задача без этих аргументов. Именно её передавай в `eda-plan` и в проверки плана. Служебные слова не должны попасть в план как часть задачи, иначе проверка покрытия найдёт «непокрытую часть запроса», которую нечем закрыть.

`$RESEARCH_FILE` определи так: явный путь используй как есть; при словах «последнее исследование» или без указания возьми самый новый файл из `docs/artifacts/researches/`, если он относится к этой задаче; если подходящего research нет, работай по тексту задачи и запиши `research: none`. Отдельный вопрос про research не задавай.

Если передан готовый план из `docs/artifacts/plans/`, пропусти `eda-plan` и начни с проверок плана, записав причину пропуска.

Overrides сообщения важнее настроек и действуют только на текущий запуск:

| Override | Действие |
|---|---|
| `automatic`, `manual` | Режим ответов на вопросы цикла |
| `без ревью плана` | Пропустить проверки плана и мета-ревью |
| `без ручных тестов`, `с ручными тестами` | `flow.manual_test.mode` = `off` или `always` |
| `без ревью кода` | Пропустить третью сессию |
| `только план` | Выполнить первую сессию и остановиться, отдав пути к плану и ревью плана |
| `начни с выполнения` | Пропустить первую сессию целиком; требует готового плана во входе |
| `execute single`, `execute subagents` | Режим для `eda-plan-execute` |
| `manual-test smoke` | Аргумент глубины для `eda-manual-test` |
| `кругов ревью N` | `flow.code_review.max_cycles` = N |

Слово из описания самой задачи за override не принимай: override должен явно относиться к цепочке, а не к предметной области.

## Настройки

Прочитай `docs/settings.yaml`, если файл есть. Поддерживается только `version: 3`; при другой версии или отсутствующем разделе используй дефолты ниже и добавь предупреждение в финальный отчёт. Настройки проекта во время запуска не меняй.

```yaml
flow:
  mode: automatic
  meta_model:
    claude: fable
    codex: gpt-5.6-sol
  plan_review:
    enabled: true
    max_cycles: 1
  execute:
    mode: inherit
  manual_test:
    mode: auto
    max_cycles: 2
  code_review:
    enabled: true
    max_cycles: 1
```

| Настройка | Значения | Дефолт | Что задаёт |
|---|---|---|---|
| `flow.mode` | `automatic`, `manual` | `automatic` | Кому адресованы обратимые рабочие решения цикла |
| `flow.meta_model.claude` | `fable`, `haiku`, `sonnet`, `opus` | `fable` | Модель мета-ревьюера плана и ревьюера кода в Claude Code |
| `flow.meta_model.codex` | `gpt-5.6-luna`, `gpt-5.6-terra`, `gpt-5.6-sol` | `gpt-5.6-sol` | То же для Codex |
| `flow.plan_review.enabled` | `true`, `false` | `true` | Запускать ли проверки плана и мета-ревью |
| `flow.plan_review.max_cycles` | положительное целое | `1` | Сколько раз повторять «правка плана → мета-ревью» |
| `flow.execute.mode` | `inherit`, `single`, `subagents`, `auto` | `inherit` | Режим для `eda-plan-execute`; `inherit` не передаёт ничего, и действует `plan-execute.mode` проекта |
| `flow.manual_test.mode` | `auto`, `always`, `off` | `auto` | Когда запускать `eda-manual-test`; `auto` — только при визуальных изменениях |
| `flow.manual_test.max_cycles` | положительное целое | `2` | Сколько раз повторять «`eda-fix` → `eda-manual-test`» |
| `flow.code_review.enabled` | `true`, `false` | `true` | Запускать ли третью сессию |
| `flow.code_review.max_cycles` | положительное целое | `1` | Сколько раз повторять «`eda-review` → `eda-fix-by-review`» |

Готовность плана определяют сами проверки: план готов, когда не осталось ни одной принятой находки. `plan-review.threshold` относится к отдельному скилу `eda-plan-review` и в этом цикле не применяется. Режимы и модели специализированных проверок кода задают `review.agents.<check>.mode` и `review.agents.<check>.model.<platform>`; их применяет сам `eda-review`. Глубину ручной проверки задаёт `manual-test.depth`.

Если модель из `flow.meta_model` не поддерживается хостом, один раз сообщи это и продолжи цикл на модели по умолчанию, пометив в отчёте, что мета-ревью выполнено другой моделью.

## Вопросы

`automatic` — обратимые рабочие решения текущего цикла делегированы тебе: выбирай сам и записывай выбор в журнал. `manual` — передавай вопросы шагов человеку.

- Claude Code: используй `AskUserQuestion`.
- Codex interactive: используй `request_user_input`, если доступен; иначе задай один короткий вопрос с вариантами 1–3 и остановись до ответа.
- Codex exec и другой неинтерактивный запуск: не читай stdin; заверши `blocked: нужен ответ пользователя` и перечисли вопрос с вариантами.

Вопрос человеку задаёт только основной агент. У субагентов сессий интерактивного канала нет: они возвращают вопрос в своём контракте, ты передаёшь его человеку и продолжаешь того же субагента с ответом.

В `automatic` не спрашивай о переходе между успешными шагами и о месте выполнения плана: выбирай текущую ветку, если пользователь явно не просил ветку или worktree. Для `eda-plan` передавай `decision_mode: autonomous`, а значения `ask_each_time` для размера, тестов и логирования заменяй на `normal`, `after_each_phase` и `standard`, если текущий вызов не задаёт другое. Подтверждение плана в Plan Mode остаётся за пользователем в обоих режимах.

`automatic` не разрешает необратимые внешние действия, расширение scope, публикацию, расходы, удаление данных, ослабление проверок и изменение production или staging. Такое подтверждение всегда передавай человеку.

## Изоляция сессий

Сессии 2 и 3 запускай в новых изолированных субагентах со свежим контекстом без истории текущего диалога: в Claude Code — новый `Agent` с самодостаточным task-сообщением, в Codex — `spawn_agent` с `fork_turns: "none"`. Субагент сессии сам загружает `SKILL.md` нужных скилов и сам запускает их штатных субагентов.

В Claude Code субагент сессии читает установленный `SKILL.md` как файл и выполняет его контракт сам. Инструмент `Skill` для этих скилов он не вызывает: у части из них включён `context: fork`, и вызов создал бы ещё один уровень вложенности с другой моделью, из-за чего мета-модель сессии перестала бы что-либо решать.

Каждому субагенту сессии передавай блок погружения в контекст:

```text
Рабочая директория: <cwd>
Задача пользователя дословно: <$TASK_TEXT>
Ориентиры проекта: CLAUDE.md или AGENTS.md в корне.
Рамку проекта — docs/rules.md, docs/arch.md и применимые карточки — читают сами вызываемые скилы и их исполнители. Не читай их заранее целиком, чтобы не дублировать.
Артефакты: research <path|none>, план <path>, ревью плана <path|none>, журнал выполнения <path|none>, ручная проверка <path|none>, ревью кода <path|none>.
Скилы этой сессии: <список в порядке запуска и их аргументы>
Интерактивных вопросов у тебя нет: вопрос любого скила верни в поле questions своего контракта и остановись со статусом blocked.
Запрещено: коммитить, пушить, создавать PR, менять docs/settings.yaml, запускать eda-polish и eda-plan-polish.
Верни YAML-отчёт по контракту ниже.
```

Основной агент содержательную работу сессий не выполняет: он готовит вход, передаёт ответы человека, проверяет статусы и связывает артефакты.

Если изоляция или субагенты недоступны, остановись: `blocked: недоступна изоляция сессии`. Не выполняй сессию основным агентом и не добавляй CLI-fallback, которого нет в вызываемом скиле.

## Технические остановки субагентов

Техническую ошибку инструмента субагентов не смешивай со статусами `failed` и `blocked` содержательного контракта. Сохрани полный исходный текст ошибки и обработай её по причине:

- лимит параллельности или отсутствие свободного слота — дождись уже запущенного этим циклом агента, при необходимости закрой завершённые потоки и повтори тот же запуск; если управляемых активных агентов нет, заверши `blocked: заняты слоты субагентов`;
- лимит глубины вложения — не повторяй запуск и не выполняй этап сам; заверши `blocked: достигнут лимит глубины субагентов`, указав наблюдаемую и требуемую глубину;
- исчерпана usage-квота — не делай автоматических повторов; заверши `blocked: исчерпана квота`, сохрани время reset или условие продолжения, если хост его сообщил;
- не хватает разрешения — запроси одно конкретное разрешение по правилам текущей среды и после ответа продолжи того же агента; в неинтерактивной среде заверши `blocked: нужно разрешение пользователя`;
- временная API-, server-, overload- или network-ошибка — один раз продолжи того же агента; если resume недоступен, один раз запусти ту же роль с исходным входом, полным частичным результатом и требованием сначала сверить текущее состояние; повторный такой сбой заверши как `blocked` с исходной ошибкой;
- неизвестная техническая ошибка — не угадывай причину и не зацикливай retry; заверши `blocked: техническая ошибка субагента` с полным исходным текстом.

Ожидание слота и один технический retry не расходуют лимиты кругов.

## Старт

До первой сессии выполни `git status --short` и запиши состояние рабочего дерева как `$BASELINE`. Если в нём уже есть незакоммиченные изменения, в `automatic` продолжай с предупреждением в финальном отчёте, в `manual` спроси, продолжать или сначала разобраться с ними. Baseline нужен, чтобы третья сессия ревьюила изменения этого цикла, а не чужую работу.

## Сессия 1. План и ревью плана

Выполняй её в текущем контексте: Plan Mode и подтверждение плана человеком требуют основной сессии.

1. Запусти `eda-plan` с `$TASK_TEXT`, путём `$RESEARCH_FILE` и аргументом `без проверок`: встроенные проверки плана заменяет эта сессия. Сохрани путь как `$PLAN_FILE`.
2. Если `flow.plan_review.enabled: false`, пропусти шаги 3–7 и переходи ко второй сессии.
3. Одним пакетом в одном ответе запусти три установленных агента параллельно: `eda-plan-check-executability`, `eda-plan-check-alignment` и `eda-plan-check-feasibility`. Не дели их на волны и не жди завершения одного перед запуском другого. Результаты собирай только нативным механизмом субагентов; в Codex используй `wait_agent`. Не опрашивай файлы, не используй `sleep` и фиксированные таймауты.

   Вход у проверок разный — лишнее не передавай:

   ```text
   Рабочая директория: <cwd>
   PLAN_FILE: <путь>
   MODEL: <модель из установленного определения агента>
   PLAN_CONTEXT: <тип задачи, затронутые области, применимые документы>
   TASK_TEXT: <только для alignment>
   RESEARCH_FILE: <только для alignment; путь или none>

   Верни результат строго по YAML-контракту установленного агента.
   ```

   Модели проверок плана настройками не управляются: в `MODEL` пиши модель из установленного определения агента и сверяй ответ с ней. Системные prompts агентов в task-сообщение не копируй.
4. Проверь у каждого ответа `status`, `check`, `model` и структуру. При `blocked`, неверном YAML или отсутствующих обязательных полях один раз повтори того же агента с описанием ошибки формата. Если проверка не завершилась и со второго раза, останови цикл без мета-ревью.
5. Запусти агента `eda-plan-meta-review` на модели `flow.meta_model`. Передай рабочую директорию, `PLAN_FILE`, `$TASK_TEXT`, полные YAML-результаты проверок и `PREVIOUS_REVIEW` — отчёт прошлого круга или `none`. Он сверяет находки, отсеивает неподтверждённые, строит единый чек-лист с идентификаторами `E`, `A`, `F` и `M`, считает score, сохраняет отчёт в `docs/artifacts/plan-reviews/` и при `ready` сам обновляет в плане `status: reviewed` и `plan_review`. Сохрани путь как `$PLAN_REVIEW_FILE`, а также `open_items`, `growth_items` и `checks_to_repeat`.
6. При `plan_status: changes-required` запусти `eda-plan-review-fix` в изолированном субагенте с `$PLAN_FILE` и `$PLAN_REVIEW_FILE`. Он закрывает все строки чек-листа со статусом `fail` — и пункты исполнимости, и принятые находки соответствия и реализуемости.

   Если fix вернул `blocked: пункт требует роста плана`, сам scope не расширяй: передай человеку один вопрос — доработать план через `eda-plan` под эти пункты или отказаться от них с причиной. Непустой `growth_items` в мета-ревью предупреждает об этом заранее.
7. После успешного fix повтори проверки экономно: `eda-plan-check-executability` запускай всегда, а `eda-plan-check-alignment` и `eda-plan-check-feasibility` — только если они были в `checks_to_repeat` прошлого круга. Затем снова запусти мета-ревью, передав ему прошлый `$PLAN_REVIEW_FILE` как `PREVIOUS_REVIEW`.

   Круги считай по `flow.plan_review.max_cycles`. Если лимит достигнут, а статус всё ещё `changes-required`, остановись: `blocked: план не сходится` с идентификаторами открытых пунктов. Если два круга подряд не меняют состав принятых находок, остановись раньше по той же причине.

При `plan_status: ready` переходи ко второй сессии без вопроса. При override `только план` остановись здесь и отдай пути к плану и ревью.

## Сессия 2. Реализация

Запусти один изолированный субагент со свежим контекстом. Он координирует работу и последовательно выполняет:

1. `eda-plan-execute` с `$PLAN_FILE`. Режим передавай, только если `flow.execute.mode` не `inherit`; при `inherit` режим выбирает сам `eda-plan-execute` по `plan-execute.mode` проекта. Место выполнения — текущая ветка, если пользователь не просил другое.
2. Определяет визуальные изменения по фактическому diff выполненного плана: компоненты, шаблоны, стили, клиентские маршруты, публичные страницы и другие части интерфейса. При `flow.manual_test.mode: auto` запускает `eda-manual-test` только при визуальных изменениях и записывает причину решения; при `always` запускает всегда; при `off` не запускает и не изображает ручную проверку.
3. При `failed` у ручной проверки — `eda-fix` с её отчётом, затем повторный `eda-manual-test`. Повторяет до `passed` или до `flow.manual_test.max_cycles`; при исчерпании лимита или при двух одинаковых результатах подряд возвращает `blocked` с причиной.
4. `eda-manual-test` и `eda-fix` он запускает вложенными изолированными субагентами, а не в собственном контексте: каждый повтор должен начинаться со свежего контекста, а не поверх накопленной истории выполнения.
5. Автоматические тесты и линтеры проекта ручную проверку не заменяют. `blocked` у ручной проверки за `passed` не выдаётся.

Контракт результата сессии:

```yaml
status: completed | blocked
plan: <docs/artifacts/plans/...>
execution: <docs/artifacts/executions/...>
changed_paths: [<пути, изменённые этой сессией>]
visual_changes: true | false
visual_reason: <почему решено так>
manual_test: <docs/artifacts/manual-tests/... | skipped | off>
manual_test_result: <passed | failed | blocked | none>
fixes: [<docs/artifacts/fixes/... или пусто>]
qa_cycles: <число>
checks: <итог финальной проверки проекта>
questions: [<вопросы человеку или пусто>]
blockers: [<блокеры или пусто>]
```

`blocked` с непустым `questions` означает вопрос человеку, а не провал: передай его по режиму и продолжи того же субагента с ответом. Не начинай третью сессию, пока вторая не вернула `completed`.

## Сессия 3. Ревью кода и исправления

Запускай только при `flow.code_review.enabled: true` и после успешной второй сессии.

1. Запусти изолированный субагент на модели `flow.meta_model` — он и есть мета-ревьюер кода. Субагент читает установленный `SKILL.md` скила `eda-review` и выполняет его контракт сам: специализированные проверки запускает установленными агентами на их моделях из `review.agents`, а сведение результатов, отсев неподтверждённого и итоговый отчёт делает сам, на мета-модели.

   Передай ему target и контекст: незакоммиченные изменения цикла, `$BASELINE` и `changed_paths` второй сессии, `$PLAN_FILE`, журнал выполнения и отчёт ручной проверки. Журнал даёт отклонения и решения, отчёт ручной проверки — что уже проверено руками. Если рабочее дерево было чистым на старте, ограничивать target не нужно.

   Сохрани путь ревью как `$REVIEW_FILE`, а также `result` и `score`.
2. При `result: clean` третья сессия закончена.
3. При `result: changes-required` запусти второй изолированный субагент на модели по умолчанию: `eda-fix-by-review` с `$REVIEW_FILE`. Он применяет находки; отклонить может только фактически неверную и обязан записать причину.
4. Если `flow.code_review.max_cycles` больше единицы, после исправлений повтори шаг 1 по обновлённым изменениям. При исчерпании лимита с непринятыми находками цикл успешным не считай и перечисли открытые пункты.

Контракт результата каждого субагента этой сессии:

```yaml
status: completed | blocked
artifact: <docs/artifacts/reviews/... | docs/artifacts/review-fixes/...>
result: <clean | changes-required | applied>
score: <0..100 | null>
total: <число находок ревью | null>
accepted: <число применённых находок | null>
rejected: <число отклонённых находок | null>
questions: [<вопросы человеку или пусто>]
blockers: [<блокеры или пусто>]
```

Сессия считается успешной, когда `accepted + rejected` равно числу находок ревью, отчёт исправлений сохранён со `status: done`, а финальная проверка проекта зелёная. Отклонённые находки перечисли в финале с причинами: они остаются в коде осознанно.

## Журнал и финал

Веди журнал в своём контексте: сессия, шаг, аргументы, статус, пути артефактов, score, число кругов. Отдельный файл оркестрации не создавай.

В финальном сообщении укажи: режим, фактически выполненные сессии и шаги с аргументами, пропущенные шаги и причины, пути ко всем артефактам, score плана и score ревью кода, результат ручной проверки или причину её пропуска, отклонённые находки ревью с причинами, число кругов, состояние git «не закоммичено» и следующий шаг `eda-commit`.

Цикл успешен, когда план получил `ready`, вторая сессия вернула `completed`, а третья закрыла все находки ревью в пределах лимита кругов. Пропущенные по настройкам шаги называй явно: «ручные тесты пропущены настройкой», «ревью кода отключено настройкой».

## Чего НЕ делать

- Выполнять содержательную работу сессии вместо вызванного скила или агента.
- Запускать `eda-polish` и `eda-plan-polish`: полировочных циклов в этом скиле нет.
- Передавать служебные аргументы цикла в план и в проверки как часть задачи.
- Коммитить, пушить, создавать PR, отправлять ревью и управлять worktree.
- Начинать следующую сессию до успешного завершения предыдущей.
- Считать зелёные автотесты заменой включённой ручной проверки.
- Терять аргументы, порядок шагов и пути артефактов при передаче между сессиями.
- Менять `docs/settings.yaml` во время запуска.

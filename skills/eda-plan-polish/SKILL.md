# Скил: Полировка плана (eda-plan-polish)

Берёшь готовый план из `docs/plans/` и доводишь его до состояния, когда его можно передать в `eda-plan-execute`. Порог по умолчанию — `95`, лимит по умолчанию — `5` итераций. В `strict` каждая итерация после трёх моделей дополнительно отдаёт план соседнему CLI на кросс-ревью.

Каждая итерация начинается с трёх независимых моделей с одним и тем же промптом. Основной агент не ставит предварительную оценку сам: он оценивает план только после ответов агентов, принимает или отклоняет предложения, правит план при оценке ниже порога и запускает новую итерацию.

## Вход из сообщения пользователя

Текст рядом с вызовом скилла — главный вход. Разбери путь к плану, название или часть названия, «последний план», порог, лимит итераций, ограничения и прямые запреты.

Если входа достаточно, продолжай без вопроса. `AskUserQuestion` задавай только если входа нет, найдено несколько равных вариантов или есть риск полировать не тот план. Старую историю не считай входом, если пользователь не связал её с текущим вызовом явно.

## Настройки

Прочитай `docs/settings.yaml`, если файл есть. Прямое указание пользователя в текущем сообщении важнее настроек.

Поддерживается только `version: 2`. При другой версии, отсутствующем разделе или неизвестном значении используй дефолт; настройки старого формата не применяй. Дефолт: `plan-polish.strict: false`.

- `plan-polish.strict` включает кросс-CLI ревью плана после трёх агентов в каждой итерации; выключение: `normal`, `без strict`, `без строгого режима`.
- Порог качества по умолчанию — `95`, можно переопределить словами `до 90`, `threshold 90`, `цель 90`.
- Лимит по умолчанию — `5` итераций, можно переопределить словами `лимит 3`, `max iterations 3`, `не больше 3 кругов`.
- Оценка `95–100` означает готовность к исполнению; `80–94` — нужно уточнить; `60–79` — рискованный план; ниже `60` — нужен серьёзный переплан или вопросы пользователю.

## Жёсткие правила

1. Работай только с готовым файлом плана в `docs/plans/`.
2. Не правишь код. Содержательно менять можно только выбранный файл плана; в `strict` можно создать или обновить только вспомогательный файл `${PLAN_FILE%.md}_strict_cli_review.md`. Миграции, конфиги, зависимости и lock-файлы не трогай.
3. Не запускай проверки и исполняющие команды: `test`, `lint`, `build`, `typecheck`, `check`, `dev`, `start`, миграции, seed, smoke-тесты, браузерные проверки и API-запросы. При полировке плана можно читать файлы и искать по коду, но нельзя проверять проект выполнением команд.
4. Не ставь предварительную оценку без агентов. Сразу запускай три изолированных агента параллельно, одним batch, до чтения любого результата.
5. Итоговую оценку 0–100 выставляй только после чтения результатов всех трёх агентов, а в `strict` — ещё и результата соседнего CLI.
6. У всех трёх агентов один общий промпт: каждый проверяет весь план целиком, а не отдельную роль.
7. Не добавляй неподтверждённые существенные решения: БД/API-контракты, зависимости, архитектурные развилки, auth/permissions/payments/secrets/персональные данные и миграции.
8. Сохраняй структуру `eda-plan`: `Целевой алгоритм`, `Контракты реализации`, `Фазы выполнения`, `Тесты`, `Логирование`, если эти разделы есть или должны быть по формату.
9. Не пропускай кросс-CLI молча в `strict`: если соседней CLI нет, спроси через `AskUserQuestion`, завершить как normal или прервать.
10. Если качество не растёт два круга подряд, достигнут лимит или нужен ответ пользователя, остановись и честно назови причину.

## Интерактивные вопросы

Когда инструкция говорит `AskUserQuestion`, это блокирующий вопрос:
- Claude Code: используй `AskUserQuestion`.
- Codex interactive: если доступен `request_user_input`, используй его; иначе задай один короткий вопрос в чат с вариантами 1–3 и остановись до ответа.
- Codex exec / non-interactive: не читай stdin; если без ответа нельзя безопасно продолжать, заверши со статусом `blocked: нужен ответ пользователя`.

## Процесс

### 1. Выбрать план

Определи `$PLAN_FILE`:
- указан путь — используй его;
- указано название или часть названия — найди совпадение в `docs/plans/`;
- сказано «последний план» — возьми самый новый файл из `docs/plans/`;
- входа нет — спроси, показав несколько последних планов;
- `docs/plans/` нет или она пуста — остановись: `blocked: нужен готовый план`.

Прочитай только выбранный план целиком. По front matter извлеки `status`, `mode`, `plan_size`, `test_strategy`, `logging_strategy`, `sources.rules`, `sources.arch`, `sources.references`, `sources.research`, `meta_reviewers`.

Сам не читай `docs/rules.md`, `docs/arch.md`, `sources.references`, `sources.research` и релевантный код на этом шаге. Передай эти пути агентам в общем промпте: проверка правил, архитектуры, эталонов, research и кода — их работа. Если старый план не содержит `sources.references`, но существует `docs/references.md`, передай агентам индекс: они должны выбрать только применимые карточки. Если индекса нет, продолжай без references. Основной агент может открыть внешний файл только позже и точечно, если нужно проверить конкретное предложение агента перед правкой плана. Не запускай проверки.

### 2. Запустить три модели

В каждой итерации, включая первую, запускай в одном batch три изолированных агента:

| Уровень | Claude Code (`Agent` tool) | Codex interactive (`spawn_agent`) | Codex exec / non-interactive fallback |
|---|---|---|---|
| Быстрая модель | `haiku` | `gpt-5.4-mini` | `gpt-5.4-mini` |
| Кодовая модель | `sonnet` | `gpt-5.3-codex` | `gpt-5.3-codex` |
| Флагманская модель | `opus` | `gpt-5.5` | `gpt-5.5` |

- Claude Code: используй `Agent` tool с моделями из таблицы.
- Codex interactive: если доступен `spawn_agent` или аналог, используй субагентов с моделями из таблицы. Не используй отдельные `codex exec`, когда субагенты доступны.
- Codex exec / non-interactive fallback: если субагентов нет, запусти три `codex exec --model <id>` параллельно одной Bash-командой с `&` и общим `wait`.
- Если модель недоступна, возьми ближайшую code-capable модель того же уровня. Не заменяй три уровня одной моделью.

Общий промпт каждому агенту:

```text
Прочитай $PLAN_FILE, docs/rules.md, docs/arch.md, карточки из sources.references, sources.research при наличии и релевантные файлы, на которые ссылается план. Если sources.references отсутствует, прочитай docs/references.md и выбери только применимые карточки.

Проверь весь план целиком: исполнимость, соответствие правилам, архитектуре и применимым эталонам, обоснованность отклонений от примеров, полноту целевого алгоритма, БД/API/внешние контракты, связность и размер фаз для одного исполнителя на фазу, тестовые сценарии, логирование, неподтверждённые решения, скрытые риски и места, где eda-plan-execute не сможет продолжить без нового исследования.

Не правь файлы и не запускай проверки, тесты, линтеры, билды, typecheck, dev-серверы, миграции, браузерные проверки или API-запросы. Можно только читать файлы.

Ответь кратко:
score: <0–100>
+ Принять: <конкретная правка и куда встроить>
~ Уточнить: <что переформулировать>
-- Убрать: <что неверно, лишнее или противоречит контексту>
? Вопрос: <что нельзя безопасно решить без пользователя>
```

### 3. Strict: кросс-CLI ревью плана

Обычный режим пропускает этот этап. В `strict` после ответов трёх агентов, но до итоговой оценки, отдай план соседнему CLI через `Bash`.

Если ты в Claude Code — запускай Codex CLI:

```bash
codex exec "Прочитай $PLAN_FILE, docs/rules.md, docs/arch.md, карточки из sources.references, sources.research при наличии и релевантные файлы, на которые ссылается план. Если sources.references отсутствует, выбери применимые карточки через docs/references.md. Глубоко проверь весь план целиком: исполнимость, соответствие правилам, архитектуре и эталонам, обоснованность отклонений, полноту целевого алгоритма, БД/API/внешние контракты, связность и размер фаз для одного исполнителя на фазу, тесты, логирование, неподтверждённые решения и скрытые риски. Не правь файлы и не запускай проверки, тесты, линтеры, билды, typecheck, dev-серверы, миграции, браузерные проверки или API-запросы. Можно только читать файлы. Ответь кратко: score: <0–100>; + Принять; ~ Уточнить; -- Убрать; ? Вопрос." > "${PLAN_FILE%.md}_strict_cli_review.md"
```

Если ты в Codex — запускай Claude CLI:

```bash
claude -p "Прочитай $PLAN_FILE, docs/rules.md, docs/arch.md, карточки из sources.references, sources.research при наличии и релевантные файлы, на которые ссылается план. Если sources.references отсутствует, выбери применимые карточки через docs/references.md. Глубоко проверь весь план целиком: исполнимость, соответствие правилам, архитектуре и эталонам, обоснованность отклонений, полноту целевого алгоритма, БД/API/внешние контракты, связность и размер фаз для одного исполнителя на фазу, тесты, логирование, неподтверждённые решения и скрытые риски. Не правь файлы и не запускай проверки, тесты, линтеры, билды, typecheck, dev-серверы, миграции, браузерные проверки или API-запросы. Можно только читать файлы. Ответь кратко: score: <0–100>; + Принять; ~ Уточнить; -- Убрать; ? Вопрос." > "${PLAN_FILE%.md}_strict_cli_review.md"
```

Если соседней CLI нет — `AskUserQuestion`: продолжить как `normal` без кросс-CLI или прервать полировку. Не заменяй кросс-CLI четвёртым локальным субагентом.

Прочитай ответ соседнего CLI и дальше оцени его вместе с тремя агентами. Файл `${PLAN_FILE%.md}_strict_cli_review.md` можно создать и обновлять в `strict`; это единственный вспомогательный файл, кроме самого плана, который разрешён в strict-режиме.

### 4. Оценить результаты

Когда все три агента ответили, а в `strict` ещё и соседний CLI, прочитай их замечания и оценки. После этого основной агент выставляет итоговый `$SCORE` по шкале 0–100.

Оцени:
- план следует `docs/rules.md` и `docs/arch.md`;
- план следует применимым карточкам или содержит подтверждённую причину отклонения;
- нет неподтверждённых существенных решений;
- `Целевой алгоритм` описывает сквозное поведение;
- `Контракты реализации` конкретны, особенно БД/API/внешние контракты;
- фазы имеют цель, шаги, результат, сценарии тестирования и проверку;
- каждая фаза связна и выполнима одним агентом за один проход;
- `test_strategy` и `logging_strategy` отражены в фазах и разделах;
- нет альтернатив вида «выбрать», «решить», «уточнить позже»;
- план можно передать в `eda-plan-execute` без нового исследования.

Если `$SCORE >= threshold`, не вноси содержательные правки ради формы. Только добавь или обнови:

```markdown
## Оценка plan-polish
- **Итоговая оценка:** <score>/100
- **Порог:** <threshold>/100
- **Итерации:** <N>
- **Модели:** <фактически запущенные модели и соседний CLI в strict>
- **Режим:** <normal | strict>
- **Решение:** план готов к исполнению.
```

На этом остановись.

### 5. Отредактировать план

Если `$SCORE < threshold`, сгруппируй замечания:
- **Принять** — подтверждено планом, правилами, архитектурой, research или кодом и улучшает исполнимость без новой развилки.
- **Отклонить** — противоречит контексту, дублирует уже закрытое, расширяет задачу или требует неподтверждённого решения.
- **Спросить** — полезно, но требует выбора пользователя или меняет подтверждённое решение.

Если есть вопросы класса **Спросить**, задай один сгруппированный `AskUserQuestion` и не редактируй план до ответа. Если предложение можно безопасно отклонить как расширение задачи, отклони его и продолжай.

Принятые замечания встраивай в основные разделы плана. Журнал в конце держи коротким:

```markdown
## Изменения после plan-polish

### Итерация <N>
- **Оценка после проверки:** <score>/100
- **Модели:** <фактически запущенные модели и соседний CLI в strict>
- **+ Добавлено:** <3–7 главных изменений>
- **~ Уточнено:** <1–5 важных уточнений>
- **− Убрано:** <если удалено>
- **Отклонено:** <существенные отклонённые предложения и причина>
- **Вопросы пользователя:** <если были, кратко решение>
```

В `meta_reviewers`, если поле есть, добавь фактически запущенные модели и имя соседнего CLI в `strict`. Если `status: draft` и открытых вопросов не осталось, поменяй на `status: meta-reviewed`; `meta-reviewed` и `reviewed` не понижай.

### 6. Продолжить или остановиться

После правок обнови:

```markdown
## Оценка plan-polish
- **Итоговая оценка:** <score>/100
- **Порог:** <threshold>/100
- **Итерации:** <N>
- **Модели:** <фактически запущенные модели и соседний CLI в strict>
- **Режим:** <normal | strict>
- **Решение:** <готов к исполнению | нужен следующий круг | blocked | достигнут лимит>
```

Если оценка ниже порога и лимит не достигнут, запускай новую итерацию с тремя агентами. Если оценка не выросла два круга подряд — остановись `blocked: score не растёт`. Если лимит достигнут — остановись и явно скажи, что порог не достигнут.

## Финал

Сообщи кратко: режим (`normal` или `strict`), путь к плану, путь к strict-review-файлу при наличии, итоговую оценку и порог, число итераций, какие модели и CLI запускались, главные принятые изменения, существенные отклонения, причину остановки и следующий шаг `eda-plan-execute <PLAN_FILE>` при успехе. Если режим был обычный — добавь строку «кросс-CLI не запускался; для проверки соседним агентом — `eda-plan-polish strict <PLAN_FILE>`».

## Чего НЕ делать

- Создавать новый план вместо полировки существующего.
- Править код, миграции, конфиги, lock-файлы или зависимости.
- Запускать любые проверки проекта, тесты, линтеры, билды, typecheck, dev-серверы, миграции, браузерные проверки или API-запросы.
- Ставить предварительную оценку без трёх агентных проверок.
- Запускать агентов последовательно или давать им разные промпты.
- Запускать все три прохода на одной модели.
- Пропускать кросс-CLI молча в `strict`.
- Вставлять предложения агентов без анализа.
- Добавлять существенные решения без подтверждения пользователя.
- Превращать план в длинный отчёт о ревью.
- Коммитить, пушить или запускать `eda-plan-execute`.

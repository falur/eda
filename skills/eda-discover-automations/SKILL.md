# Скил: Поиск автоматизаций (eda-discover-automations)

Читаешь историю ревью и фиксов, находишь ошибки, ручные правки и недостающие проверки, которые полезно предотвращать автоматически.

## Режим запуска

Прочитай `docs/settings.yaml`, если файл есть. Прямое указание пользователя в текущем сообщении важнее настроек.

Поддерживается только `version: 2`. При другой версии, отсутствующем разделе или неизвестном значении используй дефолт; настройки старого формата не применяй. Дефолт: `discover-automations.include_plans: false`.

Если актуального раздела `discover-automations` нет, но есть прежний раздел `automate`, используй `automate.include_plans` как совместимый fallback и сообщи, что настройку следует переименовать. Если присутствуют оба раздела, применяй только `discover-automations`.

| Настройка | Значения | Аргументы в сообщении |
|---|---|---|
| `discover-automations.include_plans` | `true`, `false` | `plans`, «с планами»; выключение: `normal`, «без планов» |

Обычный режим анализирует текущий проект и, если они есть, `docs/reviews/`, `docs/review-fixes/`, `docs/fixes/`. Режим `discover-automations.include_plans: true` добавляет `docs/plans/`. Отсутствие истории не отменяет полный аудит текущих проверок.

## Вход из сообщения пользователя

Текст рядом с вызовом скилла в текущем сообщении пользователя — главный вход. Сначала разбери именно его: тему, задачу, путь к файлу, режим, ограничения и прямые указания.

Если этого входа достаточно, продолжай без вопроса. `AskUserQuestion` задавай только если входа нет, он противоречивый, найдено несколько равных вариантов или есть риск выполнить не ту задачу. Старое обсуждение в истории не считай входом, если пользователь не связал его с текущим вызовом явно.

## Общие ограничения

1. **Не внедряешь изменения.** Только отчёт с предложениями. Внедрение автоматизаций, MCP-серверов, новых скилов или правок `docs/rules.md`/`docs/arch.md` — через `eda-plan` + `eda-plan-execute`.
2. **Повторяемость — сигнал, а не обязательное условие.** Единичную ошибку тоже предлагай закрыть, если у неё высокий ущерб, она может повториться, а проверка будет надёжной и оправданной по стоимости. Не автоматизируй малозначимые замечания только ради полноты отчёта.
3. **Полнота каталога обязательна.** Не вводи лимит количества предложений и не останавливайся на привычном наборе `lint + unit`. Проверь каждую группу, поставь статус `покрыто` / `предложено` / `не применимо`; для `не применимо` запиши конкретную причину.
4. **Детерминированная проверка приоритетнее AI/MCP.** MCP и агентные проверки дополняют CLI/CI только там, где нужен браузер, внешняя система или контекст, недоступный локальному инструменту.

## Интерактивные вопросы

Когда инструкция говорит `AskUserQuestion`, это означает блокирующий интерактивный вопрос.
- Claude Code: используй `AskUserQuestion`.
- Codex interactive: если доступен `request_user_input`, используй его. Если tool недоступен, задай один короткий вопрос в чат, дай варианты 1–3, напиши «Ответь номером или своим вариантом. Я продолжу только после ответа.» и остановись.
- Codex exec / неинтерактивный запуск: не задавай вопросы и не пытайся читать stdin. Если без ответа нельзя безопасно продолжать, заверши работу со статусом `blocked: нужен ответ пользователя`, перечисли вопросы и варианты, не выполняй рискованные действия.
- Не запускай команды, которые ждут интерактивного ввода в терминале; перед такими командами спроси в хост-интерфейсе или остановись с `blocked`.

## Этапы

### 1. Выбрать диапазон
Определи режим и диапазон по текущему сообщению и `docs/settings.yaml`. Без вопроса используй вход, если он задаёт `plans` / `normal`, последние N, период или конкретные файлы/папки. Если диапазон не указан, но источники есть, используй все ревью + фиксы по ревью + обычные фиксы по умолчанию.

Если вход неоднозначен — `AskUserQuestion`: все ревью и фиксы / все ревью, фиксы и планы / последние N / период / конкретные файлы.

Получи список файлов из `docs/reviews/`, `docs/review-fixes/` и `docs/fixes/`. В режиме `plans` дополнительно получи список файлов из `docs/plans/`. Отсутствующие или пустые папки отметь в отчёте, но не блокируйся: проведи baseline gap-аудит по коду, manifest-файлам, конфигам, scripts и CI текущего проекта.

### 2. Прочитать контекст
- Все выбранные ревью, отчёты о фиксах по ревью и обычные фиксы.
- В режиме `plans`: все выбранные планы из `docs/plans/`.
- `docs/rules.md`, `docs/arch.md` (если есть) — прочитай и строго следуй им.
- Какие языки и фреймворки в проекте — определи сам.
- Какие инструменты качества уже установлены и работают: линтеры, форматтеры, статанализаторы, typecheck, все виды тестов, coverage, архитектурные проверки, валидаторы конфигов, security/supply-chain сканеры, performance budgets, pre-commit, CI, release/post-deploy проверки и npm/composer/make-скрипты.
- Какие агентные усиления уже есть: `.claude/skills/`, `.codex/skills/`, MCP-конфиги, локальные скилы, команды для ревью/планирования. Не предлагай дубль уже установленному.

### 3. Найти кандидатов на автоматизацию
Сгруппируй замечания по сути, затем независимо от истории пройди экстремальный каталог:

1. **Тесты поведения:** unit, integration, component, contract/consumer-driven contract, API, e2e, smoke, acceptance, regression, negative и edge-case.
2. **Глубокое тестирование:** property-based, mutation, fuzz, differential, metamorphic, snapshot/golden, repeatability и flaky-test detection.
3. **UI и браузер:** browser e2e, visual regression, accessibility, keyboard/focus, responsive, cross-browser/device, hydration, broken links, формы/uploads, locale/timezone и browser-console errors.
4. **Стиль и качество:** formatter, linter, naming, complexity, duplication, dead code, unused exports/dependencies, forbidden patterns, TODO/FIXME policy и лимиты размера.
5. **Статический анализ:** typecheck, nullability, data-flow/taint, API misuse, unreachable code, unsafe/undefined behavior, memory/thread/address sanitizers и анализаторы выбранного языка.
6. **Границы кода:** forbidden imports, dependency direction, cycles, layers, public API, ownership, package/module boundaries, generated-code boundaries и architecture fitness functions.
7. **Конфиги и инфраструктура:** schema/parse для env, YAML/JSON/TOML, CI, Docker/Compose, Kubernetes/Helm, Terraform/IaC, proxy, feature flags, IAM, observability и env-example drift.
8. **API и совместимость:** OpenAPI/GraphQL/Proto, breaking changes, generated-code drift, serialization, backward/forward compatibility, idempotency, pagination/filter/sort.
9. **БД и данные:** migration lint/forward/rollback/dry-run, schema drift, constraints, fixtures, transactions, concurrency, query plans/N+1, backup/restore, retention/anonymization и data invariants.
10. **Безопасность и supply chain:** secrets, SAST, DAST, dependency/container/IaC scan, licenses, SBOM, lockfile integrity, provenance/signatures, authn/authz negative tests, injection, XSS/CSRF/SSRF, CORS/CSP/headers, rate limits и PII leakage.
11. **Производительность и надёжность:** benchmarks/budgets, bundle size, load/stress/spike/soak, leaks, startup, timeouts/retries/circuit breakers, graceful shutdown, fault injection/chaos и recovery.
12. **Сборка и релиз:** clean-clone/reproducible build, generated artifacts, package contents, runtime/OS/architecture matrix, install/upgrade/downgrade, semver/changelog, release dry-run, canary/rollback и post-deploy smoke.
13. **Документация:** Markdown/style/spell, links, executable snippets, CLI help/API docs drift, diagrams/schemas и migration/release notes.
14. **Эксплуатация:** health/readiness/liveness, metrics/log/trace schemas, no secrets/PII in logs, alert rules, dashboards as code, SLO/error budgets, disaster recovery и restore drills.
15. **Доменные проверки:** платежи, почта, очереди, jobs, webhooks, поиск, файлы/media, mobile signing, offline/sync, localization, analytics events и другие инварианты продукта.
16. **AI-функции:** prompt/output schemas, evals, prompt injection/jailbreak, data leakage, tool permissions, nondeterminism, latency и token/cost budgets.
17. **MCP:** browser/Playwright MCP для сценариев и визуальных доказательств; MCP для БД, API, документации, GitHub/GitLab, cloud, observability и выбранного языка/фреймворка. Укажи точный сценарий, минимальные права и почему CLI/CI недостаточно.
18. **Агентный процесс и планы:** чтение обязательных источников, формат артефактов, проверка критериев готовности, файлов/модулей и зависимостей задач, rollback/backup для рискованных действий, запрет пропуска команд и повторяющиеся ошибки агентов.

Для каждого паттерна собери: доказательство из истории либо baseline-пробел в текущем проекте, затронутые файлы, возможный ущерб, вероятность, надёжность проверки и стоимость внедрения. Повторяющиеся паттерны обычно приоритетнее, но не отбрасывай сильного кандидата из-за одного случая или потому, что ошибка ещё не произошла.

### 4. Предложить автоматизации и правки docs
Для каждого паттерна выбери одну или несколько недублирующих реакций: `automation`, `tests`, `tooling`, `agent`, `rules`, `architecture`.

**Сначала программная проверка.** Для каждого паттерна сначала оцени автоматизации на уровне языка и тулчейна: можно ли поймать его линтером, статанализатором, typecheck, тестом, pre-commit/CI-скриптом или валидатором. Агентные решения предлагай только если программная проверка невозможна, слишком дорогая или требует лучшего контекста для AI-агента.

Приоритет реакций:
1. `automation` — правило линтера, статанализатора, typecheck, custom validator, pre-commit/CI/check-скрипт.
2. `tests` — конкретный unit/integration/contract/e2e/regression-тест или тестовый helper, который ловит этот класс багов.
3. `tooling` — новый или донастроенный инструмент качества, если в проекте нет подходящего и инструмент стандартный для стека.
4. `agent` — MCP-сервер, новая/обновлённая eda-инструкция, специализированная агентная проверка или обязательный источник контекста. Предлагай только когда это закрывает значимую ошибку AI-процесса или даёт агенту данные, которые нельзя надёжно получить из кода.
5. `rules` / `architecture` — текстовые правила и архитектурные уточнения, если проблема связана с договорённостью, границей модулей или ownership.

Предпочитай уже установленный инструмент, если он ловит этот класс проблем. Новый инструмент предлагай только если он не дублирует инструмент того же класса. Для проблем из планов предлагай проверку `docs/plans/*.md`, а не runtime-линтер кода. Если правило или архитектура уже зафиксированы, не дублируй текст; предложи только уточнение, которое закрывает найденный случай.

Подменять линтер, статанализатор или тест MCP-сервером/скилом нельзя, если ошибку можно надёжно поймать программной проверкой.

Для каждой программной проверки укажи точный инструмент, команду/сценарий и контур: `pre-commit`, `pre-push`, `PR CI`, `nightly`, `release`, `post-deploy`. Быстрые проверки отдели от тяжёлых. Для MCP укажи сервер/класс инструмента, проверяемый сценарий, минимальные права, тестовые данные и контур `MCP/manual`; MCP не называй автоматической CI-проверкой, если он реально не запускается без участия агента.

### 6. Финал
Короткое сообщение: путь к отчёту, сколько групп каталога покрыто/предложено/неприменимо, общее число предложений и их распределение по контурам, сколько MCP/агентных усилений и правок docs, топ-3 рекомендации простыми словами, подсказка дальше — «хочешь внедрить → `eda-plan` для плана, потом `eda-plan-execute`».

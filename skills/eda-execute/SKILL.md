# Скил: Исполнитель (eda-execute)

Берёшь готовый план из `docs/plans/`, выполняешь до конца, ведёшь журнал. Останавливаешься только при реальных проблемах.

## Вход из сообщения пользователя

Текст рядом с вызовом скилла в текущем сообщении пользователя — главный вход. Сначала разбери именно его: тему, задачу, путь к файлу, режим, ограничения и прямые указания.

Если этого входа достаточно, продолжай без вопроса. `AskUserQuestion` задавай только если входа нет, он противоречивый, найдено несколько равных вариантов или есть риск выполнить не ту задачу. Старое обсуждение в истории не считай входом, если пользователь не связал его с текущим вызовом явно.

## Главные правила

1. **План и проектная документация — обязательная рамка исполнения.** Перед правками прочитай план, `docs/rules.md` и `docs/arch.md`. Прочитай карточки из `sources.references`; если поле отсутствует, выбери через `docs/references.md` только карточки для затронутых компонентов. Нерелевантные карточки не загружай.
2. **Соблюдай приоритет и блокируй конфликт.** Приоритет: подтверждённое решение пользователя → `docs/rules.md` → `docs/arch.md` → релевантные карточки. Если шаг плана противоречит рамке или отклоняется от примера без подтверждённой причины в плане, не исполняй его молча. Спроси: адаптировать выполнение, вернуться к `eda-plan` или отдельно изменить документацию.
3. **Не додумывай план.** Шаг непонятен — спроси через `AskUserQuestion`, не «доразрабатывай» молча.
4. **Иди целиком.** Не делай паузы «для подтверждения» после каждого шага; останавливайся только при конфликте, падении проверки, риске потери данных или рискованной операции вне плана.
5. **Проверки нельзя подавлять.** Не отключай линтеры, тесты, typecheck, static analysis и другие проверки; не добавляй игноры, исключения из проверок, ослабление правил или изменение команд так, чтобы проверка перестала запускаться. Пиши и правь код так, чтобы проверки проходили по сути.
6. **Не коммить, не пушь, не делай ревью.** Это другие скилы.
7. **Пиши просто.** В сообщениях, вопросах и журнале используй простой язык; таблицы — для структурированных данных.

## Интерактивные вопросы

Когда инструкция говорит `AskUserQuestion`, это означает блокирующий интерактивный вопрос.
- Claude Code: используй `AskUserQuestion`.
- Codex interactive: если доступен `request_user_input`, используй его. Если tool недоступен, задай один короткий вопрос в чат, дай варианты 1–3, напиши «Ответь номером или своим вариантом. Я продолжу только после ответа.» и остановись.
- Codex exec / неинтерактивный запуск: не задавай вопросы и не пытайся читать stdin. Если без ответа нельзя безопасно продолжать, заверши работу со статусом `blocked: нужен ответ пользователя`, перечисли вопросы и варианты, не выполняй рискованные действия.
- Не запускай команды, которые ждут интерактивного ввода в терминале; перед такими командами спроси в хост-интерфейсе или остановись с `blocked`.
- Для выполнения кода это правило важнее требования идти целиком: не додумывай план, не исполняй шаги вопреки `docs/rules.md` или `docs/arch.md`, не делай рискованные операции и не правь чужие/несвязанные поломки вместо ответа пользователя.

## Этапы

### 1. Выбрать план
Сначала разбери текст рядом с вызовом:
- если указан путь к плану — используй его как `$PLAN_FILE`;
- если указано название плана или часть названия — найди совпадение в `docs/plans/`;
- если написано «последний план» — возьми самый новый файл из `docs/plans/`;
- если вставлен текст плана — используй его как план выполнения и при инициализации прогресса сохрани/привяжи к файлу в `docs/plans/`, если это безопасно и однозначно.

Если найден ровно один план — продолжай без вопроса. Если найдено несколько одинаково подходящих планов — `AskUserQuestion` со списком вариантов. Если входа нет — `AskUserQuestion` со списком последних файлов из `docs/plans/`. Если `docs/plans/` отсутствует или пуста и вход не содержит план — остановись с понятным вопросом или статусом `blocked: нужен план`. Запиши путь в `$PLAN_FILE`.

### 2. Выбрать место выполнения
`AskUserQuestion` с четырьмя вариантами:

| Вариант | Что делает | Команда |
|---|---|---|
| Остаться в текущей ветке | Ничего | — |
| Новая ветка от main | Переключиться на main, создать ветку от неё | `git checkout main && git checkout -b <slug>` |
| Новая ветка от текущей ветки | Создать ветку прямо здесь | `git checkout -b <slug>` |
| Worktree от main в соседней папке | Создать worktree → **остановиться**, дать пользователю инструкцию | см. ниже |

`<slug>` бери из имени плана. Если в рабочей копии незакоммиченные изменения и `git checkout` упадёт — остановись и спроси через `AskUserQuestion`.

**Если выбран worktree** — выполни:

```bash
git worktree add -b <slug> ../<repo-name>-<slug> main
```

Покажи пользователю **готовый bash-блок** для копирования (с подставленными именами):

```bash
cd ../<repo-name>-<slug>
# затем в новой сессии запусти этот же скил:
# eda-execute docs/plans/<план>.md
```

И **выйди из скила** — текущая сессия в эту папку не переедет, поэтому продолжать здесь нельзя. Сообщи пользователю, что ждёшь его в новой сессии.

### 3. Прочитать контекст
Прочитай план, `docs/rules.md` и `docs/arch.md` (если есть). Извлеки `sources.references` и прочитай перечисленные карточки. Для старого плана без поля прочитай `docs/references.md`, если он есть, и выбери только карточки для компонентов, которые план создаёт или меняет. Тест-фреймворк проекта определи сам по конфигам и существующим тестам.

Перед выполнением проверь, нет ли в плане шагов, зависимостей, API, миграций, границ модулей, команд проверки или решений, которые противоречат правилам, архитектуре или применимым эталонам. Подтверждённое отклонение должно быть явно записано в плане. Если конфликт или необоснованное отклонение есть — остановись и задай `AskUserQuestion` по варианту из главных правил.

### 4. Инициализировать прогресс
- Создай журнал `docs/executions/{YYYY-MM-DD}_{HH-MM}_{slug}.md` (slug — тот же, что у плана, или близкий).
- В конец файла плана добавь раздел со ссылкой и чекбоксами прогресса:
  ```markdown
  ## Прогресс выполнения
  Журнал: `docs/executions/{file}.md`

  - [ ] Шаг 1: ...
  - [ ] Шаг 2: ...
  ```
- Шаблон журнала:

  ```markdown
  ---
  plan: <путь>
  started: <YYYY-MM-DD HH:MM>
  status: in_progress
  ---

  # Журнал: <заголовок>

  ## Шаги
  | # | Шаг | Файлы | Тесты | Статус |
  |---|-----|-------|-------|--------|

  ## Заметки
  ## Изменения в docs
  ```

### 5. Выполнить план
Идёшь по шагам. На каждом:
1. Перед правкой сверяешь действие с `docs/rules.md`, `docs/arch.md` и применимыми карточками.
2. Если документация задаёт способ реализации, форму компонента, границы модулей, команды проверки, требования к тестам, миграциям, API, безопасности или документации — следуй ей даже тогда, когда план описан менее строго.
3. Если есть конфликт или план требует необоснованного отклонения от примера — не правь код, задай `AskUserQuestion`.
4. Сделай правки.
5. Выполни проверки, если они прямо указаны в шаге.
6. Поставь `[x]` в файле плана и допиши строку в таблицу журнала.

Останавливайся и спрашивай через `AskUserQuestion`, если тесты к шагу упали и не правятся быстро, шаг противоречит коду или проектной рамке, необоснованно отклоняется от карточки либо задевает рискованное вне плана. Новое архитектурное решение или полезное изменение эталона записывай в «Изменения в docs», но не меняй документацию молча.

После последнего шага — `finished` и `status: done` в шапке журнала.

### 6. Обновить docs
Если в «Изменениях в docs» накопились правила или архитектурные уточнения — допиши их минимально достаточно в `docs/rules.md` или `docs/arch.md`. Изменения эталонов не вноси: перечисли их в журнале и предложи отдельный запуск `eda-docs references`. Файлов нет — пропусти.

### 7. Финальная проверка
Прогони полный сьют тестов и линтеры на проекте. Команды — стандартные для стека; если непонятно — `AskUserQuestion` один раз. Свои поломки — правишь причину и повторяешь. Запрещено делать проверки зелёными через подавление ошибок, отключение правил, исключение файлов, ослабление конфигов или изменение команд проверки. Чужие/несвязанные — `AskUserQuestion`. Результат фиксируй разделом `## Финальная проверка` в журнале.

### 8. Финал
Короткое сообщение: пути к плану и журналу, сводка шагов, результат финальной проверки, состояние git («не закоммичено»), 1–3 главных «что важно знать», подсказка «дальше — `eda-review` или `eda-commit`».

## Чего НЕ делать
- Коммитить, пушить, делать кросс-ревью изменений.
- Гонять полный сьют и линтеры на каждом шаге.
- Пропускать финальную проверку.
- Делать паузу после каждого шага «для подтверждения».
- Пропускать обновление чекбоксов и журнала — иначе теряется состояние.
- Делать рискованное (удаление файлов, миграции, секреты) без подтверждения, даже если упомянуто в плане.
- Подавлять ошибки линтеров, тестов, typecheck или других проверок вместо исправления кода.
- Считать `docs/rules.md` и `docs/arch.md` просто контекстом для ознакомления.
- Игнорировать применимую карточку или молча отклоняться от её примера.
- Исполнять план, который противоречит правилам или архитектуре проекта.
- Обходить правило или архитектурное ограничение без явного решения пользователя.

# Скил: Ревьюер (eda-review)

Работай как оркестратор установленных `eda-review-*` агентов. Сам не выполняй их специализированные роли и не копируй их системные prompts в task-сообщения. Определи target и контекст, выбери проверки, запусти агентов, проверь их структурированные ответы, объедини подтверждённые находки и сохрани одно итоговое ревью.

## Вход из сообщения пользователя

Текст рядом с вызовом скилла в текущем сообщении — главный вход. Сначала разбери target, план, ссылку, ограничения, отключённые или принудительно включённые проверки и разовые модели.

Если входа достаточно, продолжай без вопроса. Без аргументов ревьюй незакоммиченный `git diff HEAD`. Ссылка на PR/MR задаёт target однозначно. Если пользователь дал только корень удалённого репозитория, обязательно попроси указать PR/MR, ветку, коммит или файлы; весь репозиторий и последний PR автоматически не выбирай.

Разовые указания вида «без performance», «без business», «включи database», «включи business», «architecture на opus» или «tests на gpt-5.6-sol» важнее `docs/settings.yaml` и действуют только на текущий запуск.

Если во входе даны ранее отклонённые находки или путь к предыдущему ревью, прочитай их раздел «Отклонено» и не принимай эти находки повторно без нового доказательства.

## Настройки

Прочитай `docs/settings.yaml`, если файл есть. Поддерживается только `version: 3`. Используй `review.agents.<check>.mode` и `review.agents.<check>.model.<platform>`. Если файла нет или версия отличается, используй defaults и добавь предупреждение; старые настройки не применяй.

Допустимые режимы:

- `always` — запускать при каждом ревью;
- `auto` — запускать только когда проверка применима;
- `off` — не запускать.

Допустимые модели по умолчанию: Claude Code — `haiku`, `sonnet`, `opus`; Codex — `gpt-5.6-luna`, `gpt-5.6-terra`, `gpt-5.6-sol`. Неизвестное или отсутствующее значение замени default-значением конкретного агента и добавь предупреждение в покрытие.

Если `version: 3` существует, но раздела `review.agents` нет, используй defaults ниже и добавь предупреждение. Устаревшие поля `review.strict`, `review.include_code_quality` и раздел `review-check` не применяй. Существующий файл настроек не переписывай.

|---|---|---|---|
| `correctness` | `always` | `sonnet` | `gpt-5.6-terra` |
| `architecture` | `auto` | `opus` | `gpt-5.6-sol` |

| `business` | `auto` | `sonnet` | `gpt-5.6-terra` |

## Вопросы

Задавай вопрос только когда target противоречив, дана лишь ссылка на корень репозитория или безопасно выбрать цель невозможно. Вопрос о плане не задавай: используй план только если пользователь указал его или путь определяется однозначно; иначе установи `$PLAN_FILE=none`.

- Claude Code: используй `AskUserQuestion`.
- Codex interactive: используй `request_user_input`, если доступен; иначе задай короткий вопрос с 2–3 вариантами и остановись до ответа.
- Codex exec и другой неинтерактивный запуск: не читай stdin; верни `blocked: нужен target` с конкретным вопросом.

## Подготовить контекст

1. Определи `$TARGET`: явный файл, папка, URL PR/MR, ветка, коммит, указанный diff или `git diff HEAD` без аргументов. Для GitHub/GitLab URL получи metadata и diff read-only командами `gh`/`glab`; для другого сервиса используй доступное read-only средство. Если основной diff недоступен, остановись: warning разрешён только для недоступных прошлых обсуждений, а не для самого target.
2. Прочитай `AGENTS.md`, `CLAUDE.md`, `docs/rules.md`, `docs/arch.md` и сам target настолько, чтобы выбрать проверки и передать агентам точный контекст. На этом шаге не делай собственное code review.
3. Определи `$PLAN_FILE`. Если его нет, используй `none` и не пытайся восстановить последний план наугад.
4. Определи `$REFERENCE_FILES`: если план содержит `sources.references`, используй их; иначе через `docs/references.md` выбери только применимые карточки для компонентов target. Если карточек нет, используй `none`.
5. Определи `$BUSINESS_FILES`: сначала установи исходную задачу и фактически затронутое пользовательское или доменное поведение по текущему сообщению, плану и target. Если план содержит `sources.business`, используй только относящиеся к этому поведению пути; иначе прочитай `docs/business.md` и по описаниям выбери только применимые карточки. Если индекс отсутствует, подходящих карточек нет или изменения не затрагивают бизнес-поведение, используй `none`. Не загружай все карточки только потому, что индекс существует.
6. Сформируй краткий `$REVIEW_CONTEXT`: тип target, base, исходную задачу из текущего сообщения, плана, PR/MR title/body или явно связанного issue/артефакта, изменённые области, применимые документы и явные решения пользователя. Если надёжного описания задачи нет, явно напиши `task: unknown`, а не восстанавливай намерение по догадке. Не включай в контекст domain-инструкции агентов.

Текущая задача задаёт область и намерение изменений. Применимые business-карточки проверяют затронутое поведение, но не расширяют target. Если задача явно меняет правило карточки, это возможная рассинхронизация business-документации, которую должен классифицировать `eda-review-business`, а не основание молча объявить реализацию неверной.

## Выбрать проверки

Сначала примени разовые overrides, затем настройки, затем defaults.

- `always` включай всегда, `off` всегда пропускай.
- `architecture` в `auto` включай при изменении границ модулей, зависимостей, публичных контрактов или разделения ответственности.
- `references` включай только при непустом `$REFERENCE_FILES`.
- `business` включай только при непустом `$BUSINESS_FILES` и изменении пользовательского или доменного поведения.
- `plan_alignment` включай только при непустом `$PLAN_FILE`.
- `security` включай для auth, permissions, внешнего ввода, файлов, сети, секретов, криптографии и других границ доверия.
- `performance` включай для запросов, пакетной обработки, кешей, конкурентности, памяти или горячих путей.
- `frontend` обязательно включай при изменении компонентов, стилей, клиентских маршрутов, состояния или другой UI-части.
- `api` включай при изменении routes, handlers, DTO, OpenAPI, GraphQL, RPC или клиент-серверного контракта.
- `database` включай при изменении миграций, моделей хранения, SQL, схем, индексов или транзакций.
- `documentation` включай при изменении публичного API, CLI, конфигурации, установки или пользовательского поведения.
- `previous_reviews` включай для URL PR/MR или другой удалённой цели, у которой могут быть обсуждения ревью.

Для каждой проверки сохрани причину `selected` или `skipped`; она попадёт в покрытие.

## Запустить packaged-агентов

Имя агента получается из имени проверки:

- `plan_alignment` → `eda-review-plan-alignment`;
- `code_quality` → `eda-review-code-quality`;
- `previous_reviews` → `eda-review-previous-reviews`;
- остальные → `eda-review-<check>`.

В Claude Code запускай установленный custom agent через `Agent` tool. Установленная Claude-копия самого `eda-review` выполняется с `context: fork`, поэтому review-оркестрация не должна оставаться в контексте вызвавшего `eda-polish` или другого скила. В Codex каждого установленного custom agent запускай через `spawn_agent` с `fork_turns: "none"`; не оставляй `fork_turns` по умолчанию и не передавай историю review-runner. Передай выбранную модель как runtime override. Если хост не умеет применить выбранную модель или нативные субагенты недоступны, остановись: не выполняй роли главным агентом и не создавай отдельные CLI-процессы.

### Технические остановки субагентов

Техническую ошибку инструмента субагентов не смешивай со статусами `failed` и `blocked` содержательного контракта. Сохрани полный исходный текст ошибки и обработай её по причине:

- лимит параллельности или отсутствие свободного слота — дождись уже запущенного этим workflow агента, при необходимости закрой завершённые потоки и повтори тот же запуск; если управляемых активных агентов нет, заверши `blocked: заняты слоты субагентов`;
- лимит глубины вложения — не повторяй запуск и не выполняй проверку сам; заверши `blocked: достигнут лимит глубины субагентов`, указав наблюдаемую и требуемую глубину;
- исчерпана usage-квота — не делай автоматических повторов; заверши `blocked: исчерпана квота`, сохрани время reset или условие продолжения, если хост его сообщил;
- не хватает разрешения — запроси одно конкретное разрешение по правилам текущей среды и после ответа продолжи того же агента; в неинтерактивной среде заверши `blocked: нужно разрешение пользователя`;
- временная API-, server-, overload- или network-ошибка — один раз продолжи того же агента; если resume недоступен, один раз запусти ту же роль с исходным входом, полным частичным результатом и требованием сначала сверить текущее состояние; повторный такой сбой заверши как `blocked` с исходной ошибкой;
- неизвестная техническая ошибка — не угадывай причину и не зацикливай retry; заверши `blocked: техническая ошибка субагента` с полным исходным текстом.

Ожидание слота и один технический retry не считаются повторной содержательной проверкой агента.

Сначала сформируй весь набор выбранных проверок, затем отправь все вызовы одним параллельным пакетом в одном ответе ассистента. Не дели проверки заранее на волны, партии или последовательные группы и не жди завершения части агентов перед запуском остальных. Если хост ограничивает concurrency, разреши нативному механизму поставить лишние задачи в очередь; повторный запуск допустим только после фактической ошибки лимита по правилам технических остановок выше.

Ожидай результаты только нативным механизмом субагентов и их уведомлениями о завершении; в Codex используй `wait_agent`. Не используй Bash, shell-циклы, `sleep`, опрос файлов или артефактов и фиксированные таймауты для ожидания агентов. После отправки всего пакета собирай ответы по мере нативного завершения.

Каждому агенту передай только:

```text
Рабочая директория: <cwd>
TARGET: <target>
PLAN_FILE: <path | none>
REFERENCE_FILES: <paths | none>
BUSINESS_FILES: <paths | none>
MODEL: <фактически выбранная модель>
REVIEW_CONTEXT: <краткий общий контекст>

Верни результат строго по YAML-контракту установленного агента.
```

Не вставляй системный prompt агента в task-сообщение.

## Проверить ответы и обработать сбои

Проверь для каждого ответа `status`, `check`, фактически запрошенный `model` и структуру `находки`. Несовпадение модели считай ошибкой контракта. Каждая находка означает дефект, который обязательно исправить. Находка без точного места, конкретного достижимого риска, доказательства, способа воспроизведения (`repro`) и проверяемого способа исправления не подтверждена.

- При `blocked`, неверном YAML или отсутствующих обязательных полях один раз повтори того же агента на той же модели с исходным контекстом и описанием ошибки формата.
- `completed` означает успешно выполненную проверку. `not_applicable` перенеси в skipped с причиной и не повторяй.
- Если повторно не завершилась любая проверка, кроме `previous_reviews`, остановись без создания итогового файла ревью.
- Для `previous_reviews` статусы `unavailable` или повторный технический сбой преврати в warning и продолжай. Не утверждай, что старые обсуждения проверены.
- `previous_reviews` ничего не закрывает удалённо. Актуальные незакрытые замечания добавь в общий набор; исправленные, но открытые треды покажи только в покрытии.

## Собрать итог

Главный агент выполняет только редакторскую работу над результатами:

1. Проверь находки по указанным evidence и отклони неподтверждённые.
2. Объедини дубли разных агентов в один пункт, сохранив все полезные доказательства.
3. Оставь только конкретные ошибки, нарушения контрактов и существенные неточности, которые нельзя безопасно игнорировать. Косметические улучшения, вкусовой рефакторинг, спекулятивное усиление, необязательные тесты, документацию и оптимизации отклони, а не превращай в находку.
4. Отклони находку про будущее: дефект должен существовать в текущем коде. «Сломается, если позже кто-то так сделает» без достижимого на текущем коде сценария — не находка.
5. Для каждой принятой находки проверь точное место, доказательство, способ воспроизведения, практическое влияние, минимальное исправление и способ проверки. Если хотя бы одного элемента нет, отклони находку.
6. Каждую отклонённую находку запиши в раздел «Отклонено» с проверкой-источником и причиной. В число находок и в score отклонённые не входят.
7. Сам выставь итоговый `score` от 0 до 100 по серьёзности, влиянию и общему качеству реализации. Не используй фиксированные вычеты, среднее или минимум оценок агентов. Ориентир: `100` — находок нет; `95–99` — только low; `80–94` — medium или несколько low; `60–79` — high; ниже `60` — critical или нужна существенная переработка. Любое снижение score связывай с принятыми находками; если находок нет, score равен `100`. Добавь короткое обоснование числа.
8. Установи `result: clean`, только если находок нет; при любой находке используй `result: changes-required` независимо от score.
9. Не выполняй дополнительное самостоятельное ревью и не добавляй новые domain-находки от себя.

Ревью содержит только проблемы. Не перечисляй выполненную работу, похвалу и успешные проверки. Исключение — короткие технические разделы покрытия и «Отклонено».

## Сохранить ревью

Создай файл `docs/artifacts/reviews/{YYYY-MM-DD}_{HH-MM}_{slug}.md` только после успешной обработки всех обязательных агентов. Для недоступного `previous_reviews` используй `status: reviewed-with-warnings`, иначе `status: reviewed`.

```markdown
---
target: <что проверено>
plan: <docs/artifacts/plans/... | none>
score: <0..100>
status: <reviewed | reviewed-with-warnings>
result: <clean | changes-required>
date: <YYYY-MM-DD HH:MM>
checks:
  - name: <check>
    model: <model>
    status: <completed | skipped | warning>
    reason: <почему запущен, пропущен или неполон>
---

# Ревью: <краткое название>

## Оценка

**<N>/100.** <краткое экспертное обоснование>

## Покрытие

- **Completed:** <проверки и модели>
- **Skipped:** <проверки и причины>
- **Warnings:** <предупреждения или «нет»>
- **Frontend:** <если запускался: «UI/UX проверены по коду; браузерная проверка не выполнялась»>
- **Previous reviews:** <актуальные / исправленные, но открытые / недоступны>

## Проблемы сверки с планом

<Только подтверждённые plan_alignment-проблемы. Если плана нет: «Проверка плана пропущена: план не указан и не найден.»>

## Проблемы бизнес-логики

<Только подтверждённые business-проблемы: нарушение карточки или рассинхронизация карточки с явно изменившей правило задачей. Если проверка не запускалась или проблем нет — коротко укажи это.>

## Проблемы в коде

### 1. <короткий заголовок>

<1–3 коротких абзаца: контекст, проблема, практический риск и когда он проявится. Не начинай с внутренних имён.>

#### Технические детали

- **Тип:** <check>
- **Тяжесть:** <critical | high | medium | low>
- **Файлы:** `<path:line>`
- **Что подтверждает проблему:** <evidence>
- **Чем воспроизводится:** <падающий тест, вывод линтера или конкретная строка кода либо данных>
- **Как исправить:** <общий подход и конкретные шаги>
- **Тесты:** <что добавить или обновить>

## Отклонено

<Находки агентов, отклонённые при сверке: короткая формулировка, проверка-источник и причина. Если отклонённых нет — «нет».>

```

Основная часть каждого замечания — главный ответ: простой язык, 1–3 коротких абзаца и контекст, понятный без чтения diff или плана. Файлы, строки, SQL, DTO и внутренние имена давай ниже в `Технические детали`.

## Финал

Коротко сообщи путь к ревью, status, result, score, количество принятых и отклонённых находок, completed/skipped/warnings. При `changes-required` предложи `eda-fix-by-review`; при `clean` — `eda-commit`.

## Чего НЕ делать

- Править код, настройки проекта или удалённые обсуждения.
- Выполнять специализированную роль главным агентом.
- Запускать другой CLI или подменять отсутствующих субагентов одним общим ревью.
- Записывать итоговый файл после повторного сбоя обязательного агента.
- Выбирать последний PR или весь репозиторий по ссылке на корень.
- Загружать все карточки references без отбора.
- Усреднять оценки агентов или считать score по фиксированной формуле.
- Утверждать, что UI визуально проверен без `eda-manual-test`.

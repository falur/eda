# План реализации

## Задача

Обновить инструкции eda-скиллов так, чтобы агент сначала учитывал текст рядом с вызовом скилла, а вопросы задавал только когда без ответа нельзя безопасно продолжать.

Готовый результат: все скиллы явно знают, что текст пользователя рядом с вызовом — это главный вход. `eda-plan` больше не спрашивает про исследование, если пользователь уже дал задачу или указал research-файл.

## Контекст

Сейчас часть скиллов уже ведёт себя правильно. Например, `eda-fix` принимает короткий текст задачи как вход, а `eda-review` не задаёт вопрос, если цель ревью понятна из запроса или состояния репозитория.

Проблема сильнее всего видна в `eda-plan`: он всегда спрашивает, какое исследование использовать, хотя пользователь может уже передать задачу или путь к research-файлу.

Также похожая проблема есть в скиллах, которые первым шагом выбирают файл или диапазон:

| Скилл | Текущая проблема |
|---|---|
| `eda-plan` | Всегда спрашивает про research. |
| `eda-execute` | Спрашивает план, если путь не передан явно. |
| `eda-fix-by-review` | Спрашивает файл ревью, если путь не передан явно. |
| `eda-send-review` | Спрашивает файл ревью, если путь не передан явно. |
| `eda-automate` | Спрашивает диапазон анализа, даже если он написан в сообщении. |
| `eda-docs` | Спрашивает, какие документы трогать, даже если это указано в сообщении. |

В проекте нет `docs/rules.md` и `docs/arch.md`, поэтому дополнительных проектных правил для этой правки нет.

## Принятые решения

1. Добавить во все скиллы общий раздел `Вход из сообщения пользователя`.
2. Считать текст рядом с вызовом скилла главным входом.
3. Не задавать вопрос, если по тексту пользователя можно безопасно продолжать.
4. Задавать вопрос только если входа нет, вход противоречивый, найдено несколько равных вариантов или есть риск выполнить не ту задачу.
5. Для `eda-plan` убрать обязательный вопрос про research.
6. Для `eda-plan` читать research-файл без вопроса, если путь указан в сообщении пользователя.
7. Не менять runtime-код установщика и CLI: текущая задача меняет только тексты скиллов.
8. Синхронизировать пакетные файлы `docs/skills/*.md` и локальные установленные копии `.codex/skills/*/SKILL.md` и `.claude/skills/*/SKILL.md`, если такие копии есть.
9. Обновить короткое описание в YAML-шапке скиллов, если оно обещает старое поведение.
10. Добавить автоматические тесты на содержание скиллов, чтобы `npm test` ловил возврат старых обязательных вопросов.

## Целевой алгоритм

1. Пользователь вызывает скилл и пишет рядом текст.
2. Скилл сначала разбирает только текст текущего сообщения рядом с вызовом.
3. Если в тексте есть путь к файлу, название артефакта, режим, диапазон, ограничение или сама задача, скилл использует это как вход.
4. Если входа достаточно, скилл продолжает работу без вопроса.
5. Если входа нет или он неоднозначный, скилл задаёт один короткий блокирующий вопрос.
6. Если действие рискованное и по правилам требует подтверждения, скилл всё равно спрашивает подтверждение.
7. Скилл сохраняет результат в свою обычную папку.

Для `eda-plan` целевой поток такой:

1. Пользователь вызывает `eda-plan`.
2. Если рядом есть описание задачи, это становится контекстом плана.
3. Если рядом есть путь к `docs/researches/...`, скилл читает этот файл.
4. Если research не указан, скилл не спрашивает его автоматически.
5. Если текста задачи нет совсем, скилл спрашивает, что нужно планировать.
6. Дальше скилл пишет план в обычном формате и запускает мета-ревью.

## Фазы выполнения

### 1. Добавить общее правило входа во все скиллы

Цель: закрепить единое поведение для всей серии eda.

Что сделать:
- В каждый `docs/skills/eda-*.md` добавить раздел `## Вход из сообщения пользователя`.
- В этот раздел добавить правило: текст рядом с вызовом скилла — главный вход.
- Указать, когда можно задавать вопрос.
- Указать, что речь идёт только о текущем сообщении пользователя, а не о старом обсуждении в истории.
- Повторить правку в соответствующих `.codex/skills/<skill>/SKILL.md` и `.claude/skills/<skill>/SKILL.md`, если файл существует.
- Обновить YAML `description`, если он говорит о question-first поведении.

Результат: у всех скиллов есть общий принцип, и новые инструкции не зависят от памяти агента.

Проверка:
- `rg -n "Вход из сообщения пользователя" docs/skills .codex/skills`
- `rg -n "Вход из сообщения пользователя" .claude/skills`
- В каждом скилле раздел найден один раз в `docs/skills`, `.codex/skills` и `.claude/skills`.

### 2. Исправить `eda-plan`

Цель: убрать лишний вопрос про research и сделать путь из сообщения полноценным входом.

Что сделать:
- В этапе `Подтянуть контекст` заменить обязательный вопрос про research на разбор текста пользователя.
- Описать правила:
  - если есть описание задачи, использовать его как контекст;
  - если есть путь к research-файлу, прочитать его;
  - если пользователь явно просит research, но файл не указал, тогда спросить выбор;
  - если задачи нет совсем, спросить, что планировать.
- Сохранить остальные требования `eda-plan`: простой язык, целевой алгоритм, фазы, проверки, мета-ревью.
- Обновить YAML `description`, чтобы он не создавал впечатление, что research всегда нужно выбирать отдельно.

Результат: вызов вида `eda-plan docs/researches/file.md` больше не приводит к вопросу “какое исследование взять”.

Проверка:
- Прочитать `docs/skills/eda-plan.md` и `.codex/skills/eda-plan/SKILL.md`.
- Убедиться, что старой фразы “Через AskUserQuestion спроси про релевантное исследование” больше нет.
- Убедиться, что описание скилла тоже говорит про использование текста рядом с вызовом.

### 3. Уточнить скиллы, которые выбирают файл или диапазон

Цель: научить эти скиллы использовать текст пользователя вместо немедленного списка вариантов.

Что сделать:
- В `eda-execute` уточнить: если текст содержит путь к плану, название плана, “последний план” или вставленный план, использовать это.
- В `eda-fix-by-review` уточнить: если текст содержит путь к ревью, название, номер замечания или сами замечания, использовать это.
- В `eda-send-review` уточнить: если текст содержит путь к ревью, “последнее ревью”, номер PR или тип отправки, использовать это. Подтверждение для `approve` и `request-changes` оставить обязательным.
- В `eda-automate` уточнить: если текст задаёт `plans`, последние N, период или конкретные файлы, не спрашивать диапазон.
- В `eda-docs` уточнить: если текст указывает `rules`, `arch`, `AGENTS` или “все”, не спрашивать список документов. Вопросы про перезапись существующих файлов оставить.
- Для `eda-execute`, `eda-fix-by-review`, `eda-send-review` и `eda-automate` описать поведение при пустых папках `docs/plans`, `docs/reviews`, `docs/fixes`, `docs/automations`: если вход не найден, остановиться с понятным вопросом или сообщением, а не продолжать с пустым списком.

Результат: скиллы не начинают с выбора файла или диапазона, если пользователь уже написал нужный вход.

Проверка:
- Точечно прочитать изменённые этапы выбора входа.
- Убедиться, что опасные действия всё ещё требуют подтверждения.
- Убедиться, что пустые папки и отсутствие папок описаны как отдельный безопасный случай.

### 4. Уточнить скиллы, которые уже близки к нужному поведению

Цель: не сломать хорошие текущие сценарии, а только закрепить общий принцип.

Что сделать:
- В `eda-research` явно написать: текст рядом с вызовом — тема исследования; если темы нет, спросить тему.
- В `eda-research` убрать обязательное “не уходи дальше, пока цель не подтверждена” для случаев, где тема и цель уже понятны из текста.
- В `eda-fix` оставить текущую поддержку текстового контекста и добавить общий раздел входа.
- В `eda-review` оставить текущую авто-логику выбора цели и добавить общий раздел входа.
- В `eda-commit` добавить, что текст пользователя может задавать файлы, сообщение коммита или намерение push.
- Для `eda-commit` явно зафиксировать: inline `push` — это намерение, но не обход обязательного вопроса после коммита; merge, force-push и спорные файлы всё равно требуют подтверждения по правилам.

Результат: поведение этих скиллов становится явно описанным, но не меняется радикально.

Проверка:
- Убедиться, что `eda-fix` всё ещё содержит правило “если передан текст — используй его как контекст”.
- Убедиться, что `eda-review` всё ещё не задаёт вопрос, если цель понятна.
- Убедиться, что `eda-commit` не получает разрешение на опасные действия без подтверждения.

## Тесты

| Сценарий | Проверка |
|---|---|
| `eda-plan docs/researches/file.md` | В инструкции нет обязательного вопроса про выбор research. |
| `eda-plan <описание задачи>` | Инструкция говорит использовать описание как контекст плана. |
| `eda-execute последний план по оплате` | Инструкция разрешает искать план по тексту и спрашивать только при нескольких кандидатах. |
| `eda-fix-by-review замечания 1,3 из последнего ревью` | Инструкция не требует сразу показывать список ревью. |
| `eda-send-review последнее ревью в PR 12 как comment` | Инструкция использует PR и тип отправки из текста. |
| `eda-automate plans последние 10` | Инструкция использует режим и диапазон из текста. |
| `eda-docs обнови только AGENTS.md` | Инструкция не спрашивает список документов. |
| `eda-commit только docs/skills/eda-plan.md и push` | Инструкция учитывает файлы и push, но сохраняет проверки безопасности. |
| Входа нет | Скилл задаёт один блокирующий вопрос или завершает `blocked` в неинтерактивном режиме. |
| Найдено несколько одинаково подходящих файлов | Скилл задаёт один блокирующий вопрос со списком вариантов. |
| Нет папки `docs/reviews` или она пустая | Скиллы, которым нужно ревью, не продолжают с пустым входом. |
| Опасное действие указано inline | Скилл всё равно требует подтверждение, если это предусмотрено правилами. |

## Документация и эксплуатация

README менять не обязательно: изменение касается поведения внутри скиллов, а не установки или списка команд.

Если после правок будет публикация npm, нужно поднять patch-версию пакета и опубликовать новую версию.

## Риски

| Риск | Как снизить |
|---|---|
| Скилл начнёт выполнять задачу по слишком расплывчатому тексту. | В общем правиле оставить явное условие: если вход неоднозначен, спросить. |
| Скилл пропустит полезный research-файл. | В `eda-plan` читать research, если он явно указан или пользователь явно просит research. |
| Опасные действия начнут выполняться без подтверждения. | В каждом скилле сохранить специальные подтверждения: approve/request-changes, merge, force-push, перезапись docs, рискованные правки. |
| Пакетные и локальные копии скиллов разойдутся. | В фазе проверки сравнить `docs/skills`, `.codex/skills` и `.claude/skills`. |
| Тесты останутся зелёными при плохих prompt-правках. | Добавить content-тесты на обязательный раздел и отсутствие старых blocking-фраз. |

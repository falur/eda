# Миграция eda

Версия 3.0 перенесла все рабочие результаты скилов в `docs/artifacts/`; постоянная документация проекта остаётся непосредственно в `docs/`. Версия 3.1 дополнительно переработала проверку плана, ревью кода и циклы полировки. Версия 3.2 обновила commit-flow и расположение проектных Codex-скиллов. В npm 3.0 не публиковалась, поэтому переход с 2.x выполняется сразу на актуальную версию 3.x.

## Переход на 4.0

4.0 ломает обратную совместимость настроек ревью и формата плана:

- **Проверки `eda-review` выбирает агент.** Режимов `always` / `auto` / `off` больше нет: в `subagents` первым запускается `eda-review-triage` и по содержимому ревью выбирает нужные проверки, в `main` выбор делает основной агент.
- **Модель роли — одна строка для всех сред.** `review.agents.<role>` принимает `default` или `provider/model#variant`, например `security: anthropic/claude-opus-5-5#high`. Если среда не может запустить модель, роль выполняется на модели установленного агента с warning в ревью.
- **Старые значения не переносятся.** `eda update` и `eda update-all` ставят `default` всем ролям `review.agents`, включая вручную выбранные модели, и переписывают `docs/settings.yaml`; остальные настройки сохраняются. Нужные модели впишите заново вручную. Вопросов о проверках установщик больше не задаёт.
- **Новые роли ревью:** `eda-review-triage`, `eda-review-infra` и `eda-review-seo`.
- **`eda-plan` больше не полирует план.** Настройки `plan.review` нет, флага `без ревью плана` тоже: полировку делает `eda-plan-polish` отдельно или этапом `eda-orhestra`. `eda update` удаляет `plan.review` из конфига.
- **Новые значения по умолчанию** для новых и неполных конфигов: `plan.test_strategy: phase_tests_final_checks`, `plan.logging_strategy: standard`, `plan-polish.limit: 5`, `plan-execute.mode: main`, `review.execution: main`, `send-review.close_previous_reviews: true`. Уже заданные значения сохраняются.
- **Новый формат плана.** У плана появился раздел `Рамка`: по строке на каждое применимое требование правил, архитектуры, эталонов, бизнес-карточек и `AGENTS.md`. `Целевой алгоритм` пишется сценариями из нумерованных шагов в порядке выполнения, таблица событий больше не используется. В `Данных и БД` у каждой таблицы своя таблица колонок, в `Принятых решениях` записан каждый ответ пользователя, у фазы может быть поле `Согласование`. `sources.rules` и `sources.arch` — списки. Старые планы `eda-plan-execute` выполняет, выбирая карточки по индексам, но новые проверки плана ждут `Рамку`.
- **`eda-plan-execute` сверяет каждую фазу с рамкой.** Исполнитель и независимый проверяющий проходят изменения по каждому пункту `Рамки` и `Принятых решений`; нарушение не даёт закрыть фазу.
- **Структура рамки проекта.** `docs/rules.md` и `docs/arch.md` — короткие индексы с таблицами карточек областей в `docs/rules/` и `docs/arch/`. Любой файл рамки, включая карточки business и references, не больше 20 КБ, без датированных разделов и журналов изменений. Чтобы перестроить существующие документы, запустите `eda-prepare-ai`; бизнес-карточки больше 20 КБ делит на подтемы `eda-business`.
- **Адаптер Codex.** Codex-копии скилов и агентов требуют дочитывать обрезанный вывод команд и читать документы рамки и план целиком.
- **Чек-листы ревью в одном месте.** Чек-лист каждой проверки `eda-review` лежит в `skills/eda-review/references/checks/<проверка>.md`: его читает `main`, а установщик встраивает в агента. `references/review-matrix.md` удалён, `eda update` убирает его из установленных копий. Проверки стали конкретнее: тихие сбои и гонки, доступ к чужим объектам, SSRF и prompt injection, совместимость API для старых клиентов, миграции без простоя, вес CSS и JS, сжатие и кеш статики, production-настройки. У находок общие уровни серьёзности.
- **Чек-лист плана — 22 пункта.** Новые пункты: ошибки и восстановление в шагах с внешними вызовами и изменением данных, тест на каждую ветку и ошибку алгоритма, одинаковые имена во всех разделах, удаляемое и переименованное поведение. Старый план может получить по ним `fail`: `eda-plan-review-fix` закроет их, но за один проход план растёт не больше чем на 3%.
- **Вопросы — раундами с рекомендацией.** `eda-plan`, `eda-explore`, `eda-business`, `eda-new-project` и `eda-prepare-ai` задают сразу все вопросы, предпосылки которых закрыты, и ставят рекомендованный вариант первым. Правило лежит в `skills/_shared/questions.md` и подключается строкой `<!-- include: … -->` при установке.
- **«Готово» — только с доказательством.** `eda-plan-execute`, `eda-fix`, `eda-fix-by-review`, `eda-just-do-it`, `eda-polish` и агенты `eda-aim` подтверждают результат выводом команды из текущего запуска; исправление ошибки — исчезновением исходного симптома; после трёх неудачных попыток останавливаются.
- **Новый скил `eda-prod-check`.** Read-only диагностика работающего прода или стейджа: замер симптома, проход по слоям снаружи внутрь, отчёт в `docs/artifacts/prod-checks/` с причинами и исправлениями.
- **Установщик спрашивает меньше.** Вопросы построены на `@clack/prompts`, идут по ходу работы и касаются только основных настроек; редкие меняются вручную в `docs/settings.yaml`, разделы которого теперь тоже идут по ходу работы.

## Обновление

```bash
npm install -g @gian-tiaga/eda@3
eda --version
eda update
```

Версия CLI должна начинаться с `3.2`. После обновления перезапусти Claude Code или Codex CLI, чтобы среда перечитала новые скилы и агентов.

Для нескольких проектов:

```bash
eda update-all /path/to/projects
```

`eda init` устанавливает новую версию компонентов, но не переносит старые артефакты. Для существующего проекта используй `eda update`.

## Новое расположение Codex-скиллов

Проектные скиллы Codex устанавливаются в `.agents/skills/<skill>/SKILL.md`. Агенты и manifest владения остаются соответственно в `.codex/agents/` и `.codex/eda-manifest.json`.

При `eda update` и `eda update-all` актуальные скиллы записываются в `.agents/skills/`, а известные принадлежащие `eda` копии из старых форматов `.codex/skills/<skill>/` и `.codex/skills/<skill>.md` удаляются. Чужие скиллы в старом каталоге не изменяются.

Из управляемых eda файлов в корне `docs/` остаются постоянные документы:

## Автоматический перенос

`eda update` и `eda update-all` перед обновлением настроек и компонентов рекурсивно объединяют каждый старый каталог с соответствующим каталогом в `docs/artifacts/`.

- Неконфликтующие файлы и вложенные каталоги перемещаются.
- Если одинаковый относительный путь уже существует в `docs/artifacts/`, новый объект сохраняется, а старый удаляется.
- Содержимое файлов не переписывается, поэтому SHA-256 планов и ревью не меняется.
- Старые пути, записанные внутри исторических Markdown-файлов, остаются текстом как есть и могут больше не открываться.
- Неизвестные пользовательские файлы и каталоги в `docs/` не переносятся и не удаляются.
- Повторный запуск безопасен: при отсутствии старых каталогов перенос ничего не меняет.

После обновления скилы работают только с путями внутри `docs/artifacts/`. Fallback на старые каталоги и path aliases не поддерживаются.

## Настройки

Версия npm-пакета и версия схемы настроек независимы: в eda 3.3 актуальным остаётся `docs/settings.yaml` с `version: 3`.

Установщик по-прежнему сохраняет полный валидный v3 как есть — кроме двух случаев: если в файле остались устаревшие ключи или если текст файла отстал от шаблона пакета. Тогда он перезаписывает файл без вопросов, сохраняет значения и печатает, что сделал. Старый, неизвестный или неполный YAML нормализуется: известные валидные значения переносятся, а отсутствующие спрашиваются в TTY или получают defaults без TTY.

В `eda update-all` режим `configure` один раз спрашивает общий профиль v3 и записывает его во все проекты. Режим `skip` сохраняет актуальный полный v3, перерисовывает устаревший по шаблону, индивидуально переносит остальные конфиги и создаёт defaults только при отсутствии файла.

## Ревью и полировка

Что в 3.x изменится в уже настроенном проекте:

- **Удалены двенадцать агентов `eda-plan-review-*`.** Проверку плана целиком выполняет один субагент по фиксированному чек-листу. `eda update` стирает файлы этих агентов из `.claude/agents/` и `.codex/agents/`.
- **Секция `plan-review.agents` больше не читается.** Начиная с 3.1.1 `eda update` находит её в готовом файле настроек и убирает вместе с другими устаревшими ключами — `review-check`, `review.strict`, `review.include_code_quality`. Дефолт `plan-review.threshold` — `100`, `plan-polish.limit` — `1`: с 3.9.0 лимит считает итерации «проверка + исправление», а не review-проходы, поэтому сохранённое значение `2` теперь означает два круга правок вместо одного.
- **Режим `single` переименован в `main`.** `eda update` переносит `review.execution: single` и `plan-execute.mode: single` в `main`, а `orhestra.execution: single` и `single_propagated` — в `main` и `main_propagated`. В `main` работу выполняет основной агент без субагентов; модели отдельных `review.agents` не применяются.
- **У `eda-review` есть режим исполнения.** `review.execution` принимает `subagents` или `main`; default `subagents` сохраняет прежнее поведение. Безусловный Claude `context: fork` удалён, поэтому `main` не создаёт отдельного агента для ревью.
- **У `eda-orhestra` появился режим исполнения.** `orhestra.execution` принимает `subagents`, `main` или `main_propagated`; default `subagents` сохраняет прежнее поведение. `main` выполняет верхние этапы текущим агентом, а `main_propagated` дополнительно передаёт `main` совместимым execute/review-этапам.
- **У `eda-polish` больше нет порога.** Цикл завершается при нуле находок или по лимиту; отсутствие прогресса его не останавливает. Аргумент вида `args: "threshold 90 limit 2"` в шаге оркестратора `eda update` приводит к виду `args: "limit 2"`.
- **У `eda-polish` появилась своя настройка исполнения.** `polish.execution` принимает `subagents` или `main`; default `subagents`. Раньше цикл полировки брал режим из `review.execution`, поэтому в проекте с `review.execution: main` `eda-polish` тоже работал без субагентов. После обновления эти настройки независимы: `review.execution` задаёт только раскладку проверок внутри `eda-review`, а прежнее поведение возвращает `polish.execution: main`.
- **Формат ревью дополнен.** У каждой находки появилось поле `repro` — чем проблема воспроизводится, — а в отчёт добавлен раздел «Отклонено» с причинами отклонения. `eda-fix-by-review` может отклонить находку, но только фактически неверную и с обоснованием в отчёте. Старые файлы ревью читаются как есть.

## Проверка миграции

После `eda update` проверь:

- старые рабочие каталоги исчезли из `docs/`, а файлы находятся в `docs/artifacts/`;
- `docs/business.md`, `docs/business/`, `docs/references.md`, `docs/references/`, `docs/arch.md` и `docs/rules.md` остались на месте;
- `docs/settings.yaml` содержит `version: 3`;
- `eda --version` выводит версию `3.3.x`;
- в `docs/settings.yaml` нет секции `plan-review.agents` и аргумента `threshold N` у шага `eda-polish`;
- в `.claude/agents/` и `.codex/agents/` не осталось файлов `eda-plan-review-*`;
- Claude-скиллы установлены в `.claude/skills/`, Codex-скиллы — в `.agents/skills/`, агенты — в `.claude/agents/` и `.codex/agents/`.

Установщик не создаёт и не перезаписывает корневой `AGENTS.md` пользовательского проекта и не удаляет чужие skills/agents.
